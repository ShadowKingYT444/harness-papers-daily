Agensh: Scaling Organizational Intelligence to 1,024 Agents

Day 14 · Oct 13, 2026

Agensh: Scaling Organizational Intelligence to 1,024 Agents

Zhihao Zhan, Ting Song, Li Dong, Shaohan Huang, Jianxun Lian, Yan Xia, Furu Wei · published 2026-09-22 · arXiv:2609.26781

relevant

One line

Agensh is a multi-agent harness with no central orchestrator: up to 1,024 concurrent workers run an identical five-step cooperation loop (gather context, claim a sub-task, act, verify, merge) coordinated only through a shared workspace, message interface, and shared context, and agent count becomes a scaling dimension for both quality and latency.

The problem

Single-agent capability is bounded by one context window, one action stream, one memory stream, and sequential execution imposes high latency on complex tasks. Existing multi-agent harnesses (Codex/Claude Code sub-agents, Copilot fleet, Kimi Agent Swarm) use orchestrator–worker structures where a main agent plans, decomposes, assigns, and integrates — but the orchestrator's capacity to coordinate workers and merge their contributions caps the whole system's scalability. The paper asks whether self-organized workers, with no central planner at all, can scale cooperation to a thousand agents and whether agent count is itself a performance scaling axis.

How it works

Agensh layers an organization harness above an unmodified single-agent harness (tested with Copilot; plug-and-play adapters exist for others). Every worker runs the same prompt (identical except worker ID) implementing a five-step cooperation loop, executed concurrently and asynchronously:

1. Gather context. Read the shared goal, peer progress, messages, and accumulated findings; identify the next useful step.

2. Claim sub-task. Propose a sub-task and announce its scope as a CLAIM appended to shared context; resolve overlaps/conflicts with peers via direct messages.

3. Take action. Solve the sub-task locally with available tools; publish reusable findings to shared context as they're established.

4. Verify results. Match local progress against the sub-task's acceptance criteria; revise until satisfied.

5. Merge progress. Integrate the contribution into the shared workspace; publish an update with what changed, the idea, and verification evidence; on merge conflict, incorporate peer progress and retry. Then loop back to step 1.

The infrastructure that makes this work without an orchestrator has three components: a shared workspace (Gitea Git — private checkouts/branches merged to main, version history, textual conflict detection, issues/PRs), a message interface (Mattermost — a shared task channel for announcements plus urgent direct messages, async delivery, conversation history), and a shared context (append-only store of typed entries: OBSERVED behavior, confirmed FACTs, FAIL (failed approaches), CLAIMs of work, PATCH_SUMMARYs — plus a context-grep tool to search full history beyond recent memory). Workers self-discover and self-assign work; integration is peer-negotiated through PRs and messages.

Key results

On the five hardest ProgramBench tasks (reproduce reference software from scratch, no internet, 6h budget; repos up to 26k files / 2.8M lines), with GPT-5.6-sol (high) and a fixed underlying harness:

  • 1→128 agents: mean final test-pass rate 19.31% → 28.78% (+9.47 pp, ≈+49% relative) across the five tasks.
  • pandoc at 1,024 agents: 33.89% (1 agent) → 50.94% (128) → 55.06% (1,024); the 1,024-agent org beats the 128-agent result by 4.12 pp and the single agent by 21.17 pp.
  • Latency: larger orgs reach a given score earlier — on pandoc, 128 agents pass 30% test-pass at the 30-minute checkpoint vs. 60 min (32 agents) and 90 min (8 agents); the single agent never clears it in 2h.
  • Emergent organization (from worker trajectories): at 8 agents, peer coordination (agreeing on module interfaces, resolving claim overlaps); at 32, multi-worker integration (peer review/approval of contributions, counterexamples, re-review); at 128, specialization and standardized workflows (reviewers chosen by prior experience, reusable integration protocols that peers revise after failures); at 1,024, role specialization (multiple integrator roles, failed-attempt takeover by same-area specialists). All of it self-organized — no worker is assigned a role.

How it relates to adaptive decomposition

Agensh is the strongest example in this set of the "agent discovers the decomposition" half of adaptive decomposition — sub-task discovery and allocation are genuinely bottom-up: workers claim work themselves, negotiate boundaries, and even revise their own cooperation protocols, with no central planner decomposing anything. But it is task decomposition for parallel execution, not harness decomposition for optimization: the cooperation loop itself is completely fixed (five steps hard-coded in an identical prompt for all 1,024 workers), there is no search over harness structure, no independent search budgets per subproblem, no splitting of failing components, no fusing of working ones, and no revert-to-monolithic behavior. What evolves is organizational behavior (roles, workflows, integration norms), not executable code. Closest structural analogue: the workers' emergent specialized roles resemble the "specialized handlers" that emerge in Growing Harness (2609.26760) — but here specialization is social, there it is programmatic.

Limits and open questions

No orchestrator-baseline comparison at matched agent counts, so it's unclear how much the gains come from self-organization vs. simply more parallel attempts (the 1→128 curve could partly be best-of-N sampling). Costs aren't reported — 1,024 agents × 6h on a frontier model is an enormous token bill, and coordination overhead (messages, context reads, merge conflicts) at that scale is unmeasured. The tasks are all "reproduce existing software" with test-pass as the metric; whether self-organization works on tasks without crisp acceptance criteria is open. Merge conflicts are textual (Git) — semantic integration conflicts are resolved by worker judgment, which may not scale. Next probe: hold total compute fixed and compare N workers × (budget/N) against 1 worker × budget, to separate the scaling-of-organization effect from the scaling-of-compute effect; and try porting the cooperation loop to a harness-optimization setting, where workers evolve harness components instead of software features.
