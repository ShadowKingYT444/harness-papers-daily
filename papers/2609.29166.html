Day 9 · Oct 08, 2026

HarnessPAI: An Evolving Harness for Physical AI

Xin Wang, Wenhao Wu, Menghao Zhang, Zhi Wang, Kun Shao, Jian Luan, Yang Li, Qing Li, Shangding Gu, Huichi Zhou, Shuqing Shi, Fei Ni, Shuo Lu, Weicheng Meng, Kang Li, Jin Wu, Kang Zhao, Shangmin Guo, Gen Li, Yongqiang Tang, Zhizhong Zhang, Yuan Xie, Heng Qu · published 2026-09-24 · arXiv:2609.29166

highly relevant

One line

An executable, evolvable code harness for physical AI that compiles perception, reasoning, action-model calls, and verification into a program that runs open-loop within a rollout and is revised across rollouts, distilling failures into a graph-structured reusable skill library.

The problem

Physical AI has fixated on the action model (VLAs/WAMs mapping observations to controls), but post-training those models can erode perceptual/reasoning capabilities and leaves them fragile to scene perturbations and long-horizon tasks. Existing harnesses around action models depend on repeated online LLM reasoning and memory retrieval during deployment — expensive and fragile. Code-as-policy approaches compile behavior into code but replace learned contact-rich control with hand-designed APIs. The gap: an executable harness that keeps the learned action model as a frozen primitive and compiles everything around it into reusable, verifiable, evolving programs.

How it works

Two timescales. Within a rollout (open-loop execution): an agent instantiates one executable program that fixes the task decomposition, perception calls, geometric reasoning, action-model invocations, and success checks — then the program runs end-to-end with no further high-level LLM deliberation, delegating contact-rich manipulation to the frozen action model. Across rollouts (closed-loop evolution): observations, execution traces, failures, and outcomes are collected as physical feedback; an agent diagnoses errors, revises the program, and distills failure-to-repair knowledge into a node-centric graph-structured skill memory that transfers across tasks sharing the same workflow stages. The converged program also becomes a cheap, reliable expert-data collector: its successful trajectories are used to fine-tune the wrapped action model itself (post-training), so the harness improves the model it wraps.

Key results

  • LIBERO-PRO (perturbation benchmark): +61.6 percentage points over the π0.5 action model it wraps; holds 96.5%, 8.8 points above the strongest harness baseline.
  • RoboCasa atomic tasks: +27.2 points over WorldDreamer.
  • Rollout execution requires no online high-level LLM deliberation once a program is selected.
  • Fine-tuning π0.5 on harness-collected expert data lifts LIBERO-PRO success from 34.9% to 73.7% (a 38.8-point gain).

How it relates to adaptive decomposition

Closest cousin among this batch. HarnessPAI evolves the harness from execution feedback and accumulates reusable components (the skill library), like the "improve components, reuse them" half of adaptive decomposition. But the unit of evolution is the whole program — revised across rollouts as a monolith — and the decomposition granularity is fixed at program-authorship time, not discovered adaptively. There is no splitting of failing subproblems, no independent per-component search budgets, no fusion of working components, no revert-to-monolithic fallback. The skill library gives reuse of repair knowledge across tasks, which is one mechanism adaptive decomposition would need, but it lacks the dynamic restructuring of the search space itself.

Limits and open questions

The framework assumes the action model is good enough as a primitive — if the base model can't do the task at all, no harness program can fix it. The evolution loop depends on an agent that can diagnose physical failures well; bad diagnoses compound. Open: does whole-program evolution scale to programs with many interdependent stages, or does the revision search blow up without component-level credit assignment? And can the graph skill memory's failure-to-repair entries transfer across embodiments, or only across tasks on the same hardware?
