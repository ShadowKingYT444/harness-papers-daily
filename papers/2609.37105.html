VACE: Validation-Gated Alternating Co-Evolution of Agent Models and Harnesses

Day 46 · Nov 14, 2026

VACE: Validation-Gated Alternating Co-Evolution of Agent Models and Harnesses

Jiexing Qi, Yu He, Jun Liu, Qichen Huang, Shaohua Hu, Zhan Dang, Guohua Chen, Rui Yang, Wen Jiang, Yang Liu, Tao Lyu, Fangming Li · published 2026-09-29 · arXiv:2609.37105

relevant

One line

Alternates agentic RL (weight updates) with trajectory-driven harness revision, and — the key move — validates each proposed harness at the updated checkpoint, adopting it only if it strictly improves validation before it can shape the next RL round.

The problem

Model weights and the harness are coupled: weight updates change how the model uses the harness, while harness updates change the trajectories the model trains on. Optimizing one while fixing the other leaves the interaction unaddressed — a skill tuned for an early checkpoint can become a straitjacket after training, and a new workflow can expose decisions the model hasn't learned. The authors note the reverse hazard too: harness refinement proposes discrete changes from trajectory feedback that need not actually help the updated model (e.g., extra retrieval improves evidence coverage but burns the interaction budget on easy tasks). Since an adopted revision changes the trajectories of the next RL stage, a bad revision poisons downstream training — so proposal and acceptance should be separate decisions.

How it works

Each round of the loop has three stages:

1. RL stage: train the model with agentic RL (GRPO with DAPO-style oversampling, outcome rewards only — binary correctness on OfficeQA, dense partial credit on AutomationBench) under the current harness fixed, collecting trajectories T_t. Weight update is always retained.

2. Harness proposal: a HarnessEvolve-style optimizer S uses T_t (failed executions as diagnostic evidence) to propose a single harness revision H'_t — edits scoped to skills and execution guidance, tool semantics and environment rules held fixed.

3. Validation gate: with the updated model W_{t+1} held fixed, evaluate incumbent H_t and candidate H'_t on the same validation tasks with the same evaluator. Adopt only on strict improvement (Δ > 0; ties keep the incumbent). The retained harness governs the next RL round.

Implementation runs through Uni-Agent connecting execution, trajectory collection, RL, and harness refinement. Scheduling variants tested: WHALE-style (same alternation but commits every harness proposal ungated) and SIA-style (harness-first, then RL under the frozen best harness), all sharing the same optimizers so the only difference is the schedule/gate.

Key results

Qwen3.5-9B on OfficeQA (84/53/109 train/val/test) and AutomationBench (209-task HR/Marketing/Finance subset, 80/58/71 split):

  • VACE: 45.26% test accuracy on OfficeQA, 75.19% mean partial credit on AutomationBench — +13.15 and +24.94 pp over the static agent, +9.98/+13.58 over harness-only, +6.43/+9.09 pp over weight-only RL (38.83% / 66.10%).
  • vs ungated alternation: +4.59 pp on OfficeQA (45.26 vs 40.67) and +6.95 pp on AutomationBench (75.19 vs 68.25) — the gate itself is worth several points.
  • vs SIA-style harness-first: +4.59 pp on OfficeQA and +9.85 pp on AutomationBench (75.19 vs 65.35) — repeated alternation beats front-loading all harness work.
  • The gate earns its keep: across 44 harness proposals, 25 accepted, 17 rejected as regressions at the updated checkpoint, 2 ties (OfficeQA 7/2/3 of 12; AutomationBench 18/0/14 of 32). Rejections are large when they happen — one OfficeQA proposal dropped validation 11.31 pp (60.37 → 49.06) despite being generated to fix observed failures; accepting it would have corrupted the next RL stage.
  • Validation trajectories rise 30.28% → 47.17% (OfficeQA, +16.89 pp) and 53.08% → 81.42% (AutomationBench, +28.34 pp), though progress is non-monotonic — weight stages can also reduce the score, and the gate only compares harnesses at the current checkpoint.

How it relates to adaptive decomposition

Two things here matter for adaptive decomposition, and one big thing is missing. First, VACE is the cleanest empirical confirmation yet of the coupling worry that runs through the co-evolution literature (and that RLHarness flags): when the model and the harness move together, naive alternation adopts revisions that actively hurt the checkpoint they'll run with — 17 of 44 proposals here. That's directly relevant to a system that splits and fuses harness components online: each split/fuse proposal is a discrete structural change whose value can only be judged at the current checkpoint, and adopting a bad one reshapes all subsequent training data. I'd steal the checkpoint-specific validation gate as the acceptance rule for component-level proposals — it transfers cleanly.

Second, the joint model+harness framing is the right level of generality: harness search and weight training aren't separate pipelines but one co-evolutionary loop sharing trajectories. But the harness side is resolutely monolithic: each proposal is a single whole-harness revision (edits to "skills and execution guidance"), with no decomposition into independently-mutable components. There is no split/fuse operator, no notion of component granularity, no per-component budget — the proposal optimizer just rewrites whatever the trajectories suggest. So VACE says nothing about who discovers the decomposition; it's HarnessEvolve (the proposer VACE builds on, which already has quality checks and performance-based selection) that does the revision work, and that work is whole-harness. Adaptive decomposition's central question — the agent itself deciding when and how finely to carve the harness up — is untouched. Compared to PluginRSI's component-level evolution, VACE is one level coarser on the harness side and one level deeper on the model side.

Limits and open questions

The paper's own §5 is honest: repeated validation-set reuse invites adaptive selection effects, and the strict-improvement gate leans on noisy point estimates — with 44 accept/reject decisions on a 53-task and 58-task validation set, some of those rejections/acceptances are surely noise, not signal. I'd probe whether the gate holds up with a held-out acceptance set rather than the selection set. Scope is narrow: one model (Qwen3.5-9B), two benchmarks, edits limited to skills and execution guidance. The schedule is fixed (one proposal per RL stage) — the authors flag feedback-driven scheduling as future work, and I'd bet a component-level version of VACE would need it, since different components learn at different rates. Also worth noting: WHALE (ungated alternation, concurrent work) and Co-Harness (alternates failure-driven harness refinement with supervised training and also validates) are converging on the same loop from adjacent angles, so the "alternation + gate" pattern is becoming consensus rather than a differentiator — the differentiator left is what gets proposed, i.e., the granularity of the revision, which is exactly where adaptive decomposition sits.
