Grow the Harness, Not the Context: From Strategy-Free Scaffolds to Reusable Specialist Agents

Laizhen Li, Jiarui Li, Juanjuan Zhao, Kejiang Ye, Ye Li, Cheng-zhong Xu, Xitong Gao · published 2026-09-22 · arXiv:2609.26760

highly relevant

One line

Growing Harness learns the agent harness itself from a strategy-free scaffold: an offline optimizer turns recurring control decisions into persistent executable code, guided by failure-localizing execution traces and guarded by a held-out success gate, so the deployed LLM only handles task-specific semantic reasoning.

The problem

Agents repeatedly serving one task family keep asking the LLM to reconstruct the same control decisions (refine queries, filter observations, verify progress, recover from errors, decide when to stop) inside every task's context — each decision costs another inference call and grows context. Prior work either reuses experience as retrieved text/workflows (which the model must reinterpret online) or optimizes prompts/demos of an existing controller. The gap: nobody grows the executable harness program itself from a strategy-free starting point, so control structure can emerge from task feedback rather than being fixed in advance or delegated to inference every time. Three challenges: (a) decide what becomes code vs. what stays an LLM call; (b) optimize a growing program without the search space growing with it; (c) avoid brittle/instance-specific edits and regression of earlier gains during continual optimization.

How it works

The setup fixes the LLM backend M and tool interfaces T; only the harness code h ∈ H is learnable. Training starts from a minimal strategy-free scaffold h0 — an entry point plus model/tool interfaces, no ReAct-style controller. The failure-guided loop (Algorithm 1):

1. Execute and collect failures. Run the current harness ht on the training stream; each task produces a trace τi = (xi, Gi, yi, oi, ui) where Gi is a function-level execution DAG (nodes = harness-function invocations, LLM/tool calls, errors; edges = dynamic scope). Keep a bounded failure window Wt of capacity K (each entry: task, latest trace, repair-attempt count).

2. Trace-local optimization. An offline optimizer (a different, stronger model, e.g. GPT-5.6-terra High) receives ht, the failure traces, and diagnostic artifacts, and synthesizes a complete candidate. Edits are constrained to the trace scope: the optimizer may modify only main and functions invoked by a supplied failure trace, At = {main} ∪ F(τi), plus add new helpers; it must preserve signatures, cannot delete functions, cannot encode task IDs/answers, and the edit distance dfun(ht, candidate) ≤ L (edit budget). Guidance: implement deterministic, reusable operations in code (parsing, validation, state updates, query refinement, error recovery, stopping); keep LLM calls for semantic interpretation, synthesis, fuzzy comparison, answer generation.

3. Joint repair. The candidate is re-executed on the whole window; it must fix at least Q failures (|Pt| ≥ Q), else it's discarded (with attempt counts incremented, tasks retired at Rmax attempts).

4. Success-first held-out gate. Accepted candidates are re-evaluated on gate set G after every Q solved tasks: accept iff SR_G(ht) ≥ SR_G(hgate); otherwise roll back the entire repair sequence since the last checkpoint (code, task cursor, window, counters — transactional restore). Lower online cost can never compensate for lower gate success.

5. Accumulate. Repaired behavior becomes ordinary program paths in one shared harness, reusable by all later tasks. After the stream is exhausted, h* is evaluated once on the final test set Dte.

Key results

Evaluated on BrowseComp-Plus and WebArena-Verified (200 training / 50 gate / 50 test tasks each) with three deployment models (gpt-oss-120b, gpt-oss-20b, Qwen3.5-4B), vs. Tool-Calling, Self-Ask, IRCoT, WebDreamer, AgentOccam (all means over 3 runs):

  • Highest mean success in 5 of 6 benchmark–model settings; trails the best by 0.7 pp in the sixth.
  • vs. Tool-Calling: 76.0–91.8% fewer LLM calls and 74.4–98.6% lower deployed-agent inference cost.
  • On WebArena-Verified, success stays 44.7–45.3% across all three model scales, while Tool-Calling collapses from 30.0% (120b) to 6.7% (4B) — the biggest gains come with the smallest model.
  • Ablations (BrowseComp-Plus, gpt-oss-20b, 10 steps, single runs on the 50-task test set): full method 36.0% vs. 18.0% without function-level guidance, 22.0% without gate validation (gate success rose to 30% then fell to 16% without rollback), 28.0% without the multi-failure window (K=1).
  • Emergent structure: both harnesses grew from the same seed, yet BrowseComp-Plus converged to a single shared retrieval/verification pipeline while WebArena-Verified grew specialized handlers (Shopping, Reddit, Map) around a general LLM-guided browser loop — the task family shapes the controller.

How it relates to adaptive decomposition

This is the closest cousin in the set to adaptive decomposition, but it is not the same mechanism. The harness does develop emergent modularity — specialized handlers grow around a general loop, i.e. the structure is discovered from task feedback rather than human-designed, and the gate-rollback is a direct analogue of the "revert when local gains harm global behavior" rule. What it lacks: no explicit split/fuse operators (repairs are synthesizer-proposed code edits, never a "split this failing component in two" or "fuse these working helpers" primitive), no independent search budgets per subproblem (one shared failure window, one candidate per round), no parallel component evolution, and no revert-to-monolithic behavior. The optimizer is also external and offline (GPT-5.6-terra), not the deployed agent rewriting itself. Action set: open-ended code synthesis within trace scope and edit budget — evolvable structure, but via LLM code generation rather than structural mutation operators.

Limits and open questions

Requires a repeated task family to amortize offline optimization — gains must offset the optimizer's cost, and the paper gives no accounting of total training compute. The fixed model/tool interfaces are still human-designed, so "low prior commitment" is only partial. The success-first gate can't catch regressions on behavior outside the 50-task gate set. Ablations are single runs; main results have wide confidence intervals (±10–13 pp on success rate). Real deployment needs sandboxing and permission boundaries for optimizer-generated code, which the paper flags but doesn't solve. Next probe: add explicit split/fuse structural operators and per-component search budgets to see whether the emergent modularity sharpens into a true adaptive decomposition; and test whether the growth loop works when the optimizer model is the same small model being deployed.
