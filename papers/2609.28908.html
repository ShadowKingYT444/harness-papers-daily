Automatic Harness Evolution for Hardware Design Verification: Can LLMs Consolidate Gains Across Discovered Harnesses?

Kidus Seyoum, Ajay Mittur · published 2026-09-24 · arXiv:2609.28908

highly relevant

One line

An LLM-driven outer loop evolves agent harnesses (runtime + scaffold) around a fixed subject model on 12 proprietary hardware root-cause tasks, and finds that while evolved harnesses complete far more attempts and cover more tasks, gains from different candidates exchange rather than consolidate into a single dominant harness.

The problem

An agent's behavior depends heavily on its harness — the external runtime control layer running the model–tool loop, context management, and stopping/finalization policy — but almost all harness knowledge comes from mainstream software/NLP settings. Hardware design-verification debugging (tracing a regression failure to a root cause across RTL, testbench, and simulation state) is a "lower-resource domain": few public traces, demos, or docs. The authors ask whether automatic harness evolution can compensate for that gap without touching model weights, and specifically whether gains discovered across many evolved candidates can be consolidated into one harness.

How it works

A subject model (fixed per campaign) runs tasks inside a candidate harness; a separate LLM optimizer (Claude Opus 4.8/5, distinct from the subject) proposes new candidates. Every candidate is materialized in an isolated directory with its manifest, lineage, traces, scores, and failure labels, then evaluated on benchmark tasks and kept in a first-class archive (Algorithm 1 in the paper: baseline → summarize evidence → branch candidates → activation check → evaluate → confirm promising ones with more trials → promote or archive). Two search styles are used: prompt-constrained (edit instructions/skills to fix speculative search, unbounded reads, late commitment, timeouts) and whole-harness (also change executable checks, read limits, turn management, runner behavior, finalization). Activation checks verify a proposed rule actually reaches the rendered subject harness before its score is interpreted; failures are classified (malformed, activation failure, provider/environment, timeout, incorrect, correct). The campaign covers three distinct subject harnesses (internal terminal agent, custom OpenAI-Agents-SDK Python harness, Codex CLI), with Kimi K3 as the subject in the final repeated five-trial study. A CVDP (Verilog RTL generation/repair) cross-benchmark case study uses a separate fixed subject model (GLM-5.2) with an executable functional verifier scored only after outputs complete.

Key results

On the 12 proprietary root-cause tasks, five trials per task, matched Kimi K3 protocol: an evidence-grounded harness raised first-trial success 2/12 → 6/12, pass@5 5/12 → 9/12, and completion 34/60 → 58/60; a later batched-causal harness reached 60/60 completion and 10/12 pass@5 but regressed first-trial and Success≥2/5 back to 5/12. Total correct attempts improved only 17/60 → 20/60 → 21/60 — gains came mostly from completion and breadth, not repeated correctness. The two evolved harnesses together solved 11/12 tasks (T1 unsolved), but neither dominated. Consolidation failure is the central finding: a 990-branch run's promoted incumbent froze at 3/12 while the archive union covered 10/12; a DeepSeek validation-set gain (mean score 0.375 → 0.725) collapsed to near-zero in a 12-task replay; domain-context treatments (curated docs, retrieval, term density 11→25/1k words) showed no lift and cost ~30% more tokens. In the CVDP case study, an evolved defined-width repair harness passed 61/142 vs 45/142 for the reference verification loop (+35.6% functional passes). The authors conclude: treat the archive as the output, route among complementary harnesses, confirm promotions with repeated task-level trials, and enforce critical constraints in code rather than instructions.

How it relates to adaptive decomposition

This paper is the closest empirical cousin to the consolidation question: it explicitly tests whether specialized behaviors discovered in different candidates can be fused into one stronger harness, and the answer in this lineage is no — useful search, evidence, and finalization behaviors appeared in different candidates but "did not consistently consolidate," and a later candidate that explicitly inherited earlier rules still exchanged gains across tasks (winning pass@5 while losing first-trial coverage). There is no agent-discovered decomposition here: each candidate is a monolithic harness (instruction set + runtime policy); branching creates sibling variants with independent evaluation, and the archive union is portfolio selection, not fusing of subproblem components. Action space is evolvable (whole-harness code edits), and the paper's own recommendation — "route among modular harnesses instead of continually extending one instruction set" — points at exactly the gap adaptive decomposition fills: an agent that discovers the decomposition, gives subproblems independent budgets, splits failing pieces further, fuses working ones, and reverts to monolithic state when local/global correctness disagree. This paper supplies the negative baseline: without that mechanism, evolution produces complementary specialists and an archive you must select from.

Limits and open questions

The strongest repeated result is only 12 proprietary tasks — too small for broad claims, and the authors deliberately didn't scale because "no evolved harness reliably fit even the existing set." Score changes can't be attributed to single edits (candidates differ in many controls at once; completion and diagnostic behavior changed together), five trials reduce but don't remove sampling noise, and earlier runs used single-trial promotion. The validation-set gain that failed to persist wasn't an independent generalization test (the replay reused the search tasks). Open probe: is the consolidation failure optimizer choice, instruction interaction, subject-model compliance, or just sampling variation? — the artifacts can't say. For adaptive decomposition this is the key prediction to test: if per-subproblem independent budgets plus explicit fuse/revert logic can do what this lineage could not, that's the head-to-head experiment worth running.
