Video-RSI: Recursive Self-Improvement of Video Understanding Agents via Harness Evolution

Video-RSI: Recursive Self-Improvement of Video Understanding Agents via Harness Evolution

Bingjun Luo, Jialin Guo, Siqi Li · published 2026-09-29 · arXiv:2609.37950

relevant

One line

The same frozen language model acts as both Solver and Editor: it actively revisits training videos to diagnose failures before editing its own executable harness, and a revision is kept only if it passes a gate on both answer accuracy and visual observation cost.

The problem

An execution trace contains only what the current harness chose to observe, so competing failure explanations stay unresolved: a missing event could mean the agent never looked (sampling gap), looked but misperceived (perception error), or saw it but failed to use the evidence (reasoning failure) — each demanding a different code fix. And fixing a failure doesn't automatically make a better harness: denser sampling can fix one answer while inflating frame usage everywhere else. So a video-agent RSI loop needs (a) better evidence for what to change than the trace alone, and (b) a retention criterion that weighs accuracy against visual cost.

How it works

A harness H governs evidence acquisition and use; running it produces (ŷ, τ, c) = Run(H, V, q; M) — answer, trace, resource record — with model services M frozen. Each of 20 attempts runs:

1. Active Video Investigation: the Editor examines training traces and formulates diagnostic queries that vary the temporal region, sampling density, modality (video/transcript/OCR), or perceptual question to test competing explanations — e.g., denser inspection reveals whether a short event fell between sampled frames. The Editor accumulates evidence across queries with the incumbent harness untouched, and ends with either a supported revision hypothesis or an unresolved case. Crucially, the resulting revision must use only cues the Solver can access on new questions (training annotations may locate intervals during diagnosis, but the fix can't depend on them).

2. Diagnosis-guided revision: the Editor maps the diagnosis to code changes spanning prompt construction, tool implementation, observation processing, memory, and execution control, specifying applicable conditions and successful behaviors to preserve (a reusable fix may need coordinated edits to a tool and its consumer).

3. Cost-aware selection: the candidate and incumbent are compared on a private, video-disjoint selection set (72 LVBench questions; per-item outcomes hidden, only aggregate feedback to the Editor). With accuracy A and mean frame count C, the gate admits two improvement directions: accuracy gain with bounded cost growth (ΔA > 0 and Ĉ ≤ (1+α)C), or cost reduction with bounded accuracy loss (−ε ≤ ΔA ≤ 0 and Ĉ ≤ (1−β)C). The experiments fix α = 0.1, β = 0.2, ε = 1/|Dg|.

Solver/Editor are DeepSeek-V4-Pro with Qwen3.6Plus for visual observations; investigation used 216 LVBench questions, with evolution offline and the final harness frozen for evaluation.

Key results

  • Four benchmarks (MLVU test, LongVideoBench long, Video-MME long, EgoSchema): the evolved harness beats the initial HS0 on accuracy while using 10.8–44.1% fewer frames.
  • Active investigation vs trace-only revision: higher final accuracy on all four benchmarks; on MLVU the gain is 8.2 percentage points at similar inference-time frame usage. Investigation also retained more revisions (5 of 20 vs 3).
  • Cost-aware gate vs accuracy-only gate: higher accuracy with fewer frames on every benchmark (roughly half the frames on Video-MME).
  • vs reproduced VideoSeek and VideoHarness-RSI (same model): higher accuracy on all four benchmarks with lower frame usage in all but the Video-MME/VideoSeek comparison.
  • Retained code changes: HS2 replaced free-form visual responses with goal-directed structured observations (findings + image references + uncertainty, mapped to frame timestamps); HS4 added a relation-graph mechanism that extracts entities/events/relations from accumulated observations to surface evidence gaps without processing new frames; HS3 added a Global-64 route (wider initial overview for whole-video questions); HS5 added an occurrence tool for counting with duplicate consolidation.
  • Dynamics caveat: the first accepted revision cut frames but lowered MLVU accuracy despite improving both dev metrics; accuracy recovered later, with the final two accepted revisions accounting for most of the net MLVU gain — dev-set gains don't transfer monotonically.

How it relates to adaptive decomposition

The Editor revises the harness as a monolithic code artifact — there is no decomposition of the harness into independently-evolved components, no split of a failing component, no fusion of working ones, and no per-component search budgets. Diagnosis is whole-harness (distinguishing failure explanations), and each revision is a whole-harness rewrite gated by global metrics. The cost-aware gate does have a faint echo of the user's "revert when local and global correctness disagree" instinct — a locally-useful repair gets rejected if it regresses the global accuracy–cost balance — but the retention decision is centralized, not per-component. The most transferable lesson for adaptive decomposition is methodological: diagnosis quality dominates — going back to the source to test competing hypotheses beat trace-only revision by 8.2pp, suggesting a per-component version of adaptive decomposition would similarly benefit from hypothesis-driven, evidence-gathering diagnosis of why a component fails before deciding to split it.

Limits and open questions

Video-domain only; nothing says the loop transfers to non-visual harnesses. Because revisions are monolithic rewrites, a bottleneck that cuts across the prompt/tool/memory boundary can only be fixed by one coordinated edit — the Editor is expected to get cross-component coupling right in a single shot, with no mechanism to evolve components against each other. The selection set is small (72 questions, and ε allows exactly one fewer correct answer), aggregate-only feedback may throttle what the Editor can learn, and cost is measured in frames rather than total compute. I'd also want to know whether investigation helps because of new evidence or simply because the Editor gets more inference budget pre-edit — the controlled variant shares per-attempt resource limits, which partially addresses this, but the marginal value of each extra diagnostic query isn't quantified.
