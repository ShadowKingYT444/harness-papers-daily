ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement

Day 53 · Nov 21, 2026

ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement

Siwei Wu, Jincheng Ren, Yizhi Li, Haau-Sing Li, Chengran Yang, Yuxuan Zhang, Weicheng Gu, Jian Yang, Riza Batista-Navarro, Chuanyi Zhang, Xianglong Liu, Ming Zhou, Bryan Dai, Chenghua Lin · published 2026-09-14 · arXiv:2609.14857

core mechanism

One line

Split the harness into five fixed functional modules, evolve each independently from contrastive trajectory evidence on benchmark-disjoint tasks, then integrate — and the result transfers across benchmarks and foundation models, while joint or whole-harness evolution actually hurts.

The problem

Harness RSI has a generalization problem with three coupled roots. First, nearly every existing method evolves on data drawn from the evaluation benchmarks (or their subsets), so nobody can tell whether the "improved" harness learned reusable mechanisms or just adapted to benchmark-specific patterns. Second, trajectory-level ambiguity: a single success/failure trace entangles systematic harness deficiencies with instance-specific reasoning, so edits derived from it transfer poorly. Third, mechanism-level credit assignment: even when a recurring deficiency is identified, a monolithic harness gives no principled way to localize which component is at fault, so whole-harness optimization entangles unrelated mechanisms.

How it works

ModularRSI has three stages. (1) Contrastive trajectory sampling and analysis. For each evolution task the agent rolls out K times; tasks are binned into Positive (all succeed), Negative (all fail), and Contrastive (mixed). Same-task success/failure pairs are compared to identify function-level factors behind different outcomes; a Trajectory Memory supplies historical successes for all-fail tasks. A Code-Modify Agent (the agent under evolution itself) consolidates diagnoses into structured JSON findings per batch, with per-function candidate modifications ranked by vote count across distinct supporting tasks. (2) Module-wise evolution. The harness (Terminus-2 from Harbor, reorganized) is decomposed into five functional modules — Agent Loop, Observation Management, Tool Use, Context Management, Task Completion Detection — each evolved independently within a restricted modification scope, in parallel, with per-function Evolution History to prevent oscillation. (3) Validation gates + integration. Program checks (AST, imports, protocol compliance), a diff review that rejects task-specific hacks, and execution validation on sampled tasks, each with rollback. Then a cross-module integration epoch resolves conflicts/duplication between independently evolved modules. The function library is frozen before downstream evaluation. The evolution pool is 2,000 independently curated executable tasks, filtered for instance-level similarity against downstream benchmarks.

Key results

With DeepSeek-V4-Flash-Preview as backbone, in-domain evolution improves TerminalBench 2.0 accuracy 47.57 → 52.43 and SWE-Bench Verified 73.40 → 76.45. The gains transfer across domains: the TB-evolved harness reaches 75.80 on SWE-Bench Verified, the SWE-evolved one 49.40 on TerminalBench 2.0. Pass3 on TB 2.0 jumps 30.34 → 35.96, i.e. fewer stochastic failures, not just higher means. The frozen evolved harness transfers across foundation models on TB 2.0: GLM-5.2 59.55 → 61.80, MiniMax-2.5 41.57 → 44.94. The ablation is the headline: modular evolution + integration reaches 52.43 while joint all-module evolution drops to 44.19 and non-modular whole-harness evolution drops to 46.44 — below the 47.57 baseline. Single-module evolution of any one module helps (49.44–50.56), and integration beats every single module. Code and datasets are released at github.com/IQuestLab/ModularRSI.

How it relates to adaptive decomposition

This is the closest thing in the literature to the user's mechanism — and the sharpest contrast with it. ModularRSI demonstrates the core claim empirically: decomposition is the thing that makes harness evolution work, and monolithic evolution fails (their ablation shows it regressing below baseline). But the decomposition is human-designed and fixed — five modules chosen by the authors from their reading of harness code. Adaptive decomposition starts where this paper stops: the agent discovers the decomposition itself, failing components split recursively, working ones fuse. Two things here are directly reusable: (a) the contrastive same-task trajectory analysis as a credit-assignment primitive for deciding which component gets blamed for a failure — exactly the signal adaptive decomposition needs to drive split decisions; (b) the empirical warning that independent evolution needs an integration stage, since independently evolved modules can conflict — the fuse step in adaptive decomposition will face the same conflict-resolution problem. Also note the benchmark-disjoint protocol: 2,000 curated tasks with similarity filtering is the honest version of the "train on dev, report on test" discipline the user's own evaluation needs.

Limits and open questions

The authors state two limitations themselves: no dedicated ablation isolating the contrastive trajectory analysis (its contribution is argued from case studies), and the main evolution used only a subset of the 2,000 curated instances due to compute cost. Deeper: the five-module decomposition is asserted, not derived — the paper never asks whether a different or finer decomposition would do better, which is precisely the question adaptive decomposition is built to answer. The cross-module integration epoch is a single pass of conflict repair, not a principled composition operator. And while the harness is frozen before eval (good), the evolution tasks were curated by humans with category labels guiding instance search — the "disjoint" claim rests on similarity filtering the authors designed, not on a truly held-out distribution.
