Turbo Harness: Instance-Adaptive Harness Optimization

Day 63 · Dec 01, 2026

Turbo Harness: Instance-Adaptive Harness Optimization

Tunyu Zhang, Hao Wang, Kai Xu, Dimitris N. Metaxas · published 2026-09-30 · arXiv:2609.40330

highly relevant

One line

Turbo Harness: adapts a globally optimized harness (e.g. from Meta-Harness) to each task instance by recycling the completed search's "exhaust" — candidate harnesses, traces, reflections — into a structured playbook of successful and failed editing strategies, then RL-training a small editor model (Qwen3.5-9B, via GRPO) that emits a single per-instance code patch to the global harness at inference time, falling back to the global harness when the patch fails to apply.

The problem

Every existing harness optimizer produces one global harness applied uniformly across all test instances — yet different instances may need different harness configurations (e.g. SWE-Bench-style issues from different repos with different dev workflows and testing conventions). Second, harness search is expensive and generates a rich archive of tried strategies, most of which is discarded once the global harness is chosen. The question: can that discarded optimization experience be reused to tailor the global harness per instance, without a fresh multi-round search per instance?

How it works

(1) Playbook distillation: the outer-loop search archive (all evaluated harnesses, including discarded candidates) is summarized ACE-style into a playbook recording both successful and unsuccessful harness-editing strategies plus the conditions under which they help. (2) Editor training: for each training instance, the editor samples G candidate patches to H\, each is applied and evaluated by running the frozen execution model, and GRPO updates the editor using advantages computed from the same instance's G relative rewards; patches that can't be applied or fail validation get zero reward and are never executed. (3) Inference: one editor call per instance produces a single patch p_x, giving H_x = H\ ⊕ p_x for the frozen execution model to run — no two-pass "run, fail, then patch" procedure. The playbook is held fixed during training and evaluation.

Key results

  • Four agentic benchmarks (frozen Qwen3.5-9B editor, frozen executor): Turbo beats Meta-Harness everywhere — ALFWorld +10.0pp (60.7→70.7), ScienceWorld +7.3 (35.1→42.4), DBBench +4.2, WebShop 42.0 vs 40.0 (Harness-R1: 42.2); beats ReAct, Self-Refine, Reflection on every benchmark.
  • SWE-smith-MR: Haiku pass rate 50.7→64.0, Gemini 70.7→88.0 (+17.3pp); average over both coding benchmarks, GEPA and ACE context/prompt methods top out well below Turbo.
  • SWE-bench Verified: Gemini 38.4→54.4, Haiku 56.7→59.3 (+2.7 — small because Meta-Harness already captured most of Haiku's headroom, which the paper calls out explicitly).
  • Terminal-Bench-2.1 (Sonnet 4.5, 44 tasks): Turbo 55.5%, top of five runs, +5.0 over Meta-Harness and +3.2 over the strongest human-designed harness (Terminus-Kira); also cheapest among competitive harnesses (turns 76.3→71.2, $1.56→$1.38 per task vs Meta-Harness). Meta-Harness did not beat human harnesses here, so this is a strict test.
  • Ablations (SWE-smith-MR): neither playbook alone nor RL alone beats Meta-Harness — untrained 9B + playbook 50.0%, RL-trained editor without playbook 49.3%; combined 64.0%. RL lets a small editor match a frozen Opus-4.6 as editor (61.3) and beat frozen Sonnet-4.5 (55.3).

How it relates to adaptive decomposition

Turbo Harness is evidence for the same disease, a different treatment. It agrees a single monolithic harness leaves headroom on the table, but attacks it at instance granularity rather than component granularity: one global H\ plus per-instance patches. Adaptive decomposition's whole point is to reorganize the harness into independently evolvable components with per-component search budgets, split failing components, fuse working ones, and revert when local and global disagree. Turbo does none of that — the search object is still the full harness (patch candidates evaluated whole), the playbook catalogs editing strategies rather than component failure modes, and the only fallback is "patch didn't apply → keep H\" (a monolithic fallback, in adaptive-decomposition terms, not a component revert). It's supportive as motivation (their headline gains quantify the cost of one-size-fits-all) and the reusable-archive idea maps well onto a component-level evolutionary loop — an adaptive-decomposition run would produce exactly the kind of rich, discarded per-component search exhaust a future "Turbo per component" could recycle — but mechanistically it's orthogonal, operating one level coarser. Does not compete: instance-level patching and component-level decomposition could stack.

Limits and open questions

Effectiveness depends on the quality and diversity of the completed global search — weak or uninformative outer-loop archives yield weak playbooks (stated limitation). Training the editor needs extra environment rollouts, costly on agentic tasks (stated limitation). When the global harness already captures most headroom, per-instance adaptation adds little (Haiku on SWE-bench Verified: +2.7pp and slightly more steps). Open, flagged as future work: whether editors and playbooks transfer across tasks, domains, or harness-search runs; also whether per-instance editing can compound errors or oscillate across related instances is untested. And reported execution-cost savings exclude both the offline optimization and the one editor call per instance.
