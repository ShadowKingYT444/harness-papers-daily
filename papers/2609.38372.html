Self-Evolving Harness on Multiple Tasks with the Agent as Its Own Optimizer

Qiankai Xu · published 2026-09-29 · arXiv:2609.38372

core mechanism

One line

The closest-to-RSI harness-evolution setup yet: the same frozen frontier model (GPT-5.6 Sol), running on the same harness it is modifying, plays both solver and proposer — starting from a 49-line seed harness, with no human-designed outer pipeline and no restriction on what can be edited — and evolves a harness that beats Codex on in-distribution tasks and matches it on out-of-distribution ones.

The problem

Existing self-evolving-harness work violates the RSI spirit in four ways: (1) the proposer is usually a stronger model than the solver (e.g., Meta-Harness uses Claude Opus 4.6 to evolve harnesses for weaker models); (2) the proposer runs on a fixed human-designed harness, so improvements never compound in the improver itself; (3) editable components/edit types are fixed in advance; (4) the outer loop adds human-designed steps (trajectory organizers, preset structures). Meanwhile, evolved harnesses tend to memorize their training benchmark, with gains shrinking or vanishing on new tasks. The paper asks what a minimal-prior, genuinely self-improving harness framework looks like — and whether its improvements generalize.

How it works

The framework has three design pillars. Same model, same harness, both roles: a frozen model M plays solver (solves tasks) and proposer (reads the complete previous batch's run records — trajectories, scores, grader outputs, unsummarized — plus the current harness code and "evolution notes," then directly edits the harness files). The proposer runs on the harness it modifies, so solver improvements are proposer improvements. Maximal edit freedom: apart from the fixed execution interface, any file can be created, deleted, or rewritten; the seed is a 49-line Python file (system prompt + bash tool + minimal loop). Generalization by design: each evolution batch mixes 12 fresh tasks from each of 5 benchmarks in different domains (Terminal-Bench 2.1, GAIA2, OfficeQA Pro, τ³-bench banking, SWE-Bench Pro); train/held-out splits are strict; 5 additional benchmarks are held out entirely as out-of-distribution tests; the proposer prompt stresses generalization over memorization. The process is framed as deep-learning training: harness source code = parameters θ, task batch = training batch, solving+grading = forward pass + loss, proposer rewrite = parameter update, new-lines budget = learning rate (decaying across iterations), evolution notes = optimizer state (Adam's first-moment analogy). Stage 1 = multi-task pretraining (5 iterations); Stage 2 = continual training (2 iterations on new-domain Claw-Eval tasks + 20 "success anchors" replayed from Stage 1).

Key results

  • Harness grows 49 → 430 lines (Stage 1) → 524 lines (Stage 2); mechanisms emerged from the model's own experience: output truncation, command time limits, history compaction, independent review, and (Stage 2) a visual inspection budget.
  • In-distribution (held-out tasks of the 5 evolution benchmarks): Iteration 5 averages 60.17, +4.48 over the seed and +2.99 over Codex. Gains concentrate on long-horizon benchmarks: Terminal-Bench 2.1 66.67→83.91, SWE-Bench Pro 51.00→61.00.
  • Out-of-distribution (5 never-seen benchmarks): Iteration 5 averages 70.45, +12.64 over seed, within 1 point of Codex (70.57). BrowseComp-Plus jumps 34.00→90.00 (vs Codex 93.00), mostly from output truncation.
  • Continual training: Iteration 7 raises Claw-Eval 66.17→68.06 (passed tasks 52→57), exceeding Codex, while replay keeps Stage-1 abilities.
  • On OfficeQA Pro and τ³-bench banking the evolved harness trails the seed — task-by-task analysis attributes this to ambiguous questions and business-judgment errors, not harness mechanisms.

How it relates to adaptive decomposition

This is the monolithic-RSI baseline against which adaptive decomposition must be measured. It implements the hardest version of self-improvement — same model, same harness, no human priors, unrestricted edits — and still evolves the harness as a single undifferentiated blob: whole-harness rewrites, one batch at a time, no decomposition into components, no per-component search budgets, no splitting of failing parts, no fusing of working ones, no monolithic-fallback logic. Two of the paper's own findings are arguments for adaptive decomposition. First, "freedom without diversity": despite unrestricted edit scope, edits narrowed to a few mechanisms (truncation, compaction, review) — skills, memory, and sub-agents, all mentioned in the prompt, never appeared. Structural diversity must be enforced (e.g., by splitting the harness into independently-evolved components), not hoped for. Second, "acceptance without validation": a new version is accepted if it merely runs — no validation gate compares old vs new — which the author flags as the framework's biggest missing piece (exactly the VACE-style gate). Adaptive decomposition's answer: decompose first, then each component gets its own budget and its own gate, and local-vs-global disagreement triggers reversion rather than silent acceptance.

Limits and open questions

Single strong model (GPT-5.6 Sol high) — whether weaker models can run this loop is untested. Evolution is stochastic with a single chain reported; reruns may produce different mechanisms. Some benchmarks have few held-out tasks, and run-to-run model randomness has "a sizable effect on individual benchmarks," so small differences need caution. Only one new domain in Stage 2. The author's three costs are the research agenda: local fixes with side effects (edits target one batch's failures, regressions surface later), acceptance without validation, and freedom without diversity (the author suggests DGM-style multiple version lineages as a remedy). Open, and directly relevant: would running this same loop on a decomposed harness — where the proposer edits components independently with separate budgets — preserve the generalization gains while fixing the diversity collapse? The paper never tries.
