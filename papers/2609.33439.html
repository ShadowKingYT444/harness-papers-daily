Raven: The Harness of Harnesses for Composable Agentic Intelligence

Day 11 · Oct 10, 2026

Raven: The Harness of Harnesses for Composable Agentic Intelligence

EverMind AI · published 2026-09-27 · arXiv:2609.33439

highly relevant

One line

Raven is an open-source multi-agent ecosystem ("Harness of Harnesses") whose Host Agent decomposes goals into executable subtask DAGs over a roster of specialist agents (Research/Code/Design/Oncall), and whose harness self-evolution loop diagnoses failure traces, proposes executable patches, and recombines them via a semantic "gene bank" of elites.

The problem

As agents move to long-horizon, cross-domain work, hand-designing harnesses stops scaling, and a single tightly-coupled harness doesn't generalize across domains. The paper shifts the question from "engineer a stronger harness for one domain" to "autonomously construct specialized harnesses, improve them through experience, and orchestrate them across domains" — treating each model–harness pair as a composable unit of intelligence in an "All-Domain Collaboration Network."

How it works

Two big subsystems. (A) Host-mediated collaboration. The Host Agent decomposes each goal into a DAG of worker calls (working backward from the deliverable: each node needs an identifiable output and an executor able to produce it), with node specs (prompt template, dependencies, input bindings to upstream outputs/files, optional stateful-agent instance handles). Orchestration guidance is disclosed in stages to save context (short summary every turn, full guide loaded on demand, validation errors returned with guide pointers), and graphs pass five admission checks (format, graph structure/acyclicity, backend capability, agent status, environment/budget/approval) before dispatch. (B) Diagnosis-driven harness self-evolution (§4). A harness is a fixed modular tuple h = (id_h, Mem_h, Plan_h, Cap_h, Act_h; θ_h) — Memory, Planning, Capability, Action strategies around a frozen task model. An Evolver Agent converts the parent's failure logs into testable intervention hypotheses (symptom → trace events → editable location → expected behavior change); proposals carry an executable patch, a semantic descriptor, and a declared activation predicate β that must provably fire in the trace. Candidates pass a gated screening: (1) valid protocol log, (2) activation gate (the intervention ran at least once), (3) paired-gain test — per-task score differences vs the parent with a t-like statistic t_pair ≥ 1.96 (λ_screen, no calibrated p-value claimed). Survivors are evaluated on all training tasks and admitted to the Harness Gene Bank: a quality-diversity archive keyed by (edit category ∈ {prompt, knowledge, runtime, config} × diagnosed failure label), one elite per cell, parent selection by best training utility, and recombination of donor-lineage changes with the parent (overlapping edits resolved before materialization). The bank stores even sub-best candidates, so complementary mechanisms survive; the theory section (§2) derives sufficient conditions for composition to expand reliable task coverage under a shared resource budget. Memory (§5) and Skill Forge (§6, curated skill catalog) persist experience across tasks.

Key results

Orchestration benchmark (same backbones): Qwen3.8-27B Node F1 0.923 vs 0.776 strongest baseline, POA 0.950, Exact Match 0.711 vs 0.607; DeepSeek-V4-Flash Node F1 0.963 vs 0.854, Edge F1 0.897 vs 0.813, Exact Match 0.867 vs 0.762. Raven-Research on DeepResearch Mixed: +6.6/+3.3/+7.6 pp over the strongest baseline across three backbones (on DeepSeek-V4-Flash, BrowseComp 69.3% vs 62.4%, Humanity's Last Exam 60.0% vs 43.3%). Raven-Code: SWE-Refactor +9.5 pts (DeepSeek-V4-Flash) / +3.0 pts (GPT-5.6 Luna) over leaderboard; SWE-bench Pro 15 more of 731 solved than Claude Code with the same Qwen3.8-27B; SWE-bench Verified +0.6 pts (3/500) on DeepSeek-V4-Flash and +1.2 pts (6/500) on Claude Opus 4.8. Raven-Design on ArtifactsBench: small gains (+1.4 pp dashboard, +0.6 pp SVG). Raven-Oncall (AI4S internal): 82.35% success at $5.10/case vs 64.71% at $13.60 baseline (+17.6 pp, 62.5% lower cost). Harness self-evolution (§7.2, summarizing the published HarnessBank [39] experiments): held-out Pass@1 with frozen Qwen3.6-27B improved on all seven benchmarks — BrowseComp+ 41.3% → 56.7% (+15.4 pp), AppWorld 16.9% → 30.8% (+13.9), LiveCodeBench 58.1% → 71.8% (+13.7), with six of seven passing the paired-gain criterion (SWE-bench Verified improved but its 26-task split did not pass).

How it relates to adaptive decomposition

Raven decomposes in two ways, but neither is agent-discovered harness decomposition. At task level (§3), the Host Agent genuinely discovers a decomposition per request (backward-chaining from the deliverable into a subtask DAG, dependency-aware dispatch, integration of results) — this is agentic decomposition of the problem, but the executor roster (Research/Code/Design/Oncall) is a fixed human-designed set, matched by capability tags rather than evolved. At harness level (§4), the module structure is fixed by design (Mem/Plan/Cap/Act, edit categories {prompt, knowledge, runtime, config}), and evolution is a sequential single-parent lineage: one parent, J proposals, N_keep confirmations per round — components do not get independent search budgets, do not improve in parallel, and there are no split-failing-further / fuse-working-ones / revert-to-monolithic operators. The gene bank is the closest cousin to fusion: donor lineages recombine with the parent, and sub-best elites persist across cells — but recombination is patch-level and curated by the Evolver, not an agent discovering where to split. So: evolvable mechanisms inside a fixed decomposition, not a discovered decomposition. Closest point of contact with adaptive decomposition's revert logic is the screening gate rejecting candidates whose paired gain is not positive and significant — failure to improve is handled by rejection, never by structural splitting.

Limits and open questions

The theory assumes clean, fixed task contracts and stable evaluation environments; the paper itself notes that "occupied-cell utility and best available utility cannot decrease [in-archive], but neither property guarantees improvement on unseen tasks," and cites HarnessDev evidence that evolved-harness gains are unstable, partially transferable, and model-dependent. The §7.2 self-evolution results are summarized from the external HarnessBank paper [39], not run by the Raven team on their own harness. Cost is unpenalized in the evolution utility (token/latency measured separately), and the activation gate proves an intervention ran, not that it caused the gain. Open probe: the host's per-request DAG decomposition is the most agent-driven structural choice in the paper — could that decomposer be pointed at the harness itself (discovering Mem/Plan/Cap/Act boundaries per domain instead of taking them as fixed), which would turn Raven's fixed module taxonomy into exactly the discovered decomposition adaptive decomposition demands?
