Harness Tokenomics: A Router for the Enterprise Agentic Control Plane

Day 35 · Nov 03, 2026

Harness Tokenomics: A Router for the Enterprise Agentic Control Plane

Ted Kwartler, Alan Aqrawi, Arian Abbasi · published 2026-09-24 · arXiv:2609.28919

background

One line

Builds a cache-aware model router for enterprise AI coding-agent harnesses that sends each session, side task, and subagent to the cheapest capable model without forcing a running conversation to rebuild its prompt cache — recovering 13–21% of model spend.

The problem

Enterprises are rolling out vendor-bundled coding-agent harnesses (Claude Code, Codex, etc.) to tens of thousands of employees, but the harness decides which model answers, what it reads, how the prompt cache is used, and which subagents run — so it picks the rate on the price sheet and sets the volume bought at it, leaving enterprises with an unauditable bill and four risks: price coupling to one vendor, uninspectable closed code, non-portable governance, and novices getting half the results for the same spend. Chat-style per-request routers fail inside a harness because one user turn is many API requests over a prompt cache that belongs to a single model — moving a turn to another model pays to rebuild the cache.

How it works

The router has eight specified components (the decision engine — components 2–6 and 8 plus the override rule of 7 — is prototyped; the live gateway and user-facing routing view are specified but not built). A classifier (Jev, ~$0.04/M input tokens, ~250 ms median latency) labels every prompt against a bring-your-own taxonomy of six typed questions: action (13 options), domain (12), complexity (trivial/routine/complex/expert), context (none/artifact/history/external), stakes-high (yes/no), and names-a-model (yes/no) — returning calibrated per-option probabilities, not a single label, so the policy can compute P(tier suffices) and P(turn is history-independent) and hold the turn when either is below 0.80. Routing happens only at cache-safe points: model choice at session start, a detached request, a "ledger side lane" (small task runs on a cheaper model seeded from a project ledger, followed by one empty request to refresh the home cache), and subagent launches — never mid-turn. A payback rule tells when a mid-task switch earns back its cache writes (e.g., Opus 5→Sonnet 5 pays after 27 requests with return, 8 without; Fable 5.1→Sonnet 5 after 291/46). The paper also derives a crossover: because Fable 5.1's cache-read price is $0.25/M vs Opus 5's $0.50/M, the top model costs less on long tool-heavy sessions above 71k context tokens (18 tool steps/turn). Corrections (over a third of the bill) are never downgraded (rule R10), per-user productivity metrics are deliberately excluded from the design (EU AI Act risk), and counterfactual accounting reports cost vs. pinning, aggregated by unit, never by person.

Key results

  • Emulated 10,000-seat enterprise (46 authored scenarios/109 turns × 200 Monte Carlo variants, behavior from ~10,000 real Claude Code sessions): as-is spend $2.03M/month ($24.4M/year, $41/engineer/day); routed spend $1.76M with today's labels and $1.61M with perfect labels → 13.4%–20.8% saved, $3.3M–$5.1M/year.
  • Crossover confirmed by repricing real sessions: 51% (TraceLab) / 80% (SWE-chat) of sessions costing ≥$100 on Opus 5 are cheaper on Fable 5.1; three-quarters of the total saving comes from the crossover ($198k/month of the $271k/month net saving).
  • Classifier accuracy on the corpus: action 74%, domain 80%, complexity 63%, history-dependence 82%; 12.5% of moved turns were false downgrades (redone as correction chains), 42% of routable turns held for uncertainty — holds cost only money, misroutes cost quality.
  • Threshold 0.9 beats 0.8 slightly (13.7% saving) but 0.8 kept to avoid tuning on the test set; dropping to 0.5 lowers saving to 10% (misroutes eat the gains).
  • Sensitivities: 5-minute cache expiry and pauses matter as much as the classifier (saving 23% with no pauses, 8% for pause-heavy users; a 1-hour cache lifts saving to 15.5%); without a Fable 5.1 license saving falls to 3.1%.
  • Vendor lock-in priced: on real sessions, other vendors' strong models cost 0.12–0.80× Opus 5 (DeepSeek V4 Pro 0.12–0.14, GPT-5.6 Sol 0.80), though ceilings assume equal quality and token use.

How it relates to adaptive decomposition

Barely. The router does not decompose anything: the six-question taxonomy, the tier policy, the floors, and the execution modes (session-start, side lanes, subagent launch) are all human-authored and fixed; the "evolution" is a human tuning thresholds per function, not the agent discovering structure. There is no splitting of problems into subproblems, no independent search budgets, no parallel component improvement, no fusion, no revert-to-monolith logic. The closest cousin is rule R10's conservative "hold when unsure" stance and the correction-rate feedback the authors propose for future tuned models — but both are static safeguards, not self-modification. The one thread genuinely useful to adaptive decomposition is its cache economics: any harness self-improvement loop that forks side lanes or subagents pays cache-rebuild costs, and this paper gives the exact payback arithmetic for that.

Limits and open questions

Everything rests on an emulation, not a live deployment: the 46 scenarios/109 turns are author-written, their ground-truth tags come from the authors alone, and the taxonomy has no inter-rater agreement or ablations yet. The enforcement gateway and live user interface are specified but unbuilt — every result runs in the simulator, and "perfect labels" assume a step-function capability model (right tier always succeeds, below always fails), so 21% is a ceiling, not a target. Prices and cache rules move fast (all Anthropic list prices of 21 Sep 2026), and under a uniform 0.1× cache-read regime the crossover disappears and the saving drops to 6%. Open: does a learned per-function taxonomy transfer across enterprises; how much of the saving survives contract discounts; and whether correction chains — the costliest failure mode — could be routed on predicted, not observed, corrections.
