Harness Engineering for LLM-Driven GPU Kernel Generation

Day 12 · Oct 11, 2026

Harness Engineering for LLM-Driven GPU Kernel Generation

Yue Shui, Chenyu Ma, Hangfei Xu, Shengzhao Wen, Yanpeng Wang · published 2026-07-20 · arXiv:2607.17979

relevant

One line

A contest-engineered system (MLSys 2026 FlashInfer kernel contest on NVIDIA B200) that splits LLM kernel search into a hard measurement layer (evaluation harness) and a decision layer (profile-backed optimization controller driven by human-written skills), winning real speedups by making agent search auditable rather than autonomous.

The problem

LLMs can write GPU kernels, but the failure mode isn't usually the model's coding ability — it's the surrounding engineering loop: stale baselines, a single hand-picked input that doesn't represent the workload distribution, noisy promotion (a candidate "wins" on one lucky measurement), and losing track of which hypotheses already failed. For a contest where a candidate must package correctly, compile in the target container, stay numerically correct, and beat the baseline on all workload shapes, prompt-only trial-and-error doesn't cut it.

How it works

The paper's core architectural claim is a two-layer split:

1. Evaluation harness (measurement, no decisions). Packages candidates, compiles them in the target container (CUDA 13.2 / PyTorch 2.12 / Triton 3.6 on B200), runs correctness checks, and measures official-aligned latency. Acceptance is gated: a representative gate first compares a candidate against the same-round baseline on selected workloads; survivors get a full sweep across the entire workload distribution (one worker per workload, incremental JSON, retrying transient infra failures). A candidate is promoted only if the full distribution improves with no correctness regressions. Rejected probes, profiler reports, shape matrices, and promotion decisions are all archived — negative evidence is treated as trajectory memory that blocks re-exploration of failed tile-size/launch-bound/fusion hypotheses.

2. Optimization controller (decisions, fed by the harness). Converts NCU/Torch Profiler evidence into a "state signature" per round (dominant kernels, bottleneck class, resource limiter, occupancy, throughput, waves per SM), matches it against prior evidence, and selects one bounded optimization direction. A supervisor watches memory for stalls, cycles, regressions, plateaus, and diminishing returns, and carries blocked/recommended directions into the next round.

The controller's behavior is codified not as prompts but as human-authored skills (SKILL.md playbooks): a generic CUDA optimizer skill, a FlashInfer-B200 contest skill (reference-first reconnaissance, paired gates, latency-first promotion), and a unified controller skill (reference scan → shape regime discovery → paired gates → profile matrix → one-direction optimization → archive/promote). Agents (Codex/GPT-5.3-Codex, Claude Code/Opus 4.6, plus sub-agents for parallel debate and review) generate candidate kernels inside those constraints; sub-agent outputs are proposals, never authority — promotion stays centralized. One pragmatic mechanism is workload-grounded shape dispatch: regimes are derived from contest workload UUIDs/JSON axes and measured latency distributions, and a shape-specialized variant is integrated behind a cheap dispatch rule only when profiler evidence shows that regime has a distinct limiter.

They also ran a "Full-Agent" baseline using LoongFlow PES as the autonomous-search comparison — same protocol, same workloads.

Key results

Retained Agent-Assisted artifacts, mean-latency speedup vs supplied FlashInfer baselines (correctness-gated, averaged over all workloads per definition):

  • MoE FP8: 1.62× | DSA top-k: 18.05× | DSA attention: 29.68× | GDN decode: 1.12× | GDN prefill: 13.70×
  • Agent-Assisted kernels beat the Full-Agent artifacts on every definition; Full-Agent artifacts were 1.35–13.25× slower than Agent-Assisted under the same normalization, and two stayed below the baseline (MoE FP8 0.27×, GDN decode 0.83×).
  • Their stated takeaway: expert-provided optimization directions, high-quality references, and workload context "remain critical" — the paper's transferable claim is explicitly not that a model autonomously solves kernel optimization, but that profile-backed controller state + workload-grounded gates + artifact memory make LLM search auditable enough to improve real contest kernels.

How it relates to adaptive decomposition

There is a limited, fixed/human-designed decomposition: the workload is split into shape regimes (derived from workload JSON axes and latency evidence), each regime gets its own specialized route behind a dispatch rule — but regimes are only introduced when the human playbook says profiler evidence shows a distinct limiter. Nothing about this is discovered by the agent; the action set is fixed (propose a candidate family around one hypothesis per round), and the structural choice "split into shape-specialized components" is a hand-authored skill rule. There is no independent-search-budget-per-component, no splitting of failing components further, no agent-driven fusion (integration is "IntegrateOrDispatch" under a human gate), and no revert-to-monolith logic. The closest cousin is the trajectory-memory idea: rejected probes archived as negative evidence to prevent re-exploration — a constraint that accumulates over time, similar in spirit to certificates (see 2609.34069), but implemented as archived records humans read rather than enforced restrictions.

Limits and open questions

The paper is honest that this is an Agent-Assisted engineering workflow, not an autonomous system: humans designed the harness, curated references, made budget calls, steered plateaus (by switching model families, languages, or supplying references), and approved promotions — so it's unclear how much transfers to a fully autonomous loop. A practical limitation it flags: full-distribution evaluation on B200 is expensive, so the loop relies on representative gates + low-trial full sweeps, which can miss rare selector-boundary failures (Appendix E reports targeted high-trial replay catching one). Future work explicitly proposes moving controller state, memory, and model orchestration into the harness — i.e., the authors see the human-authored controller as scaffolding to eventually automate, not as the end state. What I'd probe: whether the skill playbooks' "one direction per round" rule is actually optimal vs. parallel multi-hypothesis search under a fixed budget, and whether the artifact archive ever gets distilled (does a later run inherit compressed knowledge, or just raw JSON logs?).
