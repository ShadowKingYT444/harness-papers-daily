Learning Meta-Skills for Agent Harness Design in Test-Time AI4AI

Day 48 · Nov 16, 2026

Learning Meta-Skills for Agent Harness Design in Test-Time AI4AI

Cheng Qian, Kunlun Zhu, Beibin Li, Zhenhailong Wang, Heng Ji · published 2026-09-29 · arXiv:2609.38143

relevant

One line

Splits test-time harness design into a Builder and a Target (both weights frozen): the Builder learns reusable "meta-skills" — when support is needed, what to provide, how the Target should use it — from the Target's execution feedback, then builds a fresh task-specific harness per test task from the frozen skill bank.

The problem

Agent performance depends on the environment, not just reasoning: a capable agent fails when its scaffolding is bad. Test-time AI4AI lets a Builder model construct harnesses for a Target model, but the Builder's experience is wasted unless distilled into reusable knowledge. The wrong unit of knowledge is the task skill (how to solve the task) — the Builder needs principles of support design (how to build the environment that lets the Target solve it), learned from its own harness outcomes rather than handed down as prompts.

How it works

A meta-skill s = (when, provide, use): when names observable conditions calling for support; provide specifies the capability/resource the environment should supply; use explains how the Target should employ it and which judgments stay its responsibility. Learning runs a construction–execution–reflection loop: the bank starts empty; per development task the Builder (GPT-5.6-Sol) constructs a harness from the neutral environment H0 plus its current bank; the Target executes, producing a public trace and benchmark score; the Builder reviews and makes at most one evidence-grounded keep/add/revise update per batch, citing supporting evidence. After two development passes the bank is frozen. At test time, the Builder constructs a fresh harness per test task using either the full bank or BM25 top-2 retrieved skills. The harness space spans seven component families: instructions, memory, context organization, composed tools, execution control, verification & recovery, and workspace preparation. The Target's execution budget is fixed and covers only Target execution, not Builder construction. Evaluated on Harness-Bench (106 tasks: 11 dev / 95 test) and NewtonBench (324 tasks: 32 dev / 292 test) with Targets Gemini-3.6-Flash, Qwen3.8Flash, and GPT-OSS-120B.

Key results

  • Full-bank meta-skills: 65.31% macro average, +8.95pp over a no-skill Builder and +12.02pp over delivering the same bank directly to the Target — the headline finding is that knowledge helps most when a Builder operationalizes it into tools/state/control before execution, not when it's handed to the solver as instructions.
  • Same-model self-evolution (same model as Builder and Target): +18.71pp average over no-skill construction — a model can improve its own future execution by learning to build better support for itself, weights frozen.
  • Gains concentrate where coordination is the bottleneck: NewtonBench +10.96pp average vs Harness-Bench +6.95pp.
  • Refinement is late and non-monotonic: on NewtonBench the first pass moves scores <1.1pp while the second adds +13.01 (Gemini) / +12.33 (Qwen); on Harness-Bench Qwen drops 4.06pp from its first-pass peak — revisions can overfit to recent evidence.
  • Transfer is shaky: a bank learned by Sol for Qwen gains +13.36pp with Sol on NewtonBench but −4.45pp when a different Builder (Gemini-Pro) implements it; confidence intervals include zero, though a bank transferred across both Builder and Target still gains +4.58/+5.48pp.
  • Component ablations (frozen harnesses, NewtonBench): removing the execution controller costs −13.36/−4.79/−1.03pp across Targets; memory+context effects are directionally positive but all CIs include zero.
  • Error analysis: NewtonBench no-valid-submission cases fall 394→254 (−35.5%), correct discoveries rise 439→535 (+21.9%).

How it relates to adaptive decomposition

This is harness self-improvement, but along a different axis: the Builder learns reusable support-design principles, while each harness is still constructed fresh per task as a monolithic, never-revised artifact — there is no persistent harness, no decomposition into independently-evolved components, no split/fuse, and no per-component search budgets. Meta-skills are declarative (when/provide/use) principles, not evolvable harness modules; the "evolution" happens in the Builder's external knowledge, not in the harness structure. Two ideas do transfer to the user's research: (1) the +12.02pp Builder-enactment gap shows knowledge is most useful when compiled into executable support rather than delivered as advice — an adaptive-decomposition agent could similarly benefit from compiling per-component lessons into persistent component structure rather than prompt-level guidance; (2) the non-monotonic refinement (Qwen's −4.06pp regression) is a concrete argument for the versioning/rollback side of his mechanism, since even principled revisions overfit.

Limits and open questions

One main Builder (GPT-5.6-Sol), two benchmarks, one adopted execution per task per condition — the authors flag this themselves. Transfer confidence intervals include zero, so "meta-skills transfer" is suggestive, not established. Construction cost sits outside the benchmark budgets, so the 8.95pp gain is gross of Builder compute. Because each test harness is built once and never improved, the paper says nothing about iterative harness evolution — it's one-shot construction guided by learned principles, not RSI in the loop sense. The BM25 retrieval mode underperforms the full bank in 5/6 settings, hinting the bank's value is in complementary procedures considered jointly, but no retrieval method that captures complementarity is offered.
