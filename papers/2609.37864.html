AgentBug-Smith: Automatically Reproducing Real-World Harness Bugs in Agentic Systems

AgentBug-Smith: Automatically Reproducing Real-World Harness Bugs in Agentic Systems

Yiming Cheng, Alfin Wijaya Rahardja, Mengshi Zhang, Zihao Chen, Zhenpeng Chen, Yiling Lou · published 2026-09-29 · arXiv:2609.37864

background

One line

Fully automated multi-agent pipeline that mines GitHub issues for real-world harness bugs, builds execution environments, and synthesizes failure-reproducing tests — used to construct Live-Harness-Bench (200 reproducible harness bugs) and distill repair skills that lift agents' harness-bug fix rate by 6.32%.

The problem

Harness implementation bugs (broken orchestration, tool integration, context management) are the dominant failure mode in agentic systems, and existing software agents repair them far worse than general software bugs (4.67% vs 40.67%). But there's almost no executable benchmark: AgentIssue-Bench has only 43 fixed bugs, built with 150 manual hours, and general-purpose reproduction tools (SWE-Factory, SWE-bench-Live) fail on harnesses because harnesses depend on external resources (LLM providers, tools, networks) and fail only under specific execution states.

How it works

Three agentic stages, no human in the loop:

1. Harness bug identification: dual-stream repo discovery (curated awesome-lists init + incremental GH Archive event streams), filtered by ≥50 stars and an LLM judge checking the repo implements an agentic system. Issues must form a one-to-one issue-PR pair with a merged functional patch; an LLM judge then keeps only issues whose patch touches harness components (orchestration, memory, tools, etc.).

2. Agent execution environment construction: rule-based scan of manifests/CI configs produces an initial Dockerfile from an official minimal image (one LLM call), then a tool-using agent iteratively refines it against build errors. Model-client calls are transparently rerouted to mock services via container-level env vars. A 20-test smoke sample (excluding assertion failures) validates executability.

3. Failure-reproducing test generation: an LLM writes a test that must fail on the buggy commit with the issue-described failure and pass on the patched commit. Only model-client/network boundaries may be mocked — the function under test must be exercised for real. If test-only refinement stalls, it optionally co-refines the test and Dockerfile jointly (Appendix F shows a case where only joint optimization works).

Key results

  • Identification: 95% repo-level and 92% issue-level accuracy (vs 0.35/0.46 for vanilla LLM), stable across 5 runs (Sset 0.92).
  • Reproduction on 225 harness bugs: up to 28.00% success (DeepSeek-v3.2), 10.67–27.56 pp over SWE-Factory and SWE-bench-Live across all three backbones (GPT-4.1-mini, Kimi-k2.5, DeepSeek-v3.2), at $0.56–$2.44 per issue. 75 bugs reproduced total, 45 of them reproducible by neither baseline; 98.67% manually validated as faithful. The ablation standout: baselines reproduce zero issues lacking in-patch tests; AgentBug-Smith reproduces 21–29 such issues per backbone.
  • Live-Harness-Bench: 200 executable harness bugs (median repo 83k LoC, median patch 102.5 lines; 31.5% in tool registries, 30.5% in context/memory), continuously extendable.
  • Downstream: mini-SWE-agent, OpenHands, AutoCodeRover correctly resolve at most 9.00% of harness bugs (vs 40.67% on SWE-Bench Verified). A distilled textual skill (SKILL.md) from 121 training bugs raises mini-SWE-agent's correct resolution from 1.27% to 7.59% (+6.32 pp) on 79 held-out bugs from disjoint repos.

How it relates to adaptive decomposition

Barely — this is evaluation infrastructure, not harness evolution. The decomposition of the harness (which components bugs belong to) is fixed and comes from prior work's taxonomy plus an LLM judge, not discovered by the agent. Nothing is split, fused, or budgeted here. The one real thread connecting it to adaptive decomposition: the distilled-repair-skill experiment shows accumulated real-world harness-failure knowledge measurably improves an agent's ability to fix harnesses — the same "accumulate reusable mechanism knowledge" argument PluginRSI makes for its plugin library, just applied to bug repair instead of optimization. A live, auto-growing corpus of failed harness states could plausibly feed a future adaptive-decomposition loop (e.g., as training signal for when a component should split), but this paper builds none of that.

Limits and open questions

Even at its best (DeepSeek-v3.2), only 28% of identified bugs get reproduced — 72% fail, and the failure analysis is in an appendix not covered here. The ≥50-star and "has tests" repo filters, plus the requirement of a merged PR with functional changes, mean the benchmark skews toward mature, well-maintained repos — the long tail of janky agent code (where the nastiest harness bugs live) is excluded. Mocking model providers to reroute to local test harnesses is the right isolation move, but it also means reproduced failures can only be as real as the mocks are faithful. The 92% issue-identification accuracy implies ~8% of the benchmark may be non-harness bugs (the contamination the paper flags in AgentIssue-Bench applies here too). And the repair-skill result, while positive, goes from 1.27% to 7.59% — still an order of magnitude below general-software repair, so the "improve agents" claim is directionally right but quantitatively thin.
