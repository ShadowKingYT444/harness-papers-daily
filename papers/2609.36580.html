SafeCoEvo: Co-Evolving Safety Harnesses and Guards for LLM Agents at Test-Time

Day 45 · Nov 13, 2026

SafeCoEvo: Co-Evolving Safety Harnesses and Guards for LLM Agents at Test-Time

Yu Cheng, Yongkang Hu, Shuaijie Ma, Zhihang Lin, Weicheng Meng, Jingyang Qiao, Jiuan Zhou, Yushuo Zhang, Yihang Chen, Weilin Luo, Kun Shao, Dong Li, Zhizhong Zhang, Yuan Xie, Zhaoxia Yin · published 2026-09-29 · arXiv:2609.36580

relevant

One line

Evolves an agent's external safety system during deployment on two timescales: a fast, explicit-knowledge safety harness updated after every task, and a slow, parametric Guard fine-tuned periodically with a PPO-style verdict-policy objective (GuardVPO = Guard Verdict Policy Optimization).

The problem

Existing safety-harness evolution methods (SHE, SafeEvolve, EvoSafeHarness) run repeated rollout–feedback–update cycles over a fixed, revisitable task distribution. That's not how deployment works: in the real world, tasks arrive one at a time and feedback only exists after each task completes — you never get to replay the same distribution. So safety mechanisms frozen at deployment time can't improve from runtime experience. SafeCoEvo formulates this as continual test-time safety adaptation: given a stream x1…xT, the system executing task xt may only use experience accumulated from tasks x1…x(t−1), and each new outcome (τt, ft) can only benefit future tasks.

How it works

The external safety system St = (Ht, Gt) sits around a fixed task-performing model M (DeepSeek-v4.1-Flash in the main experiments). After each task, the two components evolve from the shared deployment stream at different timescales:

1. S-Harness (fast, after every task): Ht+1 = UH(Ht, τt, ft). S-Harness maintains five evolvable explicit safety components — Safety Prompt (stable principles/decision constraints), Validated Memory (feedback-validated reusable experience), Safety Skills (abstracted safety-handling patterns), Permission Policy (authorization boundaries for high-risk actions), and Guard Policy (how Guard judgments get interpreted and enforced; note this is an explicit policy about the Guard, not a change to the Guard's weights). From each completed trajectory plus post-hoc safety/task feedback, it extracts reusable safety information and writes it into the corresponding components, with the update taking effect only on subsequent tasks. To avoid memorizing task-specific rules, it deliberately strips source-specific details (benchmark names, task IDs, exact samples) and abstracts them into generalizable knowledge.

2. Guard (slow, periodic): GuardVPO. The growing explicit knowledge base eventually gets redundant and costly to maintain, so the Guard — a dedicated risk-assessment model (AgentDoG1.5-Unified-Qwen3.5-4B by default) — is fine-tuned periodically on event-level safety experience: each Guard invocation records the runtime context, the candidate action, the Guard's safe/unsafe verdict, and the subsequent safety feedback, matching the learning signal to the Guard's actual decision granularity rather than whole-episode outcomes. GuardVPO treats the Guard's output as a binary decision policy and applies a clipped PPO-style objective with an asymmetric reward ({safe→safe: +0.5, safe→unsafe: −0.5, unsafe→safe: −1.5, unsafe→unsafe: +1.0}) — missing a truly unsafe event is punished most heavily, but over-conservative blocking is also punished so safety can't be "won" by just blocking everything. A KL penalty against the initial Guard as πref constrains drift during continual training. Updating a small dedicated Guard is deliberately cheaper than retraining the task-performing agent, which stays frozen throughout.

The dual-timescale pairing is the core structural claim: rapid explicit externalization for immediate benefit, slow parametric internalization for consolidation — a complementarity the ablations confirm (each component's gains stack; GuardVPO's contribution grows over time since it's activated only after the first 512 episodes).

Key results

Setup: 1,024-episode continual evolution stream mixing Agent-SafetyBench (404) and Agent Security Bench (620) with paired attack tools; episodes processed in fixed order, updates apply only to future episodes; then a frozen evaluation on a 300-episode held-out test set built from four unseen scenarios.

  • Continual stream (vs strongest evolution baseline SHE): UOR 14.01% vs 24.06% (−10.05%), TSR 76.08% vs 63.93% (+12.15%), SUCR 70.02% vs 54.35% (+15.67%). Gains are strongest under the Security setting (adversarial attack patterns), and crucially safety improves alongside task success, not by over-blocking — the asymmetric reward does its job.
  • Held-out test set (frozen system, no test-time updates): vs SHE, UOR 7.67% vs 29.19% (−21.52%), TSR 81.33% vs 54.36% (+26.97%), SUCR 78.33% vs 41.95% (+36.38%) — the accumulated experience genuinely generalizes to novel scenarios.
  • Ablations: S-Harness evolution alone (Guard frozen) already beats the fully static configuration by −10.45% UOR / +31.45% TSR; adding GuardVPO on the second-stage 512 episodes further cuts UOR by 7.81% and raises SUCR by 5.67%, showing the consolidation effect compounds over time.
  • Generalization: same pattern with Qwen3.7-Flash as the task model and SingGuard as the Guard backbone; the Guard's learned risk judgment transfers modestly to external benchmarks (R-Judge unsafe recall +1.06%, ATBench unsafe recall +2.76%, correct predictions 802→810/1000) with a small safe-specificity trade-off.

How it relates to adaptive decomposition

This is a safety paper, and I'd keep it in the right box: its "co-evolution" is between a fast explicit-knowledge harness and a slow parametric guard — not an agent discovering harness decomposition. Like PluginRSI, the decomposition here is fixed and human-designed: the five S-Harness components (prompt, memory, skills, permission policy, guard policy) are pre-atomized slots that get incrementally filled in, and nothing splits a failing component, fuses working ones, or re-decomposes the harness. Adaptive decomposition's core novelty — the agent itself deciding the decomposition — is absent.

Two things are genuinely worth carrying over, though. First, the test-time adaptation framing: existing harness optimizers (PluginRSI included) replay fixed task distributions, but adaptive decomposition deployed in the wild will face exactly SafeCoEvo's constraint — learning only from accumulated runtime experience, one pass, no replays. Second, the two-timescale split (fast externalize explicit knowledge, slow internalize into parameters) is an interesting structural idea for adaptive decomposition itself: an agent discovering decompositions post-deployment would face the same tension between reacting quickly to new failure modes and consolidating stable mechanisms, and SafeCoEvo's asymmetry (explicit-first, parametric-later) is a concrete template for resolving it. The Guard Policy component is also a neat parallel — a policy about how to use another component's judgments, i.e., meta-coordination living as an explicit evolvable slot.

Limits and open questions

The authors are upfront (Appendix G) that GuardVPO is just one instantiation — they don't claim the clipped PPO objective with their specific reward values is optimal, and experience sampling/selection is unexplored. The whole evaluation is text-driven tool-using agents; multimodal, computer-use, and long-horizon environments are listed as future work. One design detail worth probing: the held-out generalization (300 episodes from four unseen scenarios) is strong, but the evolution stream and test set still come from the same two benchmark families, so I'd want to see it on a truly different agent-risk domain before trusting the "generalizable" claim. The modest R-Judge/ATBench transfer (+8 correct predictions) with a safe-specificity drop suggests GuardVPO mostly sharpens sensitivity rather than learning new risk concepts — a real question is whether it would keep improving indefinitely or plateau (and whether the KL-to-initial-Guard penalty starts binding as the stream gets longer). Also, the S-Harness update relies on post-hoc official feedback ft from the benchmarks; in real deployment, that feedback is noisy, delayed, or absent — the paper assumes a clean feedback source and never tests robustness to it.
