Learning from Research: Toward Lifelong Agent Harness Evolution

Day 66 · Dec 04, 2026

Learning from Research: Toward Lifelong Agent Harness Evolution

Jingbo Yang, Kwei-Herng Lai, Xiaowen Wang, Yaar Harari, Evgeniy Gabrilovich, Shiyu Chang · published 2026-09-30 · arXiv:2609.40169

relevant

One line

A lifelong harness-evolution framework that turns research papers into executable harness mutations: topic-model the literature into orthogonal mechanism families per module, implement them with a coding agent, and select combinations via paired-bootstrap validation — raising Qwen3.5-27B AppWorld Challenge TGC from 49.6% to 63.6% and GPT-5.4-mini τ²-Bench Telecom pass1 from 72.7% to 81.9%.

The problem

Recent harness-evolution methods (DGM, Meta Harness, AHE) use a meta coding agent that proposes edits from execution traces and its own knowledge. The authors name three failure modes of this regime: ❶ limited exploration — broad edit permission still yields a narrow sequence of local edits (search plateaus around repeated local edits; Figure 1 shows an added verifier blocking tool calls it needed), ❷ limited design knowledge — proposals depend on the meta agent's backbone knowledge, which a failure trace can't supply, and ❸ delayed adaptation — trajectory-driven evolution only reacts after users have already hit the weakness. The research literature is an untapped source of fresh mechanisms, but nobody had made the literature→harness translation an explicit search process.

How it works

Problem formulation. A harness is H = Compose(m1, …, m5): five modules — tool interface, context management, skills, memories, agentic workflows — each with a defined interface, around a fixed backbone fθ. Three strictly disjoint sets: Devo (failure analysis, artifact construction), Dval (candidate evaluation, champion selection), Dtest (final reporting only). The objective is J(H) = E_x∼Ptar E_τ∼pθ(·|H,x)[R(x,τ)], optimized without touching θ or Dtest.

Research pool construction. An auditor attributes failed Devo trajectories to agent vs environment causes; a research model abstracts recurring agent failures into benchmark-agnostic capability gaps, generates capability + mechanism queries per module, and retrieves/dedupes papers into a pool Pj per module.

Topic modeling for orthogonal exploration (the core idea). Following the TopicGPT framework, the research model induces mechanism topics (generation), merges paraphrases/overlapping categories and drops vague ones (refinement), then assigns each paper an ordered topic list with supporting abstract excerpts, the primary label defining its selection cluster. Candidates are drawn round-robin across clusters, so a budget of Kj papers covers min(Kj, |Tj⁺|) distinct mechanism families. Topic orthogonality diversifies implementations within a module; module interfaces localize responsibilities so topics and modules compose at complementary levels.

From papers to executable mutations. For each selected paper, a research agent reads the full paper plus official code and writes a mutation blueprint (source mechanism, target module/interface, required state/artifacts, runtime ops, termination). The coding agent (Codex/GPT-5.4) implements mj^(p) and constructs Hj^(p) = H^(0)[j ← mj^(p)], keeping the other four modules fixed; lightweight health probes check importability, interface compatibility, artifact reloading, and valid action production, with a repair budget.

Crossover and selection. Predicted combination gain is additive: Δ̂(c) = (1/|Dval|) Σ_j Σ_i gj,cj(i), where cj = 0 retains the base module. Combinations are shortlisted within budget, then evaluated as complete harnesses for actual gain — the regression check accounts for module interactions and reward ceilings. The champion is replaced only if the lower endpoint Lα of the paired bootstrap gain interval is positive (statistical confirmation, not point estimates). One generation without a confirmed validation gain (s_stop = 1 in main experiments) or budget exhaustion ends the cycle.

Lifelong extension. Periodic literature refresh (retrospective windows: through Dec 2025, Jan–Apr 2026, May–Aug 2026) starts a new search cycle from the retained champion, screening topics against current mechanisms — new publications can trigger mutation rounds before corresponding failures accumulate in deployment.

Key results

  • Main table (3 runs each): AppWorld Normal Qwen3.5-27B 69.0→81.4 TGC (+12.4), SGC +20.2; Challenge 49.6→63.6 (+14.0), SGC +16.5. Mini: Normal +5.3, Challenge +9.5. Telecom: Mini pass1 72.7→81.9 (+9.2), pass4 +9.1. Meta Harness barely moved Qwen Challenge (+5.0) and regressed Mini (e.g., Telecom pass1 −6.2) under equal search-rollout budgets.
  • Closing model gaps with fixed weights: evolved Qwen reaches 81.4% TGC on Normal, matching Kimi-K2.6's 81.3% and closing ~74% of the gap to GPT-5.4 (16.7→4.3 points).
  • Generalization to unseen applications: Challenge requires Amazon/Gmail APIs absent from evolution; gains are larger on Challenge than Normal, and remain positive beyond the training API maximum of 12 (Qwen +9.5, Mini +7.2 TGC points on >12-API tasks).
  • Lifelong (3 windows, Qwen): TGC 69.00→73.41→79.76→81.55; Meta Harness flat at 71.03→70.44→69.64 (final advantages of 11.9 TGC / 15.5 SGC points).
  • Cumulative ablations: replacing topic-guided selection with relevance ranking, then module-wise mutation with joint editing, then research guidance (→ Meta Harness) — scores decline at every step; research guidance alone worth 1.4/2.3 TGC/SGC points (Qwen), 2.6/5.4 (Mini).
  • Crossover interactions: combinations beat their strongest constituent (Qwen +3.5/12.3, Mini +4.7/7.0 TGC/SGC); a weaker standalone skills candidate (73.7% vs 75.4%) formed a stronger combination — standalone scores don't identify the best composition.
  • Reliability: Qwen improves on 221/585 tasks vs 57 regressions; ~73% of gains come from intermittently-succeeding tasks; all-three-runs successes rise 205→333. Residual failures after evolution: invalid response formats 492→206 episodes, but constraint violations (91→89) and incomplete retrieval (77→70) barely budge — requirement tracking and evidence coverage persist.

How it relates to adaptive decomposition

Direct contrast, and it's an important one: ScholarEvolve's decomposition is fixed and human-designed — the five modules come from the modular harness view in Team et al. (2026), and no step ever questions the boundaries. It never discovers a decomposition, never splits a failing module into finer subproblems, never fuses modules, and has no revert-toward-monolith move. Don't be misled by "Task Decomposition" appearing among the workflow module's mutation topics: that is the agent decomposing tasks at runtime, not the system decomposing itself — a different object entirely. This paper is therefore fixed-decomposition harness evolution, closer in spirit to Meta Harness/PluginRSI than to adaptive decomposition.

Two reusable tools, though. First, the round-robin topic coverage is a concrete, tested mechanism for distributing search budget across orthogonal families of approaches — exactly the scheduling problem adaptive decomposition faces when a split produces several subproblems. The analogy: where ScholarEvolve spreads Kj paper budgets across mechanism topics to force exploration breadth, an adaptive-decomposition system could spread search budget across discovered subproblems, with merging of overlapping topics as the analog of fusing redundant subproblems. Second, the crossover design — measure candidates per-module, rank combinations by additive predicted gain, then joint-evaluate the shortlist — is a directly reusable fuse-evaluation protocol, and their result that a weaker standalone candidate produced a stronger combination is empirical evidence the user's fuse step cannot trust component-level scores alone.

On the trigger question. Adaptive decomposition needs a policy for when to split or re-evolve; ScholarEvolve's answer is an external one — new literature windows restart the search from the champion. That's an implementable trigger for "keep evolving," though it says nothing about the revert move: champion retention here is strictly forward; there is no mechanism for backing toward a monolithic state when components disagree.

Related-work positioning: this is a neighboring branch — fixed-decomposition, literature-driven evolution — not an implementation or approximation of adaptive decomposition's core. Its distinctive contribution relative to the user's mechanism is a source of novel mutation content (papers), whereas adaptive decomposition's novelty is structural (the decomposition itself is discovered). A hybrid is easy to sketch: literature-derived mechanisms as split/fuse proposals inside a self-discovered decomposition.

Limits and open questions

The five-module decomposition is taken as given from prior work and never questioned — module boundaries are never learned, split, or merged, so the paper's biggest architectural assumption is invisible to its own search. There is no in-loop anti-overfitting or anti-bloat gate beyond validation statistics: the gate is disjoint Devo/Dval/Dtest splits, paired-bootstrap LCB retention, and s_stop convergence — nothing penalizes harness code size, complexity, or prompt growth (I read §3.3 fully; no complexity regularizer appears). Topic "orthogonality" is LLM-judged by construction (TopicGPT prompted induction/refinement), not independently measured — topics could be semantic paraphrases the judge failed to merge. Budgets are small (4 candidates/module on AppWorld, 3 on Telecom), and the lifelong demonstration is three retrospective generations on one benchmark (windows reconstructed from the current arXiv index, not a live deployment). No search-compute cost is reported. Two backbone names — "Qwen3.5-27B" and "GPT-5.4-mini" — don't match publicly released models as of my knowledge cutoff, so treat those results as the paper's own reported numbers rather than independently reproducible. Residual failure families (requirement tracking, evidence coverage) were found by the same literature-driven search that found everything else, suggesting either no published mechanism targets them or the search missed it. I read the full main body (abstract through conclusion) and Appendix A (implementation details, lifelong protocol, analysis protocol, failure taxonomy); I skimmed appendices B–D contents and did not verify the selected-code listings in Appendix D.
