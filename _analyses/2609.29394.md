## One line
Separates evolution-time coding from runtime decisions: before deployment it evolves typed Policy APIs (pickplace, insert, stack, push, articulate, actuate_control), a ReAct agent harness, and experience memory through a two-phase curriculum-then-autonomous evolution loop; at runtime a frozen-API ReAct agent just steers exposed arguments.

## The problem
Code-as-Policies methods generate and repair robot programs *at runtime* — one coding iteration takes 6.8–23.8 s, a multi-turn trial 60.8–113.6 s, and generated code often hard-codes task-specific coordinates and recovery decisions that don't transfer. Prior self-improving CaP systems (RATS, ASPIRE) keep runtime code generation and have play-time or fixed-distance objectives that don't transfer to downstream tasks. The core question: how should a system divide evolution-time code from runtime decisions so it keeps evolving, transfers across tasks, and still adapts to the current scene?

## How it works
**Evolution (offline):** Three components evolve together — typed Policy APIs (each owning one bounded physical mechanism, e.g. `insert` with revisable args like place_margin, grasp, yaw_deg), the ReAct agent harness, and experience-based long-term memory. Phase 1 is **capability curriculum learning** (builds reliable execution, recovery, skill breadth, orchestration). Phase 2 is **autonomous self-evolution**: failures are selected, a visual critic + coding agent proposes changes (code diffs like place_margin 0.05→0.03, grasp None→"pinch"), and **paired rollouts** (champion vs. candidate on the same task cohort) decide promotion — a candidate promotes only when paired gains exceed paired regressions (compile → test → regression gate → WIN/PROMOTE or LOSE/ARCHIVE). **Execution (runtime):** source code is frozen; the ReAct agent uses visual observations and perceptual feedback to select APIs, revise arguments, retry, and decide stopping — task decomposition, API selection, and recovery are owned by the runtime agent, while each Policy API owns one bounded mechanism.

## Key results
- LIBERO-90 in-domain: 54.4% success; zero-shot LIBERO-PRO transfer: 45.0%; LIBERO-Long: 46.0% vs at most 4.0% for CaP baselines.
- On LIBERO-PRO: 2.5× the success rate of the strongest CaP baseline with 1.9× speedup in median policy time.
- Distilling ReAct decision traces (GPT-5.6 → Qwen3-VL-8B-Instruct via rejection-sampled fine-tuning): 13.2× per-decision inference speedup; repeated physical calls drop from 16 to 4.

## How it relates to adaptive decomposition
RACaP has the *shape* of adaptive decomposition's component layer — a fixed set of typed mechanisms (Policy APIs) each owning one bounded behavior, evolved and selected independently with paired-rollout evidence, promoted or archived like a population. But the decomposition itself is human-designed and frozen: the six APIs are typed by the authors, and the agent never splits a failing API into finer mechanisms, fuses working ones, or gives components independent search budgets with a global fallback. Evolution mutates implementations, not structure. The most transferable idea: the champion-vs-candidate paired-rollout promotion gate with explicit regression checking is exactly the kind of rigorous accept/reject criterion an adaptive-decomposition system would want for component-level changes.

## Limits and open questions
The fixed typed API set is the ceiling: if a task needs a mechanism outside the six, the system can't invent it. The evolution stage is offline and presumably expensive (no budget numbers given). Distillation is one-way (teacher → student) with no feedback loop. Open: what happens when the visual critic misjudges a physical failure — does the regression gate catch it, or do bad mechanisms get promoted on biased cohorts? And could the *API boundary design* itself (what counts as one "mechanism") become evolvable?
