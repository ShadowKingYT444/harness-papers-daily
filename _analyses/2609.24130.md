## What is actually new

Self-Healing Harness treats self-modification as **admission control** rather than trusting the agent's proposed rule.

The agent can propose a persistent behavioral rule after a stall or regression. That rule first receives temporary authority. It becomes permanent only if replay shows that it fixes target failures **and** stays within a regression margin on protected cases. The full active rule set is then checked again because individually safe rules can conflict.

This is less a search algorithm than a safety architecture for persistent self-edits.

## Mental model

Suppose an agent fails because it repeatedly forgets to verify a generated file. It proposes: "Before finishing, always run the verifier."

That sounds useful, but making it permanent immediately is risky. Maybe some tasks have no verifier. Maybe the extra call causes a timeout. Maybe another existing rule already triggers verification and the pair creates a loop.

The paper therefore separates:
- **proposal**: write a repair rule;
- **local evidence**: replay the failure;
- **protected evidence**: replay cases that already work;
- **corpus evidence**: check the whole active rule set together.

The main insight is simple: **a local win is not a global win.**

## Key objects and state

- **Failure/stall detector:** decides when a repair may be needed.
- **Candidate rule:** a proposed persistent instruction.
- **Temporary authority:** the rule can execute during validation without being committed.
- **Matched failure replays:** cases that should improve.
- **Protected success cases:** behavior that must not regress.
- **Admission gate:** quantitative rule for promotion.
- **Active rule corpus:** all committed rules.
- **Retired rule set:** failed or superseded rules.
- **Corpus guard:** validates interactions among active rules.

## Admission loop

~~~mermaid
flowchart TD
    A["Runtime evaluator detects stall / regression"] --> B["Collect trace evidence"]
    B --> C["Agent proposes candidate rule"]
    C --> D["Give rule temporary authority"]
    D --> E["Replay matched failure cases"]
    E --> F["Replay protected success cases"]
    F --> G{"Target gain clears threshold AND regression stays below limit?"}
    G -- "No" --> H["Retire candidate"]
    G -- "Yes" --> I["Activate candidate"]
    I --> J["Evaluate complete active-rule corpus"]
    J --> K{"Rules interfere?"}
    K -- "Yes" --> L["Rollback / retire conflicting rule"]
    K -- "No" --> A
~~~

## Step-by-step implementation

1. Define the runtime events that trigger self-repair. Avoid proposing edits after every single noisy failure.
2. Save the triggering trace and the exact failure criterion.
3. Ask the agent for one candidate rule plus a prediction: what behavior should change?
4. Add the rule to a temporary layer with lower persistence than accepted rules.
5. Replay several matched failure cases.
6. Replay several protected cases sampled from prior successes.
7. Measure target improvement and worst protected regression.
8. Promote only if the target improvement clears a minimum gain and protected degradation stays inside the allowed margin.
9. After promotion, run a corpus-level test because two rules can conflict.
10. Keep the previous rule corpus as a rollback checkpoint.
11. Log every rejected rule. Re-proposing the same failed rule should be detectable.

## Concrete control settings

The paper gives explicit guard values in its implementation. Representative settings include:

- a recent trace window before triggering repair;
- a small matched replay set;
- separate improvement and regression margins;
- a cap on simultaneously active rules;
- bounded validation time;
- promotion only after a measurable gain rather than subjective approval.

The exact values are task-specific. The important design is that **promotion is a testable contract**, not "the agent thinks this rule is good."

## Results that matter

About **46% of proposed rules are rejected** in the reported study.

That negative result is actually the most important evidence. Many rejected rules appear to repair the failure that caused them but damage a protected case. If the system had accepted every plausible self-edit, it would have accumulated regressions.

The study therefore directly demonstrates a local/global conflict in persistent agent adaptation.

## What the results do not prove

The protected replay set is small. Passing it does not prove the rule is globally safe.

The method also does not solve root-cause attribution. It assumes the system can propose a plausible rule from a failure trace. The gate only tests whether the rule's observed effect is acceptable.

## Failure modes and limits

- Small protected sets miss rare regressions.
- Replays add cost and latency.
- Two rules can be individually safe but jointly harmful.
- Rules can become obsolete after other harness changes.
- A rule may improve benchmark behavior through a brittle shortcut.
- If the evaluator itself is editable, the agent could weaken the admission test. The gate must live outside the mutable surface.

## Implementation checklist

Keep separate stores for:
- candidate rules;
- active rules;
- retired rules;
- protected cases;
- trigger traces;
- replay results.

Every rule needs:
- parent rule-corpus version;
- source trigger;
- predicted behavioral effect;
- target replay scores;
- protected replay scores;
- activation count;
- promotion/retirement reason.

## What RHEvolution should take from it

RHEvolution needs exactly this two-level validation pattern.

A component edit should pass:
1. a **local owner gate** on the failure class that motivated the edit;
2. a **global harness gate** on protected and OOD cases.

A split or fuse changes more than a normal rule, so it should face an even stronger gate. Keep the evaluator, hidden tests, budget accounting, and rollback mechanism outside editable owners.

When local and global scores disagree, do not simply reject the edit. That disagreement is also evidence that the current component boundary may be wrong.
