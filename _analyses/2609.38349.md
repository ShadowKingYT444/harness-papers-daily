## What is actually new

MILO evolves not only harness candidates but **the search process that produces them**.

It maintains several isolated search islands. Each island has its own harness lineage and memory of both accepted and rejected edits. When an island stalls, a higher-level orchestrator diagnoses the search problem and can:
- assign a different mutator;
- graft useful material across lineages;
- split a distinct niche into a new island;
- change the task curriculum.

The novelty is a hierarchical outer loop: **evolve harnesses inside islands; adapt the evolutionary strategy across islands**.

## Mental model

One monolithic search can fail in several ways:
- the proposer repeats the same edits;
- a promising minority strategy gets killed by the global score;
- two lineages have complementary mechanisms;
- the current tasks no longer reveal useful gradients.

MILO tries to identify *which kind of search failure* occurred before changing strategy.

This is different from simply running many random branches. The orchestrator treats search health as an object to diagnose.

## Key objects and state

- **Island:** independent population/lineage of harness candidates.
- **Island frontier:** strong candidates under score/cost objectives.
- **Lineage memory:** accepted and rejected mutation history.
- **Mutator:** agent/policy that proposes harness changes.
- **Pareto admission:** keeps candidates that trade accuracy, tokens, latency differently.
- **Stall detector:** finds low progress.
- **Orchestrator diagnosis:** classifies search failure.
- **Graft:** combine useful material from lineages.
- **Speciation:** preserve a distinct niche as its own island.
- **Curriculum revision:** change tasks used for search.

## Optimization loop

~~~mermaid
flowchart TD
    A["Several harness islands"] --> B["Choose parent inside each island"]
    B --> C["Island mutator proposes whole-harness edit"]
    C --> D["Evaluate accuracy + cost + latency"]
    D --> E["Pareto admission"]
    E --> F["Update accepted AND rejected lineage memory"]
    F --> G{"Island progress stalls?"}
    G -- "No" --> B
    G -- "Yes" --> H["Orchestrator diagnoses search problem"]
    H --> I{"Intervention"}
    I -->|Weak mutator| J["Reassign mutator"]
    I -->|Complementary lineages| K["Graft"]
    I -->|Suppressed niche| L["Speciate new island"]
    I -->|Poor task signal| M["Revise curriculum"]
    J --> B
    K --> B
    L --> A
    M --> B
~~~

## Step-by-step implementation

1. Create several independent candidate islands from a common or diverse seed.
2. Give each island its own lineage memory and evaluation records.
3. Mutate whole harnesses inside an island.
4. Score candidates on task success plus resource objectives.
5. Keep a Pareto frontier rather than one scalar winner.
6. Save rejected changes and their failure reasons.
7. Track progress over time for each island.
8. When progress stalls, classify the likely cause.
9. If the mutator seems weak, change/reassign it.
10. If two lineages contain complementary gains, attempt a graft and revalidate.
11. If a minority lineage has distinct behavior but loses global competition, promote it to a new island.
12. If the active task set no longer distinguishes candidates, revise the curriculum toward high-regret tasks.
13. Continue until the time/evaluation budget ends.
14. Evaluate final candidates on held-out tasks.

## Experimental setup and headline results

The paper uses matched long search budgets on:
- Terminal-Bench 2.1;
- PaperBench-style code development;
- DeepSWE.

Reported improvements over the initial harness with an Opus-class setup are approximately:
- **+12.0 points** on Terminal-Bench 2.1;
- **+28.3 points** on PaperBench;
- **+10.3 points** on DeepSWE.

The best prior search comparison in those settings is reported around:
- +4.5;
- +18.3;
- ~0 points, respectively.

One Terminal-Bench result reaches about **86.1 ± 2.0**, above the referenced official top result around **83.8 ± 2.3**, while using fewer tokens than the seed.

These are system-level results: multiple search mechanisms act together.

## Most important ablation lesson

The orchestrator provides the largest improvement in the reported search-mechanism ablation.

That means the gain is not only from "run several islands." Detecting when the current search regime is exhausted and changing the regime matters.

This is directly relevant to RHEvolution's question of when to split: a structural operator should be triggered by a diagnosed search failure, not on a fixed schedule.

## Failure modes and limits

- Stall types and allowed interventions are human-designed.
- Maintaining many islands can waste budget.
- Whole-harness islands still have coarse internal credit.
- Grafts can create integration failures.
- Pareto fronts can grow large.
- Orchestrator decisions are themselves model judgments and can be wrong.

## Implementation checklist

Per island store:
- candidate lineage;
- full task-score vector;
- cost/latency;
- accepted/rejected edits;
- mutator ID;
- recent progress slope;
- unique solved-task set.

Orchestrator outputs should be typed, e.g.:
- REASSIGN_MUTATOR;
- GRAFT(A,B);
- SPECIATE(candidate);
- CHANGE_CURRICULUM(task_set);
- NO_ACTION.

## What RHEvolution should take from it

MILO supplies a **meta-controller pattern**.

RHEvolution can make islands correspond to discovered harness owners/subgraphs rather than full harnesses. Then the orchestrator can ask:
- is this component search stalled?
- should it split?
- should two components fuse?
- should budget move to another owner?
- should two component lineages cross over?

This turns adaptive decomposition into one intervention class inside a broader search-health controller.
