## What is actually new

EvoGen-Harness focuses directly on **failure attribution before mutation**.

It repeats stochastic image-generation requests, compares trajectories, estimates which harness responsibility is causing a persistent failure, and uses that attribution as a search prior. After a repair, it runs attribution again because the bottleneck can move.

It also includes a **No-Patch** decision: sometimes a bad sample is random or model-limited and the harness should not change.

## Mental model

A generated image misses one object. Was the cause:
- prompt construction;
- routing/model choice;
- workflow control;
- tool use;
- pure sampling randomness?

One sample cannot answer that.

Repeat the same request. If several runs fail in the same way, compare where their trajectories differ from successful runs. The system assigns probability to several harness responsibilities, then edits the highest-value target.

After the patch, the next dominant failure may be different. The system therefore re-localizes instead of permanently blaming one module.

## Key objects and state

- **Repeated trajectories for same request**
- **Responsibility set:** prompt, routing, workflow, tools, etc.
- **Attribution vector**
- **No-Patch probability**
- **Search prior:** directs mutation toward likely cause.
- **Matched evaluation:** parent and candidate on same requests.
- **Held-out validation**
- **Progressive re-localization**
- **Regression monitor**

## Optimization loop

~~~mermaid
flowchart TD
    A["Repeat same generation request"] --> B["Compare stochastic trajectories + outputs"]
    B --> C["Estimate failure responsibility distribution"]
    C --> D{"No-Patch likely?"}
    D -- "Yes" --> E["Keep harness / collect more evidence"]
    D -- "No" --> F["Select likely responsibility"]
    F --> G["Generate targeted update"]
    G --> H["Matched parent-vs-candidate evaluation"]
    H --> I["Held-out / regression validation"]
    I --> J{"Accept?"}
    J -- "No" --> E
    J -- "Yes" --> K["Promote candidate"]
    K --> L["Re-run attribution on remaining failures"]
    L --> A
~~~

## Step-by-step implementation

1. Define a small responsibility map tied to actual source regions.
2. For each optimization request, run multiple stochastic executions.
3. Record prompts, routing, tools, intermediate states, and final outputs.
4. Compare successful and failed trajectories.
5. Produce a probability/confidence over possible responsibilities.
6. Include a No-Patch outcome.
7. Use attribution to focus the optimizer rather than giving it the full repo.
8. Run parent and candidate on matched prompts/seeds where possible.
9. Validate on held-out requests.
10. Measure regressions separately from target improvement.
11. After acceptance, run attribution again; do not assume the same module remains the bottleneck.

## Experimental setup

The method is tested on several text-to-image benchmarks with fixed generator models.

Reported evaluation separates:
- final generation quality;
- attribution F1;
- held-out gain;
- regression rate.

That is useful because a harness optimizer can score higher even when its stated attribution is wrong.

## Results that matter

One reported full setting reaches roughly:
- **0.7089** on GenEval2;
- attribution F1 **0.906**;
- held-out gain **+0.140**;
- regression rate **1.9%**.

The paper reports strong gains on complex composition and WISE-style evaluations as well.

## Ablation table: what actually causes the gain

| Variant | GenEval2 | Attr. F1 | Held-out gain | Regression |
|---|---:|---:|---:|---:|
| **Full** | **0.7089** | **0.906** | **+0.140** | **1.9%** |
| No trajectory aggregation | 0.6580 | 0.816 | +0.111 | 5.1% |
| No attribution guidance | 0.6070 | 0.906 | +0.086 | 6.8% |
| No matched evaluation | 0.6390 | 0.906 | +0.101 | 7.6% |
| No progressive re-localization | 0.6250 | 0.906 | +0.091 | 4.4% |
| No No-Patch | 0.6420 | 0.753 | +0.103 | 10.7% |
| No safe validation | 0.6780 | 0.906 | +0.119 | 13.9% |

This is one of the most informative ablation tables in the reading set.

## What the ablations mean

**Trajectory aggregation:** repeated executions improve attribution and reduce regression.

**Attribution guidance:** even with the same attribution model, not using it to focus search substantially hurts final score.

**Matched evaluation:** noisy unmatched comparison promotes worse changes.

**Progressive re-localization:** after one fix, the next bottleneck moves.

**No-Patch:** forcing a patch is dangerous. Regression jumps sharply when the system cannot abstain.

**Safe validation:** gives the largest regression-control effect.

## Failure modes and limits

- Responsibility categories are still fixed.
- Attribution can be confidently wrong.
- Image-generation failures may be easier to repeat than long-horizon agent failures.
- Semantic image scoring introduces evaluator noise.
- No-Patch can become over-conservative.
- A failure can be caused by interaction across responsibilities.

## Implementation checklist

Your attribution artifact should contain:
- task/run IDs;
- candidate owners;
- probabilities/confidence;
- supporting trace spans;
- alternative hypotheses;
- No-Patch score.

Measure attribution quality separately from optimization score wherever human/programmatic labels are possible.

## What RHEvolution should take from it

This paper gives direct machinery for **split decisions**.

If one current owner repeatedly receives:
- high-confidence but mutually different failure mechanisms;
- source evidence in separable regions;
- poor local attribution purity;

then split it.

If two owners are repeatedly co-attributed and edits to one fail without the other, fuse them.

Also keep No-Structural-Change as a first-class action. Recursion should be earned by evidence, not triggered every time progress slows.
