## What is actually new

ModularRSI is one of the strongest direct precedents for RHEvolution.

It shows that **decomposing harness evolution into functional modules can work better than evolving the whole harness at once**. It uses repeated runs of the same task, compares successful and failed trajectories, maps recurring findings to five harness modules, evolves those modules in restricted scopes, and then runs an integration stage.

The critical limitation is also clear: the five module boundaries are chosen by the authors. The method does not learn the decomposition.

## Mental model

A task fails once. That alone gives weak evidence: maybe the model sampled a bad action.

Now run the same task several times. If some attempts succeed and some fail, compare them. The task itself is held constant, so behavioral differences are more informative.

Suppose failed traces repeatedly lose important output after context compression while successful traces preserve it. That points toward **context management**, not tools or task completion.

ModularRSI collects many such findings and gives each module a restricted repair surface. This reduces the number of unrelated variables changing at once.

## Key objects and state

The fixed five modules are:

1. **Agent Loop** — top-level reason/act control.
2. **Observation Management** — how tool/environment outputs are transformed.
3. **Tool Use** — tool definitions and calling behavior.
4. **Context Management** — retention, compression, context construction.
5. **Task Completion Detection** — deciding when the job is actually done.

Other state:
- repeated task trajectories;
- contrastive success/failure pairs;
- function-level findings;
- per-module evolution history;
- local validation checks;
- anti-hacking/program checks;
- integration epoch.

## Optimization loop

~~~mermaid
flowchart TD
    A["Run several attempts for the same task"] --> B{"Mixed success and failure?"}
    B -- "Yes" --> C["Contrast successful vs failed traces"]
    B -- "No" --> D["Use weaker evidence / move to other tasks"]
    C --> E["Extract recurring function-level finding"]
    E --> F["Assign finding to one of five modules"]
    F --> G["Evolve that module inside restricted source scope"]
    G --> H["Program checks + anti-hack checks + task validation"]
    H --> I{"Local candidate accepted?"}
    I -- "No" --> G
    I -- "Yes" --> J["Store improved module"]
    J --> K["Integration epoch resolves cross-module conflicts"]
    K --> L["Validate complete harness"]
    L --> A
~~~

## Step-by-step implementation

1. Instrument the harness so source functions map to one of the five modules.
2. Run multiple attempts per training task.
3. Prioritize tasks with both successes and failures; they are natural controlled comparisons.
4. Align the successful and failed traces.
5. Extract concrete differences such as lost observation, wrong tool schema, premature stop, repeated action, or malformed context.
6. Aggregate the same pattern across tasks. One weird run should not trigger a module rewrite.
7. Assign the finding to a module and relevant functions.
8. Restrict the optimizer to that module during the local evolution stage.
9. Run syntax/program tests, leakage checks, and task validation.
10. Store accepted module versions and their evolution history.
11. After module-local work, run an **integration epoch**. Resolve duplicated logic, incompatible assumptions, and interfaces.
12. Freeze the final harness before OOD benchmarks.

## Experimental setup

The paper deliberately separates evolution data from evaluation domains.

The seed harness scores about:
- **73.40%** on SWE-bench Verified;
- **47.57%** on Terminal-Bench.

It then uses task sets related to one benchmark for evolution and measures both same-domain and cross-benchmark effects.

## Results that matter

| Evolution setup | SWE-bench Verified | Terminal-Bench | Interpretation |
|---|---:|---:|---|
| No evolution | 73.40% | 47.57% | Seed |
| Evolve on TB-related tasks | **75.80%** OOD | **52.43%** ID | Gains transfer to SWE. |
| Evolve on SWE-related tasks | **76.45%** ID | **49.40%** OOD | Transfer works in reverse too. |

The decisive structure ablation on Terminal-Bench is:

- seed: **47.57%**
- non-modular whole-harness evolution: **46.44%**
- joint all-module evolution: **44.19%**
- modular evolution: **52.43%**

That is unusually strong evidence for restricted component-wise evolution. The monolithic alternatives do not merely improve less; they fall below the seed.

## What the ablation proves—and what it does not

It supports:
- decomposition can improve optimization stability;
- module-local editing can reduce harmful interference;
- integration after local search matters.

It does **not** prove:
- the chosen five modules are optimal;
- contrastive analysis alone caused the gain;
- any arbitrary decomposition would work.

The paper does not provide a clean dedicated ablation isolating only the contrastive-trace analysis from the rest of the modular pipeline.

## Failure modes and limits

- Five module boundaries are hand-designed.
- A finding can genuinely belong to several modules.
- Restricted editing can block a repair that needs a cross-module change.
- Integration can become a hidden second whole-harness optimizer.
- Contrastive pairs are sparse when a task always succeeds or always fails.
- Cross-benchmark transfer is promising but covers a limited set of domains.

## Implementation checklist

You need:
- repeated rollouts;
- a trace alignment tool;
- source-to-module ownership map;
- typed failure findings;
- per-module edit permissions;
- module version/history;
- integration stage;
- frozen OOD evaluation.

For each finding store confidence and alternative owners. Do not force every diagnosis into one module when the evidence is ambiguous.

## What RHEvolution should take from it

This is probably the **main fixed-decomposition baseline**.

RHEvolution's experiment should hold everything else constant and replace only the partition rule:

**ModularRSI-style condition:** five fixed owners.

**RHEvolution condition:** start from the same or coarser owners, then allow split/fuse/reassign based on trace evidence and coupling.

Use the same evolution tasks, proposer, solver, rollout count, and validation budget. If adaptive decomposition beats this baseline OOD, that is direct evidence for the research claim.
