## What is actually new

Mid-Harness adds a verification layer **between model generation and harness execution**.

At each step, the generator proposes several possible next actions. A verifier compares them and selects one. Only the selected action reaches the normal harness/environment.

The core result is that **candidate diversity is only valuable if the selector is strong enough**. The generator can stay fixed while a better verifier substantially raises task success.

## Mental model

A terminal agent considers:
- inspect the repo;
- run tests;
- edit a file;
- search the web;
- finish.

Normally it samples one action and commits to it.

Mid-Harness samples several candidate actions from the same interaction history. The verifier sees all candidates plus context and decides which one should execute.

This spends extra inference compute at the action level rather than rerunning complete trajectories.

## Key objects and state

- **Interaction history**
- **Generator:** proposes N candidate next actions.
- **Candidate action set**
- **Verifier**
- **Verification strategy:** listwise, pointwise, or pairwise.
- **Selected action**
- **Existing harness:** unchanged after selection.
- **Environment state:** only one action is actually executed.
- **Distilled verifier:** smaller model trained to imitate a stronger verifier.

## Action-selection loop

~~~mermaid
flowchart TD
    A["Current interaction history"] --> B["Generator samples N next actions"]
    B --> C["Verifier receives history + candidates"]
    C --> D{"Verification mode"}
    D -->|Listwise| E["Rank all candidates in one call"]
    D -->|Pointwise| F["Score each candidate"]
    D -->|Pairwise| G["Compare candidate pairs"]
    E --> H["Choose one action"]
    F --> H
    G --> H
    H --> I["Existing harness executes ONLY selected action"]
    I --> J["New environment observation"]
    J --> A
~~~

## Step-by-step implementation

1. Keep your normal agent/harness unchanged.
2. At a decision point, sample N candidate actions using the same history.
3. Normalize candidates into the exact action schema expected by the harness.
4. Give the verifier enough context to understand consequences, not only action strings.
5. Choose one comparison strategy.
6. Execute only the winner.
7. Save verifier choice, rejected candidates, and downstream result.
8. Measure whether a stronger verifier selects actions that lead to better final outcomes.
9. If frontier verification is too expensive, collect teacher choices and train a smaller verifier.
10. Combine with full-trajectory search only if the extra action-level compute still has positive marginal value.

## Verification strategies

**Listwise:** one call sees all candidates. Cheap, but quality can fall when the list is large.

**Pointwise:** score each action independently. Easier to parallelize, but scores may not be calibrated.

**Pairwise:** compare actions two at a time. Usually stronger because the decision is simpler, but exhaustive comparison costs roughly N(N-1)/2 calls.

For N=8, exhaustive pairwise comparison needs **28 comparisons**.

## Experimental setup

The main result uses terminal-agent benchmarks and a fixed generator/harness. This isolates the value of action selection.

One reported setup wraps TMAX-9B and uses a strong frontier verifier. The method is also tested across other generator sizes, benches, and harness configurations.

## Results that matter

- TMAX-9B on Terminal-Bench Lite rises from about **50.0% to 68.03%** with N=8 candidates and a strong verifier.
- Pairwise verification is strongest among the tested verification schemes, but also most expensive.
- Distilling a strong verifier improves one smaller-verifier setting from about **54.76% to 57.14%**.
- The paper reports that action-level scaling composes with trajectory-level scaling, and one combined setting beats a Best-of-T trajectory baseline at substantially lower estimated token cost.

The important causal result is that the generator did not need to change. Better selection unlocked capability already present in its action distribution.

## What this means for harness optimization

An optimizer can generate many candidate edits, but **proposal diversity is not enough**.

If the selector cannot reliably distinguish:
- a useful split from an unnecessary split;
- a real regression fix from a benchmark trick;
- a good local edit from a globally harmful one;

then more candidates only increase search noise.

Verification quality should therefore be measured separately from proposal quality.

## Failure modes and limits

- There is no gold label for "best next action," so verifier quality is inferred from downstream task results.
- Pairwise comparison becomes expensive as N grows.
- A verifier can prefer safe-looking actions and suppress necessary risky exploration.
- Teacher-distilled verifiers can inherit teacher bias.
- This is inference-time action scaling, not persistent harness evolution.

## Implementation checklist

For every selection record save:
- history hash;
- candidate actions;
- verifier prompt/model/version;
- chosen action;
- comparison graph/scores;
- later task outcome.

Build a diagnostic: "when the final task failed, was the winning action actually worse than a rejected candidate?" This separates generator failure from verifier failure.

## What RHEvolution should take from it

Treat the **candidate selector as its own component**.

RHEvolution should separately evaluate:
- edit proposal recall: did the search generate at least one good candidate?
- selector precision: when a good candidate existed, did promotion choose it?
- full-harness outcome.

Cheap pairwise selection can triage many component edits. But split/fuse decisions should still receive real execution evidence because a structural false positive has long-term consequences.
