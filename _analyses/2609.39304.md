## What is actually new

This paper shows that automatic harness evolution can fail for a basic statistical reason: **promotion decisions are too noisy**.

With a small rollout batch, a challenger can appear better by luck. Because every promoted harness becomes the parent of future edits, one noisy mistake changes the entire later search path.

Two simple controls fix much of the problem:
1. use enough matched rollouts per decision;
2. promote a challenger only if it strictly beats the current champion on the same cases.

The novelty is less about a fancy optimizer and more about identifying **evaluation scale and selection policy as first-class parts of harness evolution**.

## Mental model

Suppose true success rates are:
- champion 55%;
- challenger 52%.

Evaluate each on five tasks. The challenger can easily score 4/5 while the champion gets 2/5. If you promote it, later search starts from a worse harness.

Repeat this mistake over 20 generations and performance drifts downward.

Larger matched batches reduce this noise. Champion-Challenger selection also stops every syntactically valid edit from becoming the new base.

## Key objects and state

- **Champion:** current accepted harness.
- **Challenger:** one proposed edit.
- **Matched rollout set:** same tasks/seeds for champion and challenger.
- **Promotion gate:** strict measured improvement.
- **Rejected-change log:** prevents repeated bad edits.
- **Rollout scale:** number of executions behind one decision.
- **Held-out set:** detects overfit to the promotion batch.

## Evolution loop

~~~mermaid
flowchart TD
    A["Champion harness"] --> B["Run fixed matched task/seed batch"]
    B --> C["Optimizer reads traces + rejected history"]
    C --> D["Propose one bounded challenger commit"]
    D --> E["Repository / syntax tests"]
    E --> F["Run challenger on SAME task/seed batch"]
    F --> G["Compute paired delta"]
    G --> H{"Strictly better?"}
    H -- "No" --> I["Reject + log change"]
    H -- "Yes" --> J["Promote challenger to champion"]
    I --> A
    J --> A
    J --> K["Periodic held-out evaluation"]
~~~

## Step-by-step implementation

1. Freeze a champion version.
2. Sample a task/seed batch for the round.
3. Run the champion and keep full trajectory evidence.
4. Let the optimizer propose one bounded change.
5. Run repository tests.
6. Run the challenger on **the exact same cases**.
7. Use paired difference, not two unrelated sample means.
8. Require a strict win or a confidence threshold before promotion.
9. Log rejected edits so the proposer can avoid repeating them.
10. Periodically evaluate the champion on held-out tasks not used for promotion.
11. Increase rollout scale for high-impact structural edits.
12. Report both training/promotion-set and held-out curves.

## Experimental setup

The study uses visual-interface robot agents. The optimizer changes prompts/tools/control rules while the underlying model is fixed.

The paper varies:
- number of rollouts per evolution round;
- unconditional acceptance versus Champion-Challenger promotion.

This is a clean way to isolate evaluation policy from proposer capability.

## Results that matter

### Rollout scale

Holding the number of search rounds fixed and increasing training rollouts from **5 to 100** raises held-out success from about **47% to 67%**.

Small training sets can look excellent on the search tasks—around **70%**—while reaching only about **54%** held-out. That is direct overfitting/noise evidence.

### Selection policy

With unconditional acceptance, performance drifts downward within roughly ten rounds.

With Champion-Challenger selection, the same general loop raises held-out success from about **51% to 67%** over 30 rounds.

So the optimizer is not enough. The gate determines whether useful edits accumulate or noise compounds.

## Why matched evaluation matters

Using the same task/seed cases reduces variance from:
- task difficulty;
- stochastic environment state;
- random starting conditions.

For RHEvolution this is even more important. A split/fuse changes the search space for later rounds, so a false-positive structural promotion is more expensive than a small prompt mistake.

## Failure modes and limits

- The largest tested rollout batch is also the best, so the paper does not identify a universal sufficient sample size.
- Strict "score must increase" gates can reject neutral stepping stones that enable later gains.
- Reusing one fixed promotion batch can overfit it.
- Robot/UI tasks may have different variance from coding benchmarks.
- A large batch improves confidence but increases cost.

## Implementation checklist

For each candidate-parent comparison record:
- exact matched task IDs;
- seeds/environment snapshots;
- per-case paired outcomes;
- mean delta;
- confidence/uncertainty;
- promotion decision.

Use separate:
- cheap local component gate;
- stronger full-harness gate;
- locked held-out/OOD evaluation.

## What RHEvolution should take from it

Structural decisions need **more evidence than ordinary local edits**.

A sensible policy:
- small prompt/tool edit → local matched batch;
- component implementation rewrite → larger local + global batch;
- split/fuse/reassign ownership → largest global batch plus held-out check.

Also consider keeping promising non-promoted structural branches instead of deleting them. That preserves stepping stones without weakening the champion gate.
