## One line
A harness where the model's only action is emitting a Python program that blocks and resumes in place (via a coroutine bridge) across evaluator tool round-trips — so one model call spans many tool calls, and deterministic policies live as enforced code in the tool layer rather than prompt prose.

## The problem
CAR-bench (in-car assistant, 58 tools, 19 domain policies, 254 tasks) externalizes tool execution to the evaluator, so every tool-result exchange is a separate agent round-trip. A conventional next-action agent spends one model call per round of results, so a chain of *dependent* tool calls costs one model call per link — a latency and cost tax. Track 2 additionally rewards compute-aware harnessing: converting fast inference into low end-to-end latency and reliable behavior. The headline metric is Pass@3: a task counts only if it passes all three independent trials, so consistency — not just single-shot success — decides the winner.

## How it works
Each agent context owns a long-lived worker (persistent Python interpreter, tool bridge, scratchpad, transcript). The model's sole action is `execute python` — it emits one program, and when that program calls a tool wrapper, the coroutine bridge suspends the Python thread, emits the official tool call, and resumes the *same stack frame* when results arrive: no new model call. The program branches over tool results and issues parallel reads via `batch([...])`. Because the action surface is code, deterministic policies are encoded as logic in the tool layer (e.g., set-fog-lights delegates to a fog-light safety helper; a confirmation state machine stores the fully grounded pending action), so policy compliance is enforced by construction at zero reasoning cost. Extra mechanisms: response obligations (policy-mandated disclosures appended only if the model's text omitted them), unknown-value sentinels (converting blanked hallucination fields into honest failures), and turn-scoped outcome tracking (mutation failures keyed by tool+arguments so optimistic success claims can't outrun failed side effects). A single static prompt, byte-identical across calls and tasks, served 78% of input tokens from cache.

## Key results
- Won CAR-bench Track 2 (hidden set): 60.0% Pass@3 vs 13.33% organizer baseline (4.5×), vs runner-up's 50.0% — both had identical 57/90 successful trials, but the harness's consistency (92.5% vs 73.9%) converted them.
- Compute profile: median 2 model calls carrying 7 agent turns per task; median 1.8 s model latency; 3.14 s median task latency; lowest estimated cost per trial of any entry above baseline ($0.041).
- Same unchanged harness reproduced 60.0% Pass@3 on GPT-5.5 in the Open track, matching frontier-model agents.

## How it relates to adaptive decomposition
It doesn't. This is a fixed, human-designed harness architecture — one static prompt, one coroutine bridge, hand-encoded policies — with no optimization loop, no components, and no decomposition of anything. It is included here as a sharp example of the *opposite* pole: harness engineering where all structure is human-set and the only win is architectural efficiency. Useful contrast for adaptive decomposition: Policy-as-Code shows what you get when the harness is a brilliant fixed design; adaptive decomposition asks what you get when the harness structure itself becomes the search object.

## Limits and open questions
The harness is entirely hand-tuned to CAR-bench's structure (deterministic policies, externalized tools); nothing generalizes to environments where policies need genuine interpretation. The "policy as code" split requires a human to decide what is deterministic vs. interpretive — that decision itself could drift. Open: could a self-improving loop *discover* which policies are deterministic given grounded facts and promote them from prompt to code automatically?
