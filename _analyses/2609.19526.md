## What is actually new

SIFT attacks the **evaluation bottleneck** in agent self-improvement.

Full benchmark execution is much more expensive than asking an LLM to compare two candidate harnesses. SIFT therefore uses cheap pairwise judgments to rank many candidates, converts those comparisons into a global strength score, and sends only promising candidates to expensive benchmark evaluation.

The core novelty is a **two-fidelity search queue**: cheap semantic ranking first, real task execution second.

## Mental model

Suppose one full candidate evaluation costs $6 and takes 2.6 CPU-hours, while one pairwise judge comparison costs a few cents and seconds.

If you fully evaluate every child, most search budget is wasted proving that bad candidates are bad.

SIFT instead asks a strong judge:
"Given the code/diff and evidence, which of these two candidates is more promising?"

Many pairwise wins/losses are then fit with a Bradley-Terry model. That produces one estimated strength per candidate. Full evaluation workers pull the highest-priority candidates.

## Key objects and state

- **Candidate tree/archive**
- **Parent-selection policy**
- **Child patch:** self-improvement edit.
- **Pairwise comparison:** judge chooses between two candidates.
- **Bradley-Terry score:** latent strength inferred from pairwise outcomes.
- **Priority evaluation queue**
- **Cheap gate:** small task sample used to reject catastrophic patches.
- **Full/intermediate benchmark evaluation**
- **Asynchronous workers:** expansion and evaluation can proceed separately.

## Search loop

~~~mermaid
flowchart TD
    A["Candidate archive"] --> B["Select parent using quality + exploration"]
    B --> C["Self-improver creates child patch"]
    C --> D["Run cheap validity / tiny task gate"]
    D --> E{"Obviously bad?"}
    E -- "Yes" --> F["Discard or low priority"]
    E -- "No" --> G["Compare child against strong archive candidates"]
    G --> H["Update pairwise win/loss graph"]
    H --> I["Fit Bradley-Terry strength"]
    I --> J["Insert child into priority queue"]
    J --> K["Expensive evaluator pulls highest-priority node"]
    K --> L["Run real benchmark tasks"]
    L --> M["Update archive with measured score"]
    M --> A
~~~

## Step-by-step implementation

1. Keep a version tree of all valid harness candidates.
2. Select a parent using a mix of measured quality and exploration.
3. Ask the self-improver to create a child patch.
4. Run syntax/repository tests and a tiny task gate.
5. Compare the surviving child pairwise with several strong incumbents using a judge model.
6. Store each judge decision as an edge: candidate A preferred to candidate B.
7. Fit a Bradley-Terry model or another pairwise ranking model to infer candidate strengths.
8. Put candidates into an evaluation queue sorted by expected value/uncertainty.
9. Separate expansion workers from expensive evaluation workers so search can continue while evaluations run.
10. Full evaluation results replace judge estimates whenever available.
11. Final claims must use real held-out benchmark execution, never judge ranking alone.

## Why the cost gap is large

The paper reports one representative resource table:

| Operation | Approx. cost | Approx. time |
|---|---:|---:|
| Self-improvement expansion | **$0.12** | **0.186 CPU h** |
| One pairwise judge call | **$0.044** | **0.0042 CPU h** |
| Polyglot-50 full eval | **$6.0** | **2.6 CPU h** |

Even ten judge comparisons are much cheaper than one full Polyglot-50 evaluation.

This makes ranking useful as a *scheduler* even if it is not reliable enough to be the final evaluator.

## Experimental setup

SIFT is built on a DGM-style coding-agent self-improvement setup.

For Polyglot:
- full benchmark: **225 tasks** across C++, Go, Rust, Java, JavaScript, Python;
- small gate: **4 tasks**;
- intermediate search signal: **50 tasks**;
- full 225 tasks are held for final evaluation;
- the matched search budget uses up to **30 expansion steps**.

One setting uses Qwen3-Coder-30B as the coding model and Qwen3-480B as both self-improver and judge.

## Results that matter

During one reported search, Polyglot-50 accuracy progresses from about **16% to 38%** across 30 evolution steps, while archive quality rises steadily.

The best descendant reports about **31.1%** on the full held-out Polyglot benchmark.

The paper compares against DGM/HGM-style baselines and reports similar or stronger end performance at substantially lower search cost because many children never require a full evaluation.

The important result is therefore **search efficiency**, not that LLM judgment replaces execution.

## Failure modes and limits

- A judge can rank stylistically attractive but functionally bad patches.
- Bradley-Terry compresses multidimensional task tradeoffs into one scalar.
- Pairwise outcomes can be non-transitive.
- Strong results use a judge larger than the coding model.
- The tiny task gate can miss rare catastrophic regressions.
- Full evaluation remains necessary for final evidence.

## Implementation checklist

Maintain:
- candidate ID / commit;
- parent ID;
- cheap-gate result;
- pairwise comparison graph;
- ranking score + uncertainty;
- expensive evaluation status;
- measured benchmark vector.

Do not overwrite task-level scores with one Bradley-Terry scalar. The scalar is for scheduling; task-level evidence is needed for specialization and OOD analysis.

## What RHEvolution should take from it

RHEvolution will create many more candidate edits because several components can evolve independently. It needs a cheap scheduler.

Use SIFT as:
- cheap component-edit triage;
- priority queue for global validation;
- asynchronous expansion/evaluation architecture.

But rank **candidate-parent deltas conditioned on the component's owned failures**, not only one global scalar. Structural split/fuse proposals should receive full-harness evaluation earlier because a bad structural decision changes later search space.
