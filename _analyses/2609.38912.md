## One line
Instead of generating harness code per task (expensive, error-prone), mine validated reusable "harness primitives" from failed trajectories, then at test time compose a task-specific harness by selecting primitives and wiring them with a deterministic compiler — no code generation at deployment.

## The problem
A mechanism that helps one task can impose overhead or context distraction on another, so a single fixed harness is suboptimal (task-mechanism mismatch). But generating harness code per task compounds execution risk: under an independent mechanism-failure model, the probability a generated harness stays executable decays exponentially in the number of generated mechanisms. The paper wants task-adaptive harnesses that are both flexible *and* robust to build at test time.

## How it works
- **Theory (Section 3):** Proposition 1 quantifies the fixed-harness gap — Γ_fixed = Σ min(µi·ūi, (1−µi)·c̄i) > 0, i.e. including a mechanism across tasks pays expected out-of-scope penalties while excluding it sacrifices in-scope utility. Proposition 2 shows a generated harness's validity decays as (1−ϵ)^k(x), while primitive-based composition (validated parts + deterministic compiler) dominates under stated conditions.
- **Harness Primitives:** mined from failed execution trajectories — cluster recurring deficiencies, propose a candidate mechanism, validate and repair it from check feedback. Each primitive carries an application scope and a composition contract. Six were developed for SWE-bench (e.g. Change-surface Tracer, Contract-case Explorer, Environment-capability Runner), five for Terminal-Bench (e.g. State Guard, Execution Supervisor).
- **STITCH:** at test time, a composer evaluates the task instructions and execution context against primitives' application scopes to pick a "composition intent"; a deterministic compiler wires the selected primitives into an executable harness graph. Selection and dependency handling are separated, so the composer never writes or repairs mechanism code.

## Key results
- SWE-bench Verified (GPT-5.6-Luna): STITCH reaches 80.5% Pass@1 vs 73.0 seed harness (Mini-SWE-agent), 79.0 Codex CLI, 70.5 MemoHarness, 73.5 MetaHarness — up to ~12 points over fixed baselines, beating human-designed harnesses; +4.5 over the strongest fixed primitive.
- Terminal-Bench 2: 72.2 vs 60.0 seed, 56.7 Codex CLI, 55.6 MetaHarness; 81.0% on medium tasks, 46.2% on hard, 100% on easy.
- Scales with library size: 75.0→80.5% (SWE) and 62.2→72.2% (Terminal-Bench) as primitives are added.
- Efficiency: composition overhead is 2.7% of execution cost on Terminal-Bench (4.3% on SWE), at least 638× cheaper than generating harnesses from scratch; 100% component activation rate (compiled primitives genuinely take effect).
- Generalization: primitives developed with GPT-5.6-Luna transfer to GPT-5.6-Terra, DeepSeek-V4-Flash, and Claude-4.5-Haiku with the composer still selecting effectively.

## How it relates to adaptive decomposition
This is the PluginRSI idea taken one level deeper: instead of fixed human-designed plugins, primitives are *mined from failures* (recurring deficiencies in real trajectories), each with an explicit application scope and composition contract, and composed per task rather than fixed globally. It validates two pillars of adaptive decomposition: (1) a library of validated, reusable components whose membership grows over time — STITCH's library-size scaling curve is exactly the "accumulate working components" dynamic; (2) per-task/per-instance composition decisions, with the theory (Prop 1) formalizing why a monolith loses. The deterministic compiler is a pragmatic answer to the "local vs global correctness" problem — composition can't produce invalid harnesses by construction. What it lacks: the agent doesn't *discover the decomposition* (humans mine the primitives), there's no recursive split of failing components, no independent per-component search budgets, and no reversion mechanism. Turbo Harness (2609.40330, same day) is the natural complement: instance-patching vs component-composition.

## Limits and open questions
The theory assumes additive primitive utilities (no interactions between primitives) and that all combinations are admissible — real mechanisms interact, and the compiler's determinism is only as good as the contracts. Primitives are mined with human involvement in the development loop (clustering, proposing, repair from check feedback); the paper doesn't claim fully automatic primitive discovery. Evaluation is two benchmarks (SWE-bench Verified, Terminal-Bench 2) with held-out subsets; cross-model transfer re-tunes application scopes per model, so it's partial transfer. The 638× efficiency figure compares against from-scratch code generation, a deliberately weak baseline.
