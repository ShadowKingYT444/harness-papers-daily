## Main idea
STITCH builds a task-specific harness from validated reusable primitives. It does not generate new harness code during deployment. A composer selects the needed primitives, and a deterministic compiler connects them.

## Key concepts
- **Harness primitive:** A reusable mechanism that solves a recurring harness problem.
- **Application scope:** A description of when a primitive should be used.
- **Composition contract:** Rules that say how a primitive can connect to other primitives.
- **Deterministic compiler:** Code that wires selected primitives together in a fixed, testable way.
- **Task-mechanism mismatch:** A mechanism helps some tasks but adds cost or confusion on others.

## Optimization loop
```mermaid
flowchart LR
    A[Failed development traces] --> B[Find recurring deficiency]
    B --> C[Create primitive]
    C --> D[Validate and repair primitive]
    D --> E[Add to primitive library]
    E --> F[New task]
    F --> G[Select matching primitives]
    G --> H[Deterministic compile]
    H --> I[Run task-specific harness]
```

## How it works
During development, recurring failures are grouped into reusable mechanisms. Each primitive gets a scope and a composition contract. The primitive is tested and repaired before it enters the library.

At test time:
1. The composer reads the task and execution context.
2. It selects primitives whose scopes match the task.
3. A deterministic compiler resolves dependencies and builds the harness graph.
4. The agent executes the compiled harness.

The composer selects parts, but it does not write mechanism code at deployment.

## Why it matters for RHEvolution
STITCH supports two major RHEvolution ideas: **keep validated components** and **compose only the components needed for the current problem**.

Its compiler also shows one way to reduce local/global conflict. If component interfaces are strict, many invalid fusions become impossible by construction.

The missing step is automatic decomposition discovery. Humans still define and mine the primitive set. RHEvolution can automate the point where a recurring failure becomes a new primitive or where one primitive is split into smaller ones.

## Evidence and limits
- The paper reports strong gains on SWE-bench Verified and Terminal-Bench 2.
- Composition overhead is small relative to task execution in the reported experiments.
- Larger primitive libraries improve results in the reported scaling study.
- The theory assumes limited interaction between primitives, while real harness components can have strong coupling.
