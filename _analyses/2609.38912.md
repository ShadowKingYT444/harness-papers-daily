## What is actually new

STITCH separates **mechanism discovery** from **task-time composition**.

During development, failures are turned into reusable, tested harness primitives. Each primitive gets:
- an application scope: when it helps;
- a composition contract: inputs, outputs, dependencies, environment needs.

At test time, an LLM only selects primitives. A deterministic compiler wires them into an executable task-specific harness. It does **not** generate new mechanism code during deployment.

The true novelty is the separation of semantic selection from reliable integration.

## Mental model

One global harness often contains mechanisms that help some tasks and hurt others.

For example:
- repository-map generation helps a large unfamiliar codebase;
- the same mechanism is wasted context on a tiny terminal task;
- a state guard helps fragile multi-step execution;
- it adds overhead when the task is one command.

A task-adaptive system should turn mechanisms on only when useful. But generating fresh Python code for every task is risky.

STITCH's answer:
1. discover and debug mechanisms offline;
2. select among those trusted implementations online;
3. use compiler rules to connect dependencies.

## Key objects and state

- **Seed harness graph**
- **Harness primitive:** tested control operation.
- **Application scope:** textual/structured conditions for use.
- **Composition contract:** input/output/dependency requirements.
- **Primitive library:** fixed at test time.
- **Composer:** LLM that outputs a composition intent.
- **Composition intent:** which primitives should be active.
- **Deterministic compiler:** creates the executable graph.
- **Shared execution state:** history/intermediate results exchanged by nodes.
- **Fallback:** seed harness if compilation cannot be repaired.

## Step-by-step implementation

### Primitive development
1. Run the seed harness on a development set.
2. Cluster or inspect failed trajectories for recurring harness deficiencies.
3. Propose one mechanism with a clear activation point and intended downstream effect.
4. Implement it as a primitive with a stable interface.
5. Test that it actually activates and changes the intended request/action/control path.
6. Run matched tasks with and without the primitive.
7. Accept only primitives with positive evidence.
8. Write an application scope from where it helped/hurt.
9. Write a composition contract: required inputs, produced outputs, dependencies, loops, environment needs.

### Test-time composition
10. Give the composer only task information, environment spec, seed graph, and primitive descriptions/contracts.
11. Composer outputs a design-level list of selected primitives. It does not write implementation code.
12. Compiler inserts those primitives, dependencies, and state edges.
13. Validate supported IDs, environment compatibility, graph connectivity, reachable termination, and bounded loops.
14. If the intent is invalid, allow bounded correction.
15. If correction fails, fall back to the seed harness.

## Why this can beat a fixed harness

The paper formalizes a simple task-mechanism mismatch.

A mechanism has:
- positive value in its scope;
- a cost outside its scope.

A fixed harness must either always include it or always exclude it. Task-conditioned activation can avoid both the missed benefit and the unnecessary cost.

The paper also models raw task-time code generation. If each generated mechanism has an independent failure chance, the probability that a multi-mechanism generated harness is valid falls as more code is generated. Reusing tested primitives avoids much of that implementation risk.

## Experimental setup

Main evaluation:
- **100** sampled SWE-bench Verified tasks;
- **45** sampled Terminal-Bench 2 tasks;
- **2 attempts per task**;
- common seed: Mini-SWE-agent 2.4.6;
- development model: GPT-5.6 Sol;
- main actor/composer: GPT-5.6 Luna;
- development tasks are disjoint from the reported evaluation sample.

Baselines include Mini-SWE-agent, SWE-agent, Codex CLI, MemoHarness, MetaHarness, and fixed-primitives variants.

## Results that matter

| Benchmark | STITCH Pass@1 | Seed | Codex CLI | MetaHarness |
|---|---:|---:|---:|---:|
| SWE-bench Verified | **80.5%** | 73.0% | 79.0% | 73.5% |
| Terminal-Bench 2 | **72.2%** | 60.0% | 56.7% | 55.6% |

Repeated-success metric also rises:
- SWE-bench Pass²: **76.0%** vs seed **68.0%**;
- Terminal-Bench Pass²: **66.7%** vs seed **51.1%**.

STITCH beats the best single fixed primitive by about **4.5 points** on SWE-bench and **5.5 points** on Terminal-Bench.

The paper reports only about **2.7% test-time composition overhead**, and estimates this is at least **638× cheaper** than generating task-specific harness code from scratch.

It also reports **100% component activation** in the tested compositions, which matters because a selected primitive that never runs should not receive credit.

## What the scaling result means

Performance improves as the primitive library becomes more useful/larger. That supports the idea that reusable mechanisms can accumulate.

But library size is not enough by itself. A poor composer can select out-of-scope primitives and reintroduce the fixed-harness problem.

So the two learned assets are:
- the primitive library;
- the mapping from task evidence to primitive activation.

## Failure modes and limits

- Primitive discovery is still an offline human/agent-guided process; structural boundaries are not fully autonomous.
- Contracts can miss semantic interactions between primitives.
- The theory assumes simplified additive utilities and independent implementation failures.
- A deterministic compiler prevents some integration bugs, not logical interference.
- Task-time adaptation is selection only; the system cannot invent a new mechanism for a novel failure.
- Scope descriptions can become stale as the actor model changes.

## Implementation checklist

A primitive registry needs:
- ID/version;
- implementation hash;
- scope;
- input/output schema;
- dependencies;
- environment requirements;
- activation test;
- matched validation results;
- known conflicts.

The compiler should reject:
- unknown primitive IDs;
- unsatisfied dependencies;
- cycles unless explicitly bounded;
- unreachable termination;
- incompatible environment/tool requirements.

## What RHEvolution should take from it

STITCH shows what the **output of successful RHEvolution** could look like: a validated library of reusable mechanisms with contracts.

RHEvolution's contribution would be upstream:
- automatically decide when one owner should become a new primitive;
- recursively split large primitives;
- fuse coupled primitives;
- learn ownership from traces;
- preserve the deterministic compiler/global gate.

A strong design is: RHEvolution discovers structure offline, then STITCH-style composition uses the validated structure safely at test time.
