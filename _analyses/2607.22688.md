## What is actually new

Co-Harness treats the model and the harness as **two coupled optimization targets**. It alternates between repairing the harness from failure traces and fine-tuning the model from trajectories produced by the improved harness.

Most harness-evolution work freezes model weights. Most model training freezes the external scaffold. Co-Harness studies the feedback loop between them.

The useful technical idea for harness research is its **structured failure attribution + validation + rollback discipline**.

## Mental model

A weak result can come from two different sources:

- the model knows what to do, but the harness gives it bad tools, context, or control logic;
- the harness is reasonable, but the model itself cannot perform the needed reasoning.

If every failure triggers a harness patch, the scaffold becomes bloated and can even compensate for model errors in brittle ways. Co-Harness therefore includes an "agent error" class: the critic is allowed to say the harness is not the right repair target.

After accepted harness repairs generate better trajectories, those trajectories become supervised fine-tuning data. A stronger model then changes which harness weaknesses are visible in the next round.

## Key objects and state

- **Five harness areas:** prompts/templates, tools, skills, middleware, and long-term memory.
- **HarnessCritic:** reads failed traces and assigns a root cause.
- **Failure record:** root cause, affected area, severity, trace evidence, proposed repair.
- **Agent-error abstention:** explicitly says "do not patch the harness."
- **Versioned harness registry:** stores accepted configurations and supports rollback.
- **Validation gate:** replays tasks before a patch is accepted.
- **Successful trajectory pool:** accepted trajectories used for model SFT.
- **Model checkpoint:** updated between harness-optimization rounds.

## Co-evolution loop

~~~mermaid
flowchart TD
    A["Current model + current harness"] --> B["Run task batch"]
    B --> C["Separate failed and successful traces"]
    C --> D["HarnessCritic classifies failures"]
    D --> E{"Harness fault?"}
    E -- "No: agent error" --> F["Do not patch harness"]
    E -- "Yes" --> G["Propose local code/config change"]
    G --> H["Replay target cases + regression cases"]
    H --> I{"Validation gate passes?"}
    I -- "No" --> J["Reject / rollback"]
    I -- "Yes" --> K["Commit new harness version"]
    K --> L["Collect successful trajectories"]
    F --> L
    L --> M["Supervised fine-tune model"]
    M --> A
~~~

## Step-by-step implementation

1. Instrument task runs so every tool call, observation, prompt, and outcome is stored.
2. Define a small failure taxonomy. Co-Harness uses prompt ambiguity, tool schema error, missing skill, middleware mismatch, memory overflow, and agent error.
3. For each failed trace, have the critic output a structured diagnosis with evidence spans. Do not accept free-form "the agent got confused."
4. Aggregate repeated diagnoses. Prioritize failures that recur, are severe, and point to the same location.
5. Generate a bounded patch in the implicated harness area.
6. Run repository tests first. Then replay the target failure and a set of previously successful cases.
7. Accept the change only if the target improves without a measured regression outside the target region.
8. Store the accepted candidate in a version registry. Keep the parent for rollback.
9. After a harness round, collect successful task trajectories produced by the improved harness.
10. Fine-tune the model on those trajectories.
11. Start the next harness round from the new model checkpoint. Re-run attribution because the bottleneck may have moved.

## Experimental setup

The strongest experiments use tool-integrated math tasks and Qwen3 model sizes. The paper reports several rounds:

- **R0:** initial model/harness.
- **R1:** after a first co-evolution cycle.
- **R2:** after another cycle.

A separate long-running engineering case study lets the system create many harness versions over more than 200 hours.

Because both the model and harness change, not every final gain can be attributed to harness evolution alone. The paper's value is the interaction study, not a pure fixed-model harness comparison.

## Results that matter

| Setting | R0 | R1 | R2 | Main point |
|---|---:|---:|---:|---|
| Qwen3-8B AIME24 | 63.3% | 84.0% | 84.7% | Large early gain; later plateau. |
| Qwen3-8B AIME25 | 56.9% | 66.7% | 78.3% | Later model alignment still helps. |
| Qwen3-8B HMMT25 | 39.6% | 52.3% | 59.7% | Improvement survives another distribution. |
| Qwen3-32B HMMT25 | 49.8% | 68.7% | 77.0% | Stronger model still benefits. |

The autonomous engineering case created **22 harness versions** over **200+ hours**. One repair stage moved a failing configuration from **0% to 59.6%**. A batching change cut one runtime from **3.78 h to 1.11 h** while restoring accuracy to about **61.5%**. A six-trajectory majority-vote setup reached **63.3%** within a **3.33 h** budget.

The registry also rolled back a prompt change that caused about a **16.5-point regression**.

## What the ablations really show

The clearest evidence is not only the final score. It is that:

- attribution prevents every failure from becoming a harness edit;
- local validation catches patches that solve one case but break others;
- model alignment can remove bottlenecks that scaffold edits alone cannot fix;
- later rounds can plateau, which is evidence that more harness complexity is not automatically useful.

The failure taxonomy received **Cohen's kappa 0.77** agreement in a 200-trajectory human annotation exercise. That measures the taxonomy's label consistency. It is **not** a reported HarnessCritic-versus-human attribution accuracy, so do not overstate it.

## Failure modes and limits

- The five harness areas are fixed by the authors.
- A root cause can cross areas, so a single-label diagnosis may be too simple.
- A repair can introduce another fault downstream: an attribution cascade.
- Counterfactual causes are hard to infer from the path that actually ran.
- Model fine-tuning adds significant compute and makes causal attribution of final gains harder.
- The strongest task family is math/tool use, so broader generalization is still open.

## Implementation checklist

Build:

- a normalized trace store;
- a typed diagnosis schema;
- an abstain label for non-harness faults;
- source-location links in each diagnosis;
- local regression suites;
- a versioned registry with parent hashes;
- rollback support;
- a separate successful-trajectory dataset;
- a model-training boundary that is logged independently from harness changes.

Never merge "model changed" and "harness changed" into one unlabeled experiment state.

## What RHEvolution should take from it

Take the critic discipline and rollback system. RHEvolution needs the same question before every structural edit: **is the problem actually owned by this part of the harness?**

Change the fixed five-way taxonomy into a mutable ownership graph. If diagnoses repeatedly hit several different mechanisms inside one owner, split it. If two owners are almost always implicated together and cannot be validated independently, fuse them.

For a clean RHEvolution paper, keep model weights frozen in the main decomposition experiment. Co-evolution can be a later extension, otherwise it becomes difficult to show that adaptive decomposition itself caused the gain.
