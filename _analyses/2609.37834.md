## What is actually new

Mixture of Self-Improving Branches lets multiple whole-harness searches **specialize on different task subsets without human task labels**.

Each branch starts from the same harness. As search progresses, a branch claims development cases where its frontier has a clear relative advantage. Search then focuses on that branch-specific subset. At test time, a router chooses which final branch should handle each new task.

The main novelty is that **the training distribution changes with the evolving specialists**.

## Mental model

Suppose one harness branch becomes good at symbolic math and another at code repair. If both branches keep optimizing on the same mixed task set, the majority/easy tasks dominate both searches and specialization may disappear.

This method repeatedly asks:
- which cases does branch 1 solve better than branch 2?
- which cases does branch 2 solve better?
- which easy cases are solved by everyone and no longer need search budget?

That task ownership becomes the curriculum for each branch.

## Key objects and state

- **Branch:** independent harness-evolution process.
- **Frontier harnesses:** recent strong candidates inside a branch.
- **Per-task branch success:** performance of each frontier on each development case.
- **Ownership margin:** minimum relative advantage needed to claim a case.
- **Active task subset:** cases currently assigned to a branch.
- **Proposal guidance:** branch-specific lessons from accepted/rejected edits.
- **Head harness:** final selected candidate for a branch.
- **Router:** chooses a branch head at deployment.

## Specialization loop

~~~mermaid
flowchart TD
    A["Shared seed harness + shared task pool"] --> B1["Branch 1 search"]
    A --> B2["Branch 2 search"]
    B1 --> C["Evaluate branch frontiers per task"]
    B2 --> C
    C --> D["Compute relative advantage / ownership"]
    D --> E1["Assign Branch 1 its stronger cases"]
    D --> E2["Assign Branch 2 its stronger cases"]
    D --> F["Drop easy cases solved by all branches"]
    E1 --> G1["Update Branch 1 proposal guidance"]
    E2 --> G2["Update Branch 2 proposal guidance"]
    G1 --> B1
    G2 --> B2
    B1 --> H1["Final head 1"]
    B2 --> H2["Final head 2"]
    H1 --> I["Router chooses specialist at test time"]
    H2 --> I
~~~

## Step-by-step implementation

1. Clone the same seed harness into two or more branches.
2. Initially give every branch the same development set.
3. Evolve each branch independently for several steps.
4. Evaluate recent frontier candidates on the common development cases.
5. For each case, estimate which branch has a reliable relative advantage.
6. Assign that case to the stronger branch only when the margin clears a threshold.
7. Remove cases that every branch solves reliably; they no longer provide useful search signal.
8. Summarize each branch's accepted and rejected edits into proposal guidance.
9. Continue branch search on the newly owned task subsets.
10. Repeat ownership updates periodically, not necessarily every single generation.
11. Freeze a head harness from each branch.
12. Train or prompt a router to select a branch for unseen tasks.

## Experimental results

The paper studies mixed task distributions and compares against Meta-Harness-like whole-distribution search.

One useful ablation varies how often ownership is updated. In a Math/Gemini setting:
- update every **1** interval: about **62**;
- every **3**: about **56**;
- every **5**: about **53**.

More responsive ownership can therefore help when specialization changes quickly.

A component ablation reports:
- neither pruning nor optimizer-guidance adaptation: **51**;
- optimizer guidance only: **50**;
- pruning/ownership effect only: **54**;
- both: **62**.

This is important: changing the **data each branch owns** matters more than merely changing its meta-prompt.

At test time, routing reaches about **62** in one reported setting versus **58** for the best single branch chosen globally.

## What the results mean

The search objective is not fixed. The system changes which examples define each specialist.

This is a form of credit assignment at the task-distribution level:
- one branch should not be punished for cases another branch is designed to handle;
- one branch should receive more budget where it has a distinctive edge.

The downside is that routing becomes part of the final system. Specialization is only useful if unseen tasks can be assigned correctly.

## Failure modes and limits

- The main study uses only a small number of branches.
- Task ownership can oscillate when scores are noisy.
- A router can erase the gains if it picks the wrong specialist.
- Branches remain whole harnesses; internal mechanisms are not safely fused.
- Total token/search budgets can differ between branch methods and baselines.
- Easy-case pruning can hide regressions unless old tasks are replayed occasionally.

## Implementation checklist

Store a matrix:
**task × branch × candidate outcome**.

From it compute:
- ownership margin;
- task difficulty;
- branch confidence;
- "solved by all" status;
- drift since the last ownership update.

Keep a small replay sample from deactivated/easy cases to detect forgetting.

## What RHEvolution should take from it

Use **adaptive ownership** for components.

A RHEvolution component should receive more optimization budget when:
- it owns a coherent failure cluster;
- edits to it disproportionately improve those cases;
- neighboring components do not explain the same failures.

The paper still routes between full harnesses. RHEvolution should instead let specialism emerge *inside one composable harness graph*, then fuse or route components under explicit interfaces.
