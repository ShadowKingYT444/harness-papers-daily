## One line
Makes the harness *search itself* adaptive: two parallel branches each evolve whole harnesses against an evolving development subset (each branch claims the cases its frontier solves better than the other's) with branch-specific proposal guidance, then a router picks one branch's head harness per new input at deploy time.

## The problem
Meta-Harness-style search fixes the development set and the proposal policy for the whole run, channeling evolution down a single trajectory toward a local optimum: a harness that solves cases the leader misses still ranks lower overall, so its capabilities never get developed. Fixed proposal guidance also can't adapt its exploration priorities to the strengths and unresolved failures that emerge mid-search. The paper's question: can adapting each branch's development subset and proposal guidance discover complementary harnesses and improve deployed performance?

## How it works
Each branch is a separate search process with its own development subset, candidate history (stored in a local filesystem), and proposal guidance (a SKILL.md), all initialized identically; the coding proposer (Claude Opus 4.6) is shared. Per iteration, the proposer reads harness–score pairs and traces, proposes one new harness, and evaluates it on the branch's subset. Two adaptive mechanisms, with B=2 branches, N=20 iterations:
1. **Development-subset updates** (every iteration, once each branch has ≥ q=5 candidates): for each dev case, a *coverage vote* counts how many of the branch's top-q frontier harnesses solve it. Cases solved by *every* frontier harness in *every* branch are dropped from all subsets (no signal). Branch b **claims** case x when its vote exceeds every other branch's by an ownership margin Δ=2 — the case is removed from all other subsets. Each branch thus specializes in cases where it has a relative advantage, with no predefined task categories.
2. **Proposal-guidance updates** (every 5 iterations): the proposer revises each branch's SKILL.md from its local search records — which modifications worked, which repeatedly failed, which problems remain unresolved — so guidance develops distinct priorities as objectives diverge.
**Deployment**: the dev-best head per branch is kept (scores across branches aren't comparable since subsets differ), and a router is built from head-exclusive dev cases (solved by exactly one head) plus expert source code and head outputs, with its instruction optimized via GEPA. For each new problem the router selects one head before execution — no test feedback used.

## Key results
- Development-selected routed system vs Meta-Harness (relative gains): **+34.8%** on Olympiad-level math with Gemini 3 Flash (46.0→62.0), +5.2% with Claude Sonnet 4.5 (29.0→30.5), **+11.6%** on Terminal-Bench 2.0 (44.8→50.0), +3.8% on SWE-bench Lite (63.6→66.0). Splits: math 250 dev / 200 held-out; TB2 30 dev / 58 test; SWE Lite 50 dev / 250 test.
- The router matches or beats the stronger dev-selected head in 2 of 4 settings (Math–Gemini +4.0pp, TB2 +1.7pp absolute), misses by one test case in the other two, and sits 4.4–5.5pp below the oracle combined coverage — recovering 75% of branch-exclusive successes (12/18 and 18/22).
- Ablations (Math–Gemini): both adaptive components together reach 62.0% vs 51.0% with neither, 50.0% with guidance-only, 54.0% with pruning-only — **proposal adaptation alone ≈ no adaptation**; it only helps once development pruning gives branches distinct challenges. Faster subset updates win: every-iteration 62.0% > every-3 56.0% > every-5 53.0%.
- Their test-best harness pool beats Meta-Harness's test-best in 3/4 settings (ties the fourth); strikingly, the dev-selected *router* (62.0%) beats their own pool's test-best individual harness (58.0%) on Math–Gemini.
- Trajectory case study: Branch 1 developed concrete answer checks and proof-obligation routing (verification), Branch 2 free-form derivation, two-sided closure, and agreement challenges (construction) — e.g., Branch 1's checks caught a candidate answer's unnecessary restriction on a polynomial-family problem via an explicit counterexample.

## How it relates to adaptive decomposition
This paper's slogan is "make the improvement process itself adaptive," which rhymes with the user's project — but the adaptivity lives at the **search-process level, not the harness-structure level**. Branches are whole-harness search trajectories with evolving *objectives* (dev subsets) and *policies* (proposal guidance); there is no decomposition of one harness into independently-evolved components, no split of failing pieces, no fusion of working pieces, and no per-component budgets. The closest analog to fusion is the router, but it *selects* one whole harness per input rather than combining components. Two genuinely transferable insights: (1) the ownership-margin rule (claim a case when your frontier beats others' by ≥2) is a simple, concrete credit-assignment mechanism for specialization that a per-component budget allocator could borrow; (2) the ablation finding that subset/objective adaptation dominates guidance/policy adaptation (guidance-only ≈ baseline) suggests that in adaptive decomposition, *how search credit is partitioned across components* may matter more than the mutation policy itself. The paper also quietly reinforces the coupling worry RLHarness raised: complementary whole harnesses are combined by selection, never merged, so cross-component integration remains unsolved here too.

## Limits and open questions
Only 2 branches, 20 iterations, one proposer (Claude Opus 4.6), four settings — and the authors admit unequal total token usage vs baselines, so efficiency claims are constrained, plus limited repeated evaluations. The router is selection-only: branches never exchange or fuse mechanisms, so the complementary gains stop at routing. Dropping cases solved by all frontiers assumes universality means no signal, which is fine for ranking but discards any shared-hard cases that could stress-test robustness. The ablations show trajectory changes *correlate* with gains but, as the authors note, don't establish that each observed change caused its subsequent test gain. I read the full main text; the appendices (exact guidance-update prompts, token-usage tables) were not fully inspected, so prompt-level details of the SKILL.md revision are secondhand from the main text.
