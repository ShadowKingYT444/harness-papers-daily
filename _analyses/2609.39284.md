## What is actually new

EngramBench is not a harness optimizer. It is an evaluation design for asking whether an evolving skill/harness system learned a **reusable capability** rather than memorizing a solution.

Its core principle is:

> **training and test should share capability requirements but not share the concrete solution path.**

This is especially relevant for RHEvolution because a decomposed harness can look intelligent while actually storing benchmark-specific repairs.

## Mental model

Suppose training teaches:
"when an API returns stale data, invalidate cache X in repository Y."

A test project with the same API or same code path does not prove abstraction. The harness could simply reuse the old fix.

A stronger transfer test asks for a different project/API that still requires:
- diagnosing stale state;
- preserving concurrency;
- recovering safely;
- checking final behavior.

The *capability* overlaps. The *solution* does not.

## Key objects and state

- **Learning tasks:** tasks used to create skills.
- **Rich learning trajectories:** include failures and repairs.
- **Skill distillation process**
- **Frozen skill bank**
- **Bank hash/version:** proves it did not change during transfer.
- **Transfer projects:** unseen business logic, APIs, and implementations.
- **Hidden evaluator:** cannot be inspected by the agent.
- **Simulated user:** drives long development interactions.
- **CCPF:** fraction of all applicable hidden test cases passed.
- **Efficiency measures:** time/tokens as well as correctness.

## Evaluation protocol

~~~mermaid
flowchart TD
    A["Learning projects"] --> B["Collect multi-hour trajectories with mistakes + repairs"]
    B --> C["Distill reusable skill bank"]
    C --> D["Freeze + hash bank"]
    D --> E["Remove access to old workspaces / hidden tests"]
    E --> F["Run new transfer projects"]
    F --> G["Simulated user drives full development session"]
    G --> H["Hidden evaluator checks exact behavior"]
    H --> I["Report correctness + time + token efficiency"]
~~~

## Step-by-step implementation

1. Design learning tasks around several target capabilities.
2. Record complete trajectories, including failed approaches. Do not distill only success text.
3. Create a reusable skill bank.
4. Freeze and hash it before transfer.
5. Ensure transfer projects change concrete APIs, schemas, business logic, and code structure.
6. Remove old workspaces and inaccessible test artifacts.
7. Let the agent use only the frozen bank plus the new project.
8. Drive long tasks with a consistent user/evaluator protocol.
9. Hide the final evaluator.
10. Score detailed requirements, not only one pass/fail result.
11. Measure development time and token usage as well as correctness.
12. Audit any suspiciously exact transfer for solution leakage.

## Benchmark scale

The paper reports:
- about **30 learning tasks**;
- **13 unseen transfer projects**;
- roughly **48 multi-hour trajectories** in the study.

The transfer projects are designed to overlap at the capability level while avoiding direct solution overlap.

## Results that matter

The main result is nuanced:

- skill banks give only **modest last-mile correctness gains** in several settings;
- they reduce coding/development time by **more than 55%** in the reported aggregate;
- less raw historical text can still produce a strong bank.

That suggests the useful asset is not "more memory." It is compressed procedural knowledge that reduces rediscovery cost.

The benchmark therefore separates two benefits:
1. can the bank raise final correctness?
2. can it make the same capability much cheaper/faster to reproduce?

## Why this matters for harness evolution

A harness mechanism can be genuinely useful even if final pass rate barely moves, because it may:
- reduce search;
- reduce tokens;
- reach the same solution faster;
- reduce variance.

RHEvolution should therefore report transfer **efficiency** as well as score.

At the same time, the bank is frozen during EngramBench transfer. That is useful for clean measurement but different from online adaptive decomposition.

## Failure modes and limits

- Skill-bank benefits depend on distillation quality.
- The detailed study has a modest number of transfer projects.
- Repeated runs per condition are limited.
- Simulated-user behavior can shape outcomes.
- Frozen-bank transfer does not evaluate online structural adaptation.
- Capability/solution separation is a design judgment and can be imperfect.

## Implementation checklist for a RHEvolution transfer benchmark

For each training/test pair, document:
- shared abstract capability;
- changed API/schema/repository;
- why direct solution copying should fail;
- hidden evaluator boundary.

Freeze:
- final harness;
- component library;
- experience bank;
- optimizer memory;

then test on OOD projects with no further edits for the pure-generalization condition.

Run a second condition that permits adaptation if you want to measure fast transfer separately.

## What RHEvolution should take from it

Use EngramBench's anti-leakage logic to make the OOD claim credible.

RHEvolution should have two evaluations:

**Frozen transfer:** Does the learned decomposition generalize as-is?

**Adaptation transfer:** Does the decomposition let the optimizer adapt faster with a small new-task budget?

If only the second improves, the contribution is fast adaptation, not zero-shot generalization. Report that distinction clearly.
