## One line
Alternates model RL with full-harness reconstruction — jointly revising the Skill Bank, invocation protocol, and few-shot demonstrations as one atomic version from current-policy success/failure traces, so the external program never goes stale under an evolving policy.

## The problem
Terminal-verifier RL tells you whether a final answer is right, not how it should be produced — the policy must discover reusable reasoning procedures while learning to execute them ("program cold start"). A fixed skill bank goes stale: as the policy improves, old triggers/protocols/demos become mismatched. And updating skills *alone* breaks consistency — a new skill saying "check no-skip edges" while the protocol still says "compute route cost first" and demos show old one-pass behavior gives contradictory guidance.

## How it works
The harness is a versioned tuple Φ = (I, B, P, E, C): input assembly I, skill bank B, selection/execution protocol P, few-shot block E, output contract C. Only B/P/E are ever revised; I/C and the verifier stay fixed. The lifecycle is build → learn → reconstruct → learn:
1. **Harness I (Exploration–Distillation)**: turns raw task experience into the initial program Φ1 (skills, invocation protocol, demonstrations) on a fixed exploration subset with strict commit gates (candidate only committed if hard accuracy on frozen Val100 strictly improves); audited accepted traces G1 exported.
2. **Policy Learning I**: SFT on G1 + DAPO (steps 0–400) with Φ1 frozen → policy θ1 and fresh rollouts.
3. **Harness II (Post-RL Reconstruction)**: the heart of the paper — stratified sampling contrasts *comparable successes and failures from current-policy rollouts* batch by batch to find the policy's current capability boundary; ineffective skills pruned from summaries + observed usage; triggers, execution steps, invocation order revised without disturbing what works; and critically, **each candidate gets a rewritten "How-to" block and demo section matched to the new skill boundaries/order** — B/P/E committed atomically as one version. A separate task-teacher (GPT-5.6-sol) selects from proxy-executed reports; the student itself doesn't validate candidates.
4. **Policy Learning II**: DAPO resumes from the same checkpoint/optimizer state (steps 400–600) with Φ2 frozen.
The shared reward is R = 0.05·rformat + 0.25·rpartial + 0.70·rall with difficulty-weighted advantages.

## Key results
- MetroMap-lite / TravelMap-lite accuracy: 16.25%/27.50% → 62.00%/50.00%; Fee-VL / Cancel-VL macro-F1: 37.13%/45.50% → 65.81%/65.51%.
- All four tasks reach their best result only after reconstruction + DAPO II; matched ablations show reconstruction beats spending the same extra RL budget under the old harness, and directly swapping the harness *without* policy adaptation doesn't always help.
- A worked example: an adjacency-only rule allowed a route shortcut skipping Heng Fa Chuen station; failure traces motivated a "No-Skip Edge Guard" in Φ2, which DAPO II then internalized.

## How it relates to adaptive decomposition
This is the most interesting **counterpoint** paper in the set. Its explicit thesis is *anti*-decomposition at the evolution level: "the update unit cannot be the Skill Bank alone" — skills, protocols, and demos are interdependent and must be revised atomically as one version, because piecemeal updates create mutually inconsistent guidance. Adaptive decomposition would say: give subproblems independent search budgets and evolve components in parallel. RLHarness says: keep the program consistent or the policy can't follow it — hence version-matched demos for every skill change, and a control plane (Γ) that commits complete versions atomically. The tension is real and worth facing head-on in any paper: adaptive decomposition needs an answer to RLHarness's inconsistency objection — e.g., consistency checks at split/fuse time, or version-aligned testing of subproblem boundaries. Note RLHarness also evolves *harness and policy* jointly, while adaptive decomposition is harness-side only.

## Limits and open questions
Reconstruction is expensive: a full task-teacher model (GPT-5.6-sol) selects from proxy-executed candidate reports, and the evaluation is narrow — four tasks, two from internal Didi data (Fee-VL, Cancel-VL) that can't be independently checked. The "same RL budget" ablations are well-designed, but the baselines are mostly internal ablations, not external harness optimizers. I'd probe how task-specific the reconstructed prompt really is (the paper's own RQ4) and whether a cheaper reconstruction (no GPT-5.6-sol teacher) preserves the gains — if not, the method is out of reach for most labs.
