## What is actually new

RLHarness argues that some harness parts should **not** be evolved independently.

It couples three artifacts:
- a procedural skill bank;
- the protocol that says when/how to invoke those skills;
- examples that demonstrate the procedure.

After reinforcement learning changes the model, the old skills and invocation protocol can become stale. RLHarness therefore alternates policy training with **atomic harness reconstruction** so the coupled artifacts stay consistent.

The important novelty for RHEvolution is the counterexample to naive decomposition: sometimes the correct operation is **fuse these owners and version them together**.

## Mental model

Suppose the harness has a skill named "inspect evidence before answering." The model learns through RL and becomes better at inspection. If you only rewrite the skill description but leave old triggers and demonstrations unchanged, the harness can become internally inconsistent.

RLHarness rebuilds the related artifacts as one version. The model then trains again under that updated scaffold.

This creates a feedback loop:
policy changes → old harness boundary becomes suboptimal → reconstruct harness → policy changes again.

## Key objects and state

- **Skill bank:** reusable procedures.
- **Invocation protocol:** rules for selecting and sequencing skills.
- **Few-shot examples / How-to block:** demonstrations aligned to the current skills.
- **Policy checkpoint:** current model weights.
- **Current success/failure traces**
- **Reconstruction candidate:** matched set of skills + protocol + examples.
- **Validation set:** candidate must improve before commit.
- **Version ID:** all coupled artifacts share one version.

## Co-evolution loop

~~~mermaid
flowchart TD
    A["Initial skill bank + protocol + examples"] --> B["RL stage 1"]
    B --> C["Collect current success/failure traces"]
    C --> D["Diagnose changed policy boundary"]
    D --> E["Reconstruct skills"]
    E --> F["Rewrite invocation protocol"]
    F --> G["Rewrite examples to match"]
    G --> H["Treat all three as one candidate version"]
    H --> I["Validate on held-out tasks"]
    I --> J{"Strict gain?"}
    J -- "No" --> K["Keep previous harness version"]
    J -- "Yes" --> L["Commit matched harness version"]
    L --> M["RL stage 2 from current checkpoint"]
    M --> C
~~~

## Step-by-step implementation

1. Build an initial harness from a skill bank, invocation policy, and examples.
2. Train the policy with RL while this harness is frozen.
3. Save current successes and failures after the policy has moved.
4. Compare them with earlier traces. Find procedures that are now redundant, missing, or triggered at the wrong time.
5. Rewrite the skill bank.
6. In the same reconstruction transaction, rewrite the invocation protocol.
7. Rewrite examples so they demonstrate the new skill structure rather than an old version.
8. Reject candidate versions with broken references or inconsistent names before running expensive tasks.
9. Evaluate on a fixed validation set. The paper uses a strict improvement gate.
10. If accepted, give every linked artifact the same version.
11. Continue RL from the existing policy checkpoint under the new harness.
12. For training data, keep the producing harness version attached to every trajectory.

## Experimental details

The paper uses long-horizon multimodal reasoning tasks and a two-stage training design.

One reported setup:
- explores with a fixed number of examples split into batches;
- validates each reconstruction on a held-out validation set;
- accepts only a strict accuracy gain;
- then runs another RL stage.

The authors also study **version-aligned reasoning distillation**: training examples are paired with the harness version that produced them instead of using generic teacher traces detached from the active scaffold.

## Results that matter

The best results require both reconstruction **and** the second RL stage.

Reported analyses include:
- the reconstructed harness followed by policy adaptation gives stronger gains than simply changing the harness and freezing the policy;
- version-aligned reasoning distillation improves average performance by about **5.5 points** over a free teacher-SFT alternative in the reported comparison;
- one RL configuration contributes a large average gain, while additional difficulty weighting adds a smaller but positive improvement.

The exact benchmark totals are less important for RHEvolution than the interaction: the harness update changes what the policy needs to learn, and the policy update changes which harness procedures remain useful.

## What the ablations mean

The paper is evidence against treating every module boundary as independent.

If skill code changes but:
- trigger rules still refer to an old skill;
- examples demonstrate old sequencing;
- policy training data came from a different harness version;

then local components can each look reasonable but the combined system is incoherent.

Version consistency is therefore a first-class variable.

## Failure modes and limits

- The task domain is relatively narrow.
- Reconstruction uses a strong teacher, increasing cost.
- Model weights change, so final gains are not harness-only.
- The coupled group is human-specified; the paper does not learn which artifacts need atomic updates.
- Freezing too many things into one atomic group can recreate the monolithic credit-assignment problem.

## Implementation checklist

Represent dependencies explicitly:
- skill ID;
- protocol rules that call it;
- examples that reference it;
- training traces produced with it.

Use an interface/compatibility hash. A candidate cannot promote if one linked artifact still targets the old version.

Keep policy checkpoints and harness versions separate but cross-referenced.

## What RHEvolution should take from it

RHEvolution needs **dependency-aware decomposition**, not maximal decomposition.

Use coupling evidence to decide whether owners can evolve separately:
- if two nodes change independently and global validation stays stable, keep them split;
- if edits repeatedly require synchronized changes, fuse them into one evolution unit;
- allow later splitting if coupling decreases.

This paper gives the conceptual reason for a fuse operator. PluginRSI shows why local mutation helps; RLHarness shows why some local mutations must be grouped.
