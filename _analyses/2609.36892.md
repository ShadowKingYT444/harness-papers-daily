## What is actually new

This paper does not propose another harness optimizer. It gives a useful **error decomposition** for understanding why harness evolution stops working.

It separates three causes:

1. **Approximation error:** the current harness design class cannot express the needed behavior.
2. **Generalization error:** the harness fits observed feedback but does not transfer.
3. **Optimization error:** the search/update method fails to find the best harness available in the current class.

That distinction matters because each failure needs a different intervention.

## Mental model

Suppose RHEvolution plateaus.

A naive response is "split the component." But there are at least three possibilities:

- The current component truly cannot represent the needed mechanism. A structural change may help.
- The component is already too flexible for the small amount of evidence. Splitting may make generalization worse.
- The optimizer keeps making bad edits. A new decomposition will not fix the search algorithm.

This paper gives a language for telling those cases apart.

## Key concepts

- **Context harness:** mainly changes information shown to the model.
- **Control harness:** can also constrain, verify, or rewrite actions.
- **Approximation error:** best possible behavior under current architecture is still insufficient.
- **Generalization error:** learned rules are weakly supported or too specific.
- **Optimization error:** update process converges to a poor solution.
- **Memory coverage:** how many behaviors/rules are represented.
- **Memory estimation error:** how uncertain each stored rule is with limited evidence.
- **Biased fixed point:** repeated updates settle into a systematically wrong policy.

## Diagnostic loop

~~~mermaid
flowchart TD
    A["Observed harness plateau"] --> B{"Can current architecture express the required control?"}
    B -- "No" --> C["Approximation problem: change architecture / add control"]
    B -- "Yes" --> D{"Does performance hold on unseen preferences/tasks?"}
    D -- "No" --> E["Generalization problem: simplify / get more evidence"]
    D -- "Yes" --> F{"Does another search/update rule find a better harness?"}
    F -- "Yes" --> G["Optimization problem: change search algorithm"]
    F -- "No" --> H["Likely near current class limit"]
~~~

## Core theoretical ideas

### 1. Context is not always enough

Some requirements can be satisfied by adding the right fact or instruction to context. Others require external control.

For example:
- "Prefer dark mode" can be context.
- "Never spend over a limit without confirmation" is safer as executable control.

If the frozen model will sometimes ignore an instruction, no amount of better memory guarantees action compliance. A control harness can check or block the action.

### 2. Bigger memory can generalize worse

With a fixed amount of user feedback, adding more independent rules means less evidence per rule.

At first, a larger memory improves coverage. Past a point, estimation noise dominates. The paper predicts and observes a U-shaped tradeoff: too little memory cannot represent preferences; too much memory contains weakly supported rules.

### 3. More update rounds do not remove update bias

If the update rule is biased, repeated self-improvement can converge to the wrong fixed point. Iterating harder is not the same as optimizing better.

## Experimental setup

The experiments use **AppWorld-P**, where an agent must follow personal preferences during tool-use tasks.

The setup is useful because the preference rules range from simple stated facts to persistent action constraints. This lets the authors compare context-only and control-style mechanisms.

## Results that matter

The experiments include cases where simple explicit context nearly removes violations:
- one private-note preference drops from near **1.0 violation rate to about 0.07**;
- one SMS sign-off preference drops from near **1.0 to 0**.

Harder preferences remain poorly handled by context alone:
- some checksum, payment, or habitual-action constraints retain high violation rates.

The paper also reports the predicted memory-size tradeoff: adding more stored rules can first help and then hurt as evidence per rule becomes too thin.

## What these results mean

The architecture must match the kind of requirement.

This is directly relevant to harness evolution: a plateau can be caused by **representation capacity**, not only bad parameters. But adding structure has a statistical cost. More owners/components require more evidence to estimate their value.

That creates the exact tradeoff RHEvolution must manage:
- split to reduce approximation error and improve credit assignment;
- do not split so far that each child receives too little evidence.

## Failure modes and limits

- The theory uses simplified learning assumptions.
- AppWorld-P is a preference-compliance domain, not generic coding-agent evolution.
- "Context" and "control" are broad categories.
- The paper diagnoses structural limits but does not give an adaptive decomposition algorithm.
- Real harnesses have interacting modules, so error terms are not perfectly separable.

## Implementation checklist for RHEvolution diagnostics

For each owner track:
- unresolved error types;
- evidence count;
- held-out transfer;
- alternative candidate performance;
- whether failures require executable control or only better information.

Before splitting, ask:
1. Does the current owner mix behaviors that require different mechanisms?
2. Is there enough evidence to estimate each proposed child?
3. Is the search algorithm already failing on simple local improvements?
4. Would a control mechanism solve a problem that prompt/context edits cannot?

## What RHEvolution should take from it

Use approximation/generalization/optimization error as the **decision framework for structural operators**.

- High approximation error → split, create a new component, or expand the edit class.
- High generalization error → prune, fuse, regularize, or collect more evidence.
- High optimization error → change proposer/search/selection; do not blame the decomposition.

This gives RHEvolution a principled reason for *when not to recurse*.
