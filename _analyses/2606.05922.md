## What is actually new

RHO asks a harder question than normal harness optimization: **how can a harness improve when deployment history has no ground-truth answers or external verifier?**

Its answer is to create a training signal from the agent's own behavior. It selects a diverse subset of old tasks, repeats them several times, uses disagreement and self-checking to find unreliable behavior, proposes full-harness changes, and uses pairwise self-preference to choose among candidates.

The novelty is therefore not "reflection." It is an **unlabeled outer loop for whole-harness optimization**.

## Mental model

Suppose an agent completed 10,000 real tasks, but nobody labeled which final answers were correct. That history still contains structure. Some tasks produce the same confident result every time. Other tasks produce very different approaches and answers. Some traces contain their own signs of inconsistency.

RHO treats these patterns as weak supervision. It spends its optimization budget on a small diverse coreset, repeats each case, and asks: "where is the current harness unstable or internally inconsistent?" Those diagnoses become proposed harness edits.

The final weakness is obvious: the system also judges its own candidates. The loop therefore removes dependence on a labeled benchmark but replaces it with dependence on **self-preference quality**.

## Key objects and state

- **Historical trajectory pool:** past task executions.
- **Coreset:** a small diverse subset of that history.
- **DPP selector:** chooses cases that are both useful and non-redundant.
- **Grouped rollouts:** several fresh executions of the same task.
- **Self-validation signal:** evidence inside a trace that the result may be wrong.
- **Self-consistency signal:** agreement or disagreement across repeated traces.
- **Diagnosis:** a natural-language account of recurring failure behavior.
- **Harness candidate:** a proposed change to prompts, workflow code, program parameters, tools, skills, or memory.
- **Pairwise preference:** the model compares two resulting behaviors and chooses one.

## Optimization loop

~~~mermaid
flowchart TD
    A["Large unlabeled trajectory history"] --> B["Score task difficulty + embed descriptions"]
    B --> C["DPP selects a diverse coreset"]
    C --> D["Run each coreset task G times"]
    D --> E["Self-validate each trace"]
    D --> F["Compare traces for disagreement"]
    E --> G["Build failure diagnosis"]
    F --> G
    G --> H["Generate N whole-harness candidates"]
    H --> I["Re-run coreset with each candidate"]
    I --> J["Pairwise self-preference against baseline / rivals"]
    J --> K{"Clear preference improvement?"}
    K -- "No" --> L["Keep old harness"]
    K -- "Yes" --> M["Select new harness"]
~~~

## Step-by-step implementation

1. Collect deployment trajectories in one normalized schema: task text, messages, tool calls, observations, timing, and final response.
2. Produce a compact description and difficulty estimate for each historical task.
3. Embed the descriptions and use a diversity selector such as a determinantal point process. The purpose is to avoid spending most of the budget on near-duplicate failures.
4. Re-run each selected task several times with the current harness.
5. Ask the model to self-check each trace. Separately measure how consistent the repeated runs are.
6. Convert these signals into a diagnosis that points to recurring behavior, not only one bad final answer.
7. Give the diagnosis, relevant traces, and current repository to the optimizer. Let it produce several harness candidates.
8. RHO's edit surface is broad: prompts, program settings, workflow code, skills, tools, and memory can all change.
9. Run the same coreset with each candidate.
10. Compare candidate outputs pairwise. The judge explains why one trajectory is preferred.
11. Aggregate preferences and promote a candidate only when its preference signal is positive.
12. Freeze the chosen harness before external benchmark evaluation.

## Why DPP matters

A DPP is only a diversity sampler. You can understand it without the matrix math:

- if two tasks are almost the same, keeping both adds little information;
- if two tasks expose different failure modes, keeping both covers more of the behavioral space;
- the selector therefore tries to maximize coverage under a fixed evaluation budget.

For RHO this is important because every repeated rollout is expensive. The coreset is the method's main cost-control device.

## Experimental setup

The paper studies software engineering plus other technical and knowledge-work tasks. The key claim is evaluated under **no external grading inside the optimization round**.

The optimizer sees its own traces and self-generated signals. External benchmark scores are used after optimization to measure whether the new harness actually improved.

This distinction matters. The method does not prove that labels are unnecessary for *evaluation*. It shows that labels are not required as an input to this particular optimization loop.

## Results that matter

- On **SWE-Bench Pro**, one RHO round raises the reported pass rate from **59% to 78%** without external grading during that optimization round.
- The paper reports gains across software engineering, technical work, and knowledge work.
- The optimized harness develops targeted tools and skills for recurring problems rather than only growing a memory log.
- The authors report that retrospective optimization can reach competitive gains with much less external evaluation than validation-driven whole-harness evolution.

The headline result is important because the selection signal is generated from behavior rather than an answer key.

## Ablations and interpretation

The paper's diagnosis stages matter beyond simply storing more experiences. Repeated execution gives information that a single trace cannot provide:

- consistent repeated failure points toward a systematic weakness;
- disagreement points toward instability;
- internal self-check failures can reveal errors even when all repetitions look superficially similar.

The coreset also matters for efficiency because naive "read all history" search scales badly.

However, preference selection is not a causal verifier. A fluent, confident candidate can win a comparison and still be wrong.

## Failure modes and limits

- **Self-preference bias:** the same model family can favor its own style or errors.
- **Bias compounds:** repeated optimization can turn a small judge bias into a stable harness rule.
- **Whole-harness edits:** credit assignment is still coarse. A good score does not identify which part caused it.
- **One-round evidence is stronger than long-run evidence:** repeated self-improvement needs stability tests.
- **Coreset dependence:** a diverse coreset can still omit rare but important failure modes.

## Implementation checklist

You need:

- normalized historical traces;
- semantic embeddings or another diversity representation;
- a coreset selector;
- grouped repeated rollout support;
- separate self-validation and cross-run consistency prompts;
- an optimizer with repository access;
- a pairwise preference evaluator;
- a hard external held-out evaluation that the optimizer cannot see.

Log the judge model and prompt with every preference. Otherwise you cannot later determine whether a gain came from a harness change or a judge-policy change.

## What RHEvolution should take from it

RHO is useful for **verifier-light** RHEvolution. Its strongest transferable pieces are:

1. select a diverse coreset instead of reading every trace;
2. use repeated rollouts to estimate instability;
3. turn raw traces into compact diagnostic artifacts;
4. keep self-preference as a proposal or screening signal.

RHEvolution should change the edit unit. Instead of one full harness candidate, diagnoses should map onto owned components or subgraphs. Self-preference should not be the final promotion gate. Use independent execution checks or held-out outcomes whenever available.
