## One line
Certified evolutionary search for CPU→GPU porting: instead of pasting failure feedback into prompts (which later candidates happily ignore), it converts failures into **validated, enforced restrictions** — certificates — so conflicting code choices get rejected, backtracked, or surgically repaired while compatible edits survive.

## The problem
Evolutionary program search (FunSearch/AlphaEvolve-style) can port and accelerate legacy scientific code, but there's a specific memory failure: repair feedback placed in the prompt is only advisory. The LLM nods, then a later candidate makes the *same* conflicting choice again — e.g., re-introducing a data-layout assumption that violates a GPU safety requirement. The motivation is scaling: porting the whole Geant4 particle-simulation toolkit to GPU is a "herculean task," so the system must reliably optimize code against formal, numerical, physical, *and* GPU-safety requirements without an expert babysitting every proposal.

## How it works
CDES (Certificate-Driven Evolutionary Search) wraps an AlphaEvolve-style core (implemented on ShinkaEvolve) with a certificate control layer:

1. **Standard loop.** Seed program → parent selection → mutator LLM proposes code *or execution settings* (both are evolvable) → evaluation harness scores programs and routes failures to a certificate database.
2. **Detection and certification.** When a candidate violates a requirement, a conflict checker + analyzer reviews it using stored certificates and symbolic checks of dependencies between code components. It writes a **certificate**: the conflicting choices, the violated requirement, plus the supporting assumptions and checker evidence. Crucially, a proposed restriction is **validated before it's allowed to block anything** — certificates are checked, not just asserted.
3. **Enforcement (the key move).** Unlike prompt feedback, validated restrictions are *enforced by control logic* even when the LLM repeats a conflicting proposal. The mechanism is explicitly modeled on CDCL SAT solvers: conflict-driven clause learning learns restrictions from conflicts and backjumps to earlier decisions; CDES similarly **rejects** conflicting combinations, **backtracks** to earlier decisions, **restarts**, or performs **targeted repair** that preserves the candidate's compatible edits while fixing only the conflicting choices. An evaluator LLM selects and orders the check tools, but a fixed policy mandates the checks — LLM-modulo style.
4. **The evaluation harness** (separate from the search loop) is unusually strong: Lean-verified contracts (e.g., GPU work-assignment proofs that each input is processed exactly once with its random-sequence ID intact, with verified rules compiled into restricted code generation), CBMC array-bounds checks, differential tests against the reference within numerical tolerances, physics checks (conservation laws, valid ranges), Compute Sanitizer for GPU memory/sync errors, statistical distribution tests, and Nsight Compute profiling. Each result is hashed to the exact candidate source. Validation suites on fresh workloads (different sizes, new RNG streams, boundary inputs) are **withheld from the search** — used to score, never to guide.

The "self-improving" claim: no retraining, no weight access — the LLM is a frozen API model (GPT-5.6-Sol in the main runs). Improvement comes from the *accumulated certificates changing which future modifications are permitted*. The certificate database is the memory; the restriction set is what learns.

## Key results
CPU→GPU porting of two Geant4 functions (Compton scattering; Fermi nuclear fragmentation), ~250k inputs on a 10 GB partition of an NVIDIA H100, model-call cost **under $10**:
- **13.78×** (Compton) and **23.54×** (Fermi) function-level speedups over CPU code, including data conversion and transfers.
- For Compton, generated GPU code beats the expert Celeritas implementation by **14.9%** GPU throughput (3.0% lower execution time incl. transfers); a human–AI **hybrid** (Celeritas energy selection + generated direction/output code) beats Celeritas by **16.1%** — complementary improvements.
- Ablation (Qwen3-Coder-Plus): certificate feedback raises the fraction of proposals passing correctness checks from **55% → 90%**; proposals also gaining >10% throughput from 50% → 80%; best throughput gain on *withheld* inputs 66.5% → 68.6%; cost per passing proposal down **10.7%**. (Without certificates the search still finds useful candidates at lower total API cost — certificates improve yield, not just correctness.)
- One number I could not verify: the ablation table's "passing with throughput gain > 20%" row was cut off in my text extraction (values 30% vs 35% visible but column alignment uncertain) — treated as not confirmed.

## How it relates to adaptive decomposition
No agent-discovered decomposition here. The "components" are human-chosen: two Geant4 functions selected by the authors, and the paper explicitly **assumes** functions can be optimized independently ("for this approach to scale to the entire codebase, we assume that selected functions can be optimized independently") — an axiom, not a discovery. The closest thing to fusion is the Celeritas hybrid, which was also assembled by the researchers. What *is* evolvable is the constraint structure: certificates accumulate restrictions that reshape the allowed edit space — a fixed action set (mutate code/settings) with a *growing, enforced rulebook*. There's no per-component search budget, no splitting of failing components further, no revert-to-monolith. Still, CDES is the strongest "constraint-as-memory" mechanism of the batch: the enforcement distinction (rejection/backtracking/targeted repair preserving compatible edits) is the part most worth stealing, since adaptive decomposition also needs a way to make *structural* decisions stick — e.g., "these two subproblems must not share state" should be enforced, not suggested in a prompt.

## Limits and open questions
Proof-of-concept on **two functions**, not the codebase — function-level gains are measured, full-simulation gains explicitly left to future work, and the independence assumption is untested at scale (Geant4 functions are not always independent; shared state could break it). The correctness guarantees are per-contract and per-fragment, not whole-program; the paper is upfront that acceptance means "passing required checks within stated domains," not equivalence. A certificate is only as good as its validation: over-broad restrictions could prune the search space too aggressively (the ablation shows certificates help on these functions, but "how the cost and correctness benefits vary across functions and optimization difficulty" is listed as future work). What I'd probe next: conflict *explosion* — as certificates accumulate over a long run on a large codebase, does restriction-checking stay cheap, and is there a mechanism to retire stale restrictions? Also whether the LLM ever learns to *route around* restrictions via novel-but-equivalent code choices that violate the spirit but not the letter — the targeted-repair loop preserves compatible edits, but nothing measures gaming of the checker.
