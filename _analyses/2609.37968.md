## What is actually new

SelfSearch removes **downstream benchmark reward from the search loop**. Each generation improves the agent by reading records of earlier self-improvement episodes, editing its own repository, locally verifying the edit, and passing that experience to the next generation.

The key novelty is that the **improver itself evolves through accumulated self-improvement experience**. The downstream benchmark is used only after checkpoints are frozen.

## Mental model

A normal evolutionary agent loop asks: "Which child got the best benchmark score?" SelfSearch asks: "What did earlier attempts at improving myself teach me about how to make the next improvement?"

The episode record becomes the training signal. It contains:
- what the previous agent tried to change;
- why it tried it;
- what tools/tests it ran;
- what code changed;
- what local verification said.

Two lineages run in parallel with different search directions. They can read each other's recent episode records. This creates cross-pollination without using benchmark score as the parent-selection reward.

## Key objects and state

- **Editable repository:** instructions, tools, policies, orchestration; model weights are fixed.
- **Self-improvement episode:** one repository-editing round.
- **Episode record:** reasoning, tool calls, changes, verification, and outcome.
- **Lineage:** sequence of descendant agents.
- **Search direction:** high-level bias such as capability or adaptation.
- **Cross-lineage memory:** recent episode records shared between branches.
- **Frozen checkpoint:** agent version evaluated only after search.

## Search loop

~~~mermaid
flowchart TD
    A["Agent repository at generation k"] --> B["Read recent self-improvement episode records"]
    B --> C["Apply lineage search direction"]
    C --> D["Agent edits its own repository"]
    D --> E["Run local tests / verification"]
    E --> F["Create episode record"]
    F --> G["Commit descendant agent k+1"]
    G --> H["Share recent record with both lineages"]
    H --> B
    G --> I["Freeze selected checkpoints"]
    I --> J["Only now run downstream benchmarks"]
~~~

## Step-by-step implementation

1. Define the mutable repository surface. Keep model weights and benchmark evaluator outside it.
2. Give the current agent a fixed self-improvement instruction plus a high-level search direction.
3. Provide a small number of previous episode records, not a giant raw history.
4. Let the agent inspect its repository, edit files, and run local checks.
5. Require the agent to leave the repository in a runnable state.
6. Save the complete improvement episode as an immutable record.
7. Create the next generation from that repository.
8. Run at least two lineages with different search biases.
9. Let each lineage read recent records from the other branch so useful ideas can cross.
10. Do **not** use downstream benchmark score to steer each edit.
11. After a fixed number of generations, freeze checkpoints and evaluate them externally.
12. Compare both final score and search cost.

## Experimental setup

The paper runs roughly **10 generations** of self-improvement and evaluates frozen descendants on:

- SWE-bench Verified;
- a multilingual coding benchmark;
- Terminal-Bench 2.1.

The self-improver and downstream task model configurations vary by experiment. The important control is that downstream evaluation is outside the search signal.

## Results that matter

Representative reported results:

| Setting | Seed | Evolved | Main point |
|---|---:|---:|---|
| GPT setting, SWE-bench Verified | 75.0% | **77.5%** best branch | Reward-free search can still improve. |
| DeepSeek setting, SWE-bench Verified | 81.7% | **86.7%** | Both lineages reach higher solve rate. |
| GPT setting, multilingual | 53.3% | **60.0%** | Improvement transfers beyond one coding distribution. |
| DeepSeek adaptive branch, multilingual | 68.3% | **73.3%** | Search direction matters. |
| GPT setting, Terminal-Bench 2.1 | 43.8% | **55.1%** | Large long-horizon gain. |
| DeepSeek setting, Terminal-Bench 2.1 | 65.2% | **73.0%** best branch | Improvement also appears from a stronger seed. |

The paper also reports lower task cost in several evolved agents. One public comparison reports a searched harness around **82% on Terminal-Bench 2.1** at only a few dollars of search cost.

## Ablations: what actually helps

Two pieces matter:

**Previous episode records.** Removing or weakening this history reduces the benefit of later generations. The agent needs evidence about earlier self-edits, not only the current repository.

**Evolving improver.** A fixed improvement policy is weaker than letting later generations inherit the consequences of earlier changes.

Cross-lineage sharing is useful because the two search directions discover different mechanisms.

## What this result does not prove

Reward-free does not mean evidence-free. The agent still runs local verification, repository tests, and receives a human-written self-improvement objective.

Also, the main paper reports one realized evolutionary chain per major condition rather than many fully independent searches. Search stability is therefore less established than checkpoint performance.

## Failure modes and limits

- A lineage can drift because no benchmark reward corrects search direction.
- Local tests can be gamed or incomplete.
- Whole-repository edits still have weak internal credit assignment.
- Episode records can become stale after large architectural changes.
- Cross-pollination can spread a bad idea between lineages.
- One successful chain can overstate repeatability.

## Implementation checklist

Keep an append-only episode store with:
- parent commit;
- search direction;
- files inspected;
- files changed;
- test commands;
- verification results;
- self-improvement rationale;
- child commit.

Keep downstream benchmark credentials and hidden tests outside the mutable repo.

## What RHEvolution should take from it

Use **episode records as optimizer memory**. They are cleaner than dumping every raw trace into the next proposer.

But change the search object. RHEvolution should attach each episode to a component/owner or structural operation:
- edit owner;
- split owner;
- fuse owners;
- reassign source;
- rollback.

Then episode history can answer "what kinds of edits worked for this owner?" rather than only "what did the previous whole-agent generation try?"
