## One line
Optimizes agent skills as text by retrieving section-level procedural knowledge from an external corpus (GitSkills) and adapting it to the target harness's vocabulary — beating retrieval-free optimizers (TextGrad, GEPA, SkillOpt, WikiSkill) on all four benchmarks with both model backbones, at lower cost.

## The problem
Millions of agent skills are publicly shared, but existing skill optimizers (SkillOpt, WikiSkill, TextGrad, GEPA) only refine from the agent's own costly rollouts, ignoring all that accumulated knowledge. Direct reuse doesn't work either: on SpreadsheetBench, 92.9% of retrieved skills come from a *different* harness, and a SkillRouter-style no-adaptation baseline sometimes underperforms running with no skill at all. The mismatch is both domain and harness: retrieved skills reference tools, commands, and objects that don't exist in the target environment.

## How it works
RASO has two stages sharing one retrieval+adaptation pipeline:
1. **Skill retrieval (section-level)**: skill documents are split at headings; BM25 retrieves top-K=5 sections per query. Sections beat whole documents on signal-to-noise because a document's overall objective may match while its procedures don't.
2. **Cross-Harness Adaptation**: an adaptation agent turns retrieved sections into concise "lessons" following three rules — strip domain-specific nouns and procedures with no target-harness counterpart, address only the target requirement, and preserve tool/parameter claims only when corroborated by the target harness description. Lessons come out in the target's objects, commands, and units.
- **RASI (initialization, zero rollouts)**: from the task + harness descriptions, a query agent generates requirement-query pairs (e.g., "multi-turn budget management"), retrieves + adapts, and a skill-initializer weaves the lessons into the initial skill s0.
- **RASU (iterative update)**: runs rollouts with the current skill, a gradient agent extracts failure modes + textual gradients, queries the corpus for fixes, adapts, and an updater proposes st+1 — accepted only if it beats st on validation.
Setup details: task and harness descriptions are generated once by a codex agent reading the benchmark's harness code (never revised after seeing test performance); a per-benchmark blocklist removes whole GitHub repos targeting the eval benchmarks from the corpus, repo-level to catch benchmark-specific procedures that don't name the benchmark.

## Key results
- **Initialization (0 rollouts)**: RASI beats retrieval-free init (RFSI) on both backbones — with GPT-5.6-Luna, +5.63 on OfficeQA (45.74 vs 40.11), +4.77 SpreadsheetBench, +3.24 ALFWorld, +1.17 WebShop; larger margins on Qwen-3.5-9B (up to +10.73 on WebShop).
- **Full RASO vs strongest baselines**: GPT-5.6-Luna: +3.49 OfficeQA (49.03 vs SkillOpt 45.54), +6.31 SpreadsheetBench (63.33 vs 57.02), +1.49 ALFWorld, +1.07 WebShop. Qwen-3.5-9B: +4.85/+1.79/+7.47/+11.30 over best competing method. Under fixed RASI init, RASU still beats all update methods (Tables 6–8).
- **Ablations**: RASI and RASU contribute complementary gains (+8.33 OfficeQA / +11.66 Spreadsheet over fully retrieval-free baseline). Cross-Harness Adaptation alone is worth +3.88/+7.74 points in RASI and +2.33/+5.47 in RASU — without it, adapted-free retrieval behaves like SkillRouter. K=5 is the sweet spot (K=10 degrades); even 1% of the corpus beats no retrieval.
- **Cost**: at matched rollout budgets, RASO is cheapest on 3 of 4 benchmarks, cutting TextGrad's API cost 42–75% (WebShop: $10.28 vs $41.03).
- **Qualitative**: the headline example adapts an empty-group rule from a satellite-imagery/numpy skill into spreadsheet openpyxl code that correctly leaves department B's cell blank instead of shifting C's value into it.

## How it relates to adaptive decomposition
This is skill optimization *within* a fixed harness, not harness-structure evolution: the model M and harness h are both frozen and the only decision variable is the textual skill s. So no component is split, fused, re-budgeted, or discovered — the decomposition is "one monolithic skill document plus external retrieval," designed by the authors. That said, two ideas rhyme with adaptive decomposition: (1) section-level retrieval treats procedural knowledge as modular, composable units — atomized like PluginRSI's plugins, though the atoms are corpus sections rather than evolvable harness components; (2) Cross-Harness Adaptation is genuinely about portability of mechanisms across harness structures, which is the prerequisite operation for any system that wants to move learned mechanisms between decompositions. It's a knowledge-accumulation paper, not a structural-evolution paper — useful plumbing for the library half of PluginRSI-style systems, irrelevant to the split/fuse half.

## Limits and open questions
The skill corpus (GitSkills) is public-repo text of unknown quality — the paper controls for benchmark leakage with a blocklist but says nothing about whether retrieved sections contain wrong or outdated procedures, and the adaptation agent's third rule (only trust corpus claims corroborated by the harness description) is the only guard. Retrieval is BM25 over headings-split sections, a deliberately simple retriever; the paper doesn't test whether a stronger retriever would change the story. The per-component ablation shows adaptation matters, but there's no analysis of *what* gets adapted — is it mostly surface vocabulary mapping or real procedural transfer? The cost comparison holds rollouts fixed across methods, which is fair, but GEPA/SkillOpt's extra rollouts exist because their acceptance logic needs them; a wall-clock comparison might narrow the gap. And all four benchmarks are single-skill, single-harness tasks — nothing here tests whether retrieval helps when the optimization target is a *composition* of skills or a multi-component harness.
