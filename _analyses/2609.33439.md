## What is actually new

Raven is a large "harness of harnesses" system. Its core idea is to treat each model-plus-harness pair as a composable specialist, then use a host agent to decompose a user goal into a dependency graph, route subtasks to specialists, and preserve experience across tasks.

For RHEvolution, the most relevant part is its **harness self-evolution pipeline**:
- failure evidence becomes a repair hypothesis;
- patches must prove they activated;
- parent and child are compared on matched tasks;
- diverse successful variants enter a gene bank;
- later search can recombine them.

The deeper novelty is that Raven uses graph composition for *task execution* but keeps most harness-evolution boundaries human-defined. That gap is exactly where RHEvolution sits.

## Mental model

Raven has two levels.

**Level 1: solve a complex job**
A Host Agent turns a user goal into a task DAG. Nodes can run different specialist agents. Edges say which outputs another node needs.

**Level 2: improve specialists**
When a specialist fails, Raven can evolve its harness and store useful variants in an archive. The system does not need one universal harness for all domains.

The result is closer to an ecosystem than one agent loop.

## Key objects and state

- **Host Agent:** decomposes goals and coordinates specialists.
- **Task DAG:** dependency graph of subtasks.
- **Specialist agent:** executable model + harness pair.
- **Host archive / EverOS:** persistent task and experience memory.
- **Skill Forge:** converts experience into reusable procedures.
- **Repair hypothesis:** claimed cause plus expected behavioral change.
- **Activation predicate:** evidence that the patch actually executed.
- **Paired-gain test:** candidate and parent run on matched cases.
- **Gene bank:** quality-diversity archive of useful harness variants.
- **Recombination:** creates candidates from archived mechanisms.

## System and evolution loop

~~~mermaid
flowchart TD
    A["User goal"] --> B["Host decomposes goal into task DAG"]
    B --> C["Match DAG nodes to specialist agents"]
    C --> D["Execute dependencies + integrate results"]
    D --> E{"Failure or persistent weakness?"}
    E -- "No" --> F["Store successful experience / skills"]
    E -- "Yes" --> G["Link failure to trace evidence"]
    G --> H["Write repair hypothesis + target source"]
    H --> I["Create executable patch"]
    I --> J["Activation predicate"]
    J --> K{"Patch actually ran?"}
    K -- "No" --> L["Reject"]
    K -- "Yes" --> M["Paired parent-vs-child validation"]
    M --> N{"Useful and distinct?"}
    N -- "No" --> L
    N -- "Yes" --> O["Insert into gene bank"]
    O --> P["Recombine diverse archived mechanisms"]
    P --> C
~~~

## Step-by-step implementation

### Task composition
1. Parse the goal into subtasks with explicit dependencies.
2. Give each node required inputs and expected outputs.
3. Match each node to a specialist by capability and resource constraints.
4. Execute nodes only when dependencies are ready.
5. Integrate outputs and preserve an execution record.

### Harness evolution
6. On failure, save the exact trace and specialist version.
7. Require a repair hypothesis with source location and a predicted behavior change.
8. Create a bounded patch.
9. Run an activation predicate. If the intended mechanism never fires, do not credit it.
10. Compare child and parent on the same task set.
11. Keep diverse strong candidates in an archive instead of only one winner.
12. Recombine archived mechanisms only after interface and regression checks.

### Skill memory
13. Distill successful experiences into reusable skills.
14. Index skills by when they apply, not only by text similarity.
15. Re-evaluate stale skills when the underlying specialist changes.

## Experimental evidence

Raven reports strong results across complex and long-horizon tasks. Because the system is broad, not every gain isolates one harness mechanism.

One useful skill-system result shows the effect of curated retrieval:
- a Raven/Qwen setting moves from about **9.2 to 22.6** on SkillsBench with its skill pipeline;
- simpler off-the-shelf retrieval and raw-crawl baselines are materially lower.

The broader evaluations support the claim that specialist composition and persistent experience can expand coverage. They do **not** by themselves prove that every gene-bank evolution mechanism is optimal.

## Why the task DAG matters for RHEvolution

A DAG is a useful ownership artifact because it makes dependencies explicit.

Raven already asks:
- which subtask depends on which;
- which specialist produced this output;
- what can run in parallel.

RHEvolution can apply the same representation one level lower:
- which harness component owns this behavior;
- which components consume its output;
- which source ranges implement it;
- which execution-trace nodes belong to it.

That turns "decomposition" into a concrete graph that an optimizer can inspect and modify.

## Failure modes and limits

- Raven is a large system, so aggregate gains have many possible causes.
- Task decomposition quality can dominate downstream specialist quality.
- The gene bank preserves diversity but does not guarantee safe recombination.
- Harness component categories are still mainly designed by humans.
- More agents and memory increase coordination cost.
- Archived skills can become stale as tools and harnesses change.

## Implementation checklist

For a Raven-like evolution subsystem you need:
- DAG execution engine;
- specialist registry;
- versioned traces;
- repair hypotheses;
- activation tests;
- matched parent-child evaluation;
- diversity archive;
- recombination with compatibility checks;
- persistent skill store with provenance.

Every archive entry should retain the task subset it improves. "Score only" loses the complementarity information needed for recombination.

## What RHEvolution should take from it

Take three ideas:
1. **DAG as the structural representation.**
2. **Activation predicates before assigning causal credit.**
3. **Quality-diversity archive instead of one linear winner.**

Then apply the decomposition logic to the harness itself. RHEvolution should allow the ownership DAG to split and fuse based on trace evidence, not only decompose end-user tasks.

A strong paper comparison would show that a learned harness DAG gives better OOD improvement or lower search cost than Raven-style fixed harness modules under the same optimizer budget.
