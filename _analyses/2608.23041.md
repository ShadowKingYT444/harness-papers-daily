## What is actually new

AutoSaddler turns harness evolution into an **evidence-tracked repair process**. A diagnosis agent reads failed traces and source code, makes a bounded patch, and stores the result in an evolution DAG. Later search can reuse and combine useful changes from different earlier versions.

The novelty is the combination of three loops:

1. diagnose a concrete failure and patch it;
2. reflect on which accepted and rejected edits taught something reusable;
3. evolve from an explicit DAG of versions instead of one linear latest candidate.

## Mental model

A normal optimizer can behave like "edit, score, keep the winner." That throws away why an edit worked, why another failed, and which earlier branch contained a useful mechanism.

AutoSaddler treats every attempt as data. The trace says what went wrong. The code diff says what was changed. The score says what happened. Reflection converts those events into durable lessons. The EvoDAG keeps several branches available so search can combine mechanisms rather than only mutate the newest harness.

This is close to software debugging: evidence first, local change, regression check, version history.

## Key objects and state

- **Execution trace:** full messages, tool calls, observations, and result.
- **Injected source context:** only the harness code relevant to a diagnosis.
- **Diagnosis-Patch session:** one bounded repair attempt.
- **Reflection memory:** summaries of accepted and rejected changes.
- **EvoDAG:** nodes are harness versions; edges are patches/lineage.
- **Incumbent:** current strong harness.
- **Archived branch:** a non-incumbent version that may contain reusable behavior.
- **Development set:** selects the final candidate.
- **Activation / execution evidence:** confirms that the patch actually affected behavior.

## Optimization loop

~~~mermaid
flowchart TD
    A["Run current harness on task batch"] --> B["Collect failed traces"]
    B --> C["Diagnosis agent links failure to source"]
    C --> D["Generate bounded patch"]
    D --> E["Run patched harness on matched tasks"]
    E --> F["Record fixed cases, regressions, cost, diff"]
    F --> G["Add node + edge to EvoDAG"]
    G --> H["Reflection extracts reusable lessons"]
    H --> I["Evolution step selects one or more useful ancestors"]
    I --> J["Create next candidate / combine prior gains"]
    J --> A
~~~

## Step-by-step implementation

1. Run the seed harness on a small task batch and save full traces.
2. For each failure, identify the relevant harness files/functions. Give those source ranges plus the trace to the diagnosis agent.
3. Require the agent to state a root-cause hypothesis before it edits code.
4. Restrict the patch to a known change surface such as prompts, tools, or middleware unless evidence justifies a broader change.
5. Re-run the same tasks. Record which failures disappear and which successful cases regress.
6. Create an EvoDAG node for the candidate. Store its parent(s), diff, evaluation summary, and diagnosis.
7. Reflect over several recent accepted and rejected nodes. Save lessons such as "this retry rule helped network failures but causes duplicate writes."
8. When choosing the next parent, do not only choose the newest node. Search the DAG for complementary improvements.
9. If combining branches, test the combined candidate from scratch; do not assume independently good patches compose safely.
10. Use a separate development/selection set before final held-out evaluation.

## Experimental setup

The paper evaluates on three distinct agent environments:

- **GAIA2**
- **SWE-Bench Pro**
- **Terminal-Bench 2.0**

The method is compared with the original harnesses and other automatic harness optimizers. The fixed task-solving model is wrapped by the evolving harness.

The important methodological point is that the search is trace-driven: candidate changes are grounded in concrete failed executions rather than proposed from only the aggregate score.

## Results that matter

The paper reports the following representative improvements:

| Benchmark / seed | Before | AutoSaddler | Gain |
|---|---:|---:|---:|
| GAIA2 default agent | **53%** | **62%** | **+9 pp** |
| SWE-Bench Pro with SWE-agent | **37.3%** | **46.9%** | **+9.6 pp** |
| Terminal-Bench 2.0 with Terminus-2 | **40%** | **50%** | **+10 pp** |

The search also keeps many rejected candidates. That negative history is part of the method rather than discarded noise.

## Why the DAG matters

A linear search has a destructive property: once a later edit removes an earlier useful behavior, recovering that behavior requires rediscovery.

An EvoDAG makes three operations easier:

- inspect which ancestor introduced a gain;
- return to an earlier branch;
- combine two branches that solve different failure classes.

The DAG does **not** solve composition by itself. It only preserves the evidence needed to attempt safe composition.

## Failure modes and limits

- The patch taxonomy and source scopes are still human-defined.
- Diagnosis can be wrong; the optimizer can spend many expensive evaluations repairing the wrong layer.
- Whole-harness DAG nodes do not expose which internal component owns a gain.
- Branch recombination can create interactions that neither parent showed.
- Development-set selection can still overfit if the same small cases guide many iterations.
- More trace history helps only if it is indexed and summarized well; raw history can become context bloat.

## Implementation checklist

Store one immutable record per candidate:

- candidate ID and parent IDs;
- repository commit/hash;
- diagnosis and supporting trace spans;
- exact patch/diff;
- activation evidence;
- per-task outcomes before and after;
- regressions;
- token/runtime cost;
- reflection lessons;
- accepted/rejected status.

Build graph queries such as "ancestors that fixed failure type X" and "branches with complementary solved-task sets."

## What RHEvolution should take from it

Use the EvoDAG, but make it **component-aware**. A RHEvolution edge should say not only "candidate B came from A" but also "owner node 7 split into 7a/7b" or "nodes 4 and 6 fused."

Use trace-grounded diagnosis as input to split/fuse decisions. The DAG then becomes a history of both code and decomposition structure.

A useful experiment is to compare:
- whole-harness EvoDAG search;
- fixed component EvoDAG search;
- adaptive RHEvolution graph search.

Keep the task/evaluation budget matched.
