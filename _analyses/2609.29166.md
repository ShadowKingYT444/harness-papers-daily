## What is actually new

HarnessPAI represents a physical-agent harness as **executable program structure** and improves that program between rollouts. It combines perception calls, geometric reasoning, action-model calls, verification, and reusable repair knowledge.

The interesting distinction is:
- task execution can be mostly open-loop at the high-level program layer;
- evolution is closed-loop across episodes.

The harness becomes a program that can be debugged and versioned rather than a long prompt that asks the model to plan everything online.

## Mental model

A robot task such as "put the mug in the cabinet" requires several different operations:
1. identify objects;
2. reason about positions;
3. invoke a low-level action model;
4. inspect whether the move worked;
5. recover if the scene changed.

HarnessPAI encodes this orchestration in code. When a rollout fails, an evolution agent can change the program rather than retraining the action model immediately.

Successful repairs also enter a skill-memory graph so later tasks can reuse them.

## Key objects and state

- **Task graph:** structured decomposition of the physical task.
- **Harness program:** executable control code.
- **Perception/model calls:** semantic visual interpretation.
- **World/action model calls:** low-level physical actions.
- **Verification functions:** check whether intermediate goals succeeded.
- **Failure trace:** program state + environment outcome.
- **Skill memory:** graph-structured store of failure-to-repair knowledge.
- **Successful trajectory set:** can later train the action model.
- **Versioned program:** updated between environment seeds/episodes.

## Evolution loop

~~~mermaid
flowchart TD
    A["Expert / task traces"] --> B["Build task graph + initial harness program"]
    B --> C["Run physical task"]
    C --> D["Collect program trace + visual/physical outcome"]
    D --> E{"Task succeeds?"}
    E -- "No" --> F["Diagnose failing stage"]
    F --> G["Edit executable harness program"]
    G --> H["Store reusable repair in skill memory"]
    H --> C
    E -- "Yes" --> I["Store successful expert trajectory"]
    I --> J["Optional: fine-tune action model later"]
    J --> C
~~~

## Step-by-step implementation

1. Convert demonstrations or task descriptions into a task graph with explicit stages.
2. Create program functions for each stage: observe, reason, select action, execute, verify, recover.
3. Keep low-level control in a pretrained action model. The harness decides *when and why* to call it.
4. Run the program end to end and log function calls, observations, actions, and physical outcomes.
5. On failure, identify the stage that first makes the episode unrecoverable.
6. Give the evolution agent the relevant code, trace, and failure outcome.
7. Edit the program. Prefer reusable control logic over task-ID-specific cases.
8. Re-run on new environment seeds so a repair must survive scene variation.
9. Store accepted repair knowledge in the skill graph.
10. On later tasks, retrieve relevant skills as implementation hints.
11. Keep successful verified traces in a separate dataset if you later want to improve the action model.

## What is fixed and what changes

During harness search:
- the wrapped physical/action model can stay fixed;
- the executable high-level program changes;
- memory of accepted repairs grows.

The paper also studies later model improvement from successful harness-generated data, but that is a separate stage. Do not mix the two when measuring harness contribution.

## Experimental evidence

The paper evaluates on simulated physical-agent suites including **LIBERO-PRO** and **RoboCasa**, plus additional physical tasks.

It reports high task success for the programmatic harness. One comparison reports about **98.1% overall** for HarnessPAI versus **97.0%** for a Harness-VLA baseline, with a larger difference on one LIBERO goal subset (**97.2% vs 94.0%**).

Treat these exact cross-system numbers cautiously because protocols and components are not always identical. The cleaner evidence is within-system improvement from evolving the executable harness and the ability to reuse successful traces for later action-model training.

## Why the program representation matters

A program exposes:
- state variables;
- stage boundaries;
- control branches;
- tool calls;
- assertions.

That makes failures more attributable than a single monolithic prompt. It also allows deterministic checks that do not consume model tokens.

This is the same reason code-oriented harness evolution is attractive for RHEvolution: source structure gives the optimizer something explicit to own and split.

## Failure modes and limits

- The base action model must already support the low-level behaviors the program requests.
- Whole-program edits can still have weak credit assignment as the program becomes large.
- A skill-memory graph can contain stale repairs after the program changes.
- Simulator success does not guarantee real-world robustness.
- Later fine-tuning of the action model confounds harness-only attribution if reported together.
- Much of the high-level decomposition is initialized from human/expert structure rather than discovered from scratch.

## Implementation checklist

Use:
- typed task-graph nodes;
- explicit function-level logging;
- assertions/verification after important actions;
- environment-seed replay;
- separate stores for program versions and skill memory;
- source links from every memory entry to the failure/repair that created it;
- frozen-model evaluation before any optional fine-tuning.

## What RHEvolution should take from it

HarnessPAI demonstrates why **executable artifacts are better optimization targets than vague natural-language responsibilities**.

RHEvolution can go further:
- map every graph node to source ownership;
- split a node when its traces contain multiple independent failure mechanisms;
- fuse adjacent nodes when they are always changed together;
- keep skill memory scoped to the owner that produced it;
- invalidate or re-check memories after structural edits.

The paper is useful as an embodied-domain example that the same structural problem appears outside coding agents.
