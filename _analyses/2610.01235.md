## What is actually new

Harness Annealing moves control responsibility **from the external harness into the model**.

Training begins with a strong scaffold that demonstrates useful control decisions. Later stages deliberately weaken the harness. The model must learn to perform more of those decisions itself.

The novelty is treating "where should this capability live?" as a trainable boundary rather than assuming the harness should always retain every useful mechanism.

## Mental model

A strong harness may:
- remind the model to inspect;
- force a revision;
- decide when to stop;
- inject a checklist.

This helps task performance, but the model can become dependent on those cues.

Harness Annealing uses the strong harness as a teacher, then gradually removes support. If training succeeds, the final model can perform well with a cheaper/weaker harness.

## Key objects and state

- **Harness hierarchy:** strong to weak levels.
- **Control decision types:** investigate, revise, stop, etc.
- **Layered supervision:** train control roles separately.
- **Policy/model checkpoint**
- **Cue dropout:** randomly remove scaffold cues.
- **Replay buffer:** older examples retained during later stages.
- **Trajectory source harness:** version attached to every training example.

## Training loop

~~~mermaid
flowchart TD
    A["Collect trajectories under strong harness H4"] --> B["Segment control decisions by role"]
    B --> C["Train model on those decisions"]
    C --> D["Move to weaker harness H3/H2/H1"]
    D --> E["Collect new trajectories"]
    E --> F["Apply cue dropout + replay"]
    F --> G["Train again"]
    G --> H{"Can model retain performance with less support?"}
    H -- "No" --> I["More replay / slower annealing"]
    H -- "Yes" --> D
~~~

## Step-by-step implementation

1. Define harness levels that differ in explicit external control.
2. Collect successful trajectories under the strongest level.
3. Label or segment decisions by control role.
4. Train the model to reproduce those decisions, not only next-token text.
5. Switch data collection to a weaker harness.
6. Mix older data so earlier capabilities do not vanish.
7. Randomly drop some harness cues during training so the policy cannot rely on them deterministically.
8. Repeat until reaching the target weak-harness condition.
9. Evaluate the same model checkpoint under several harness strengths.
10. Measure both task performance and the performance gap between strong and weak harness deployment.

## Experimental result

For one 9B setting trained from a strong harness:
- SWE-QA with weak H1 starts around **71.99**;
- after targeted annealing it reaches about **77.00**, a gain of **5.01**.

On SWE-QA-Pro:
- roughly **74.64 → 77.73**, a **+3.09** gain.

More importantly, the cross-harness performance range shrinks:
- about **5.48 → 0.57** on one benchmark;
- about **3.61 → 1.32** on another.

That means the model becomes less dependent on which harness strength it receives.

A larger 35B model shows smaller weak-support gains, suggesting stronger models may already internalize more control.

## What the ablations imply

Layered control supervision transfers better to weak-harness deployment than simply imitating complete strong-harness trajectories in the reported comparison.

Cue dropout and replay address two different problems:
- dropout reduces dependence on one external cue;
- replay reduces forgetting as the support changes.

The method is therefore more than "train on outputs from a good harness."

## Why this matters for harness evolution

A component can become unnecessary.

If a model reliably internalizes a control behavior, keeping the external mechanism may:
- waste tokens;
- add latency;
- conflict with the model's own control;
- duplicate logic.

So long-run scaffold evolution can include a **delete/internalize** operation, not only add/split/fuse.

## Failure modes and limits

- Requires model weight training; not applicable to frozen-weight-only systems.
- Training budgets are not perfectly matched in every comparison.
- Removing external control can reduce auditability.
- Internalized behavior is harder to patch than code.
- The study uses a limited model/harness hierarchy.
- A stronger model shows smaller gains, so usefulness depends on policy capacity.

## Implementation checklist

Every training trajectory must store:
- source harness level/version;
- control-decision labels;
- task outcome;
- model checkpoint.

For each external mechanism, measure:
- task gain when enabled;
- whether the trained model can reproduce the behavior without it;
- cost;
- audit/safety value.

Do not remove a guard only because the model usually learned it if the guard exists for hard safety guarantees.

## What RHEvolution should take from it

For the initial RHEvolution paper, model weights should probably remain frozen so decomposition is cleanly attributable.

But this paper suggests a future structural operator:

**INTERNALIZE(owner)** — train the model to absorb a stable responsibility, then delete or simplify the external owner if held-out performance and safety remain acceptable.

This extends adaptive decomposition across the model/harness boundary, not only inside the harness.
