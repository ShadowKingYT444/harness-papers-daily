## One line
A controlled, backbone-matched study of MLE agents showing that under equal 24h budgets, the single largest effect is giving the model a coding-agent environment (shell + filesystem); beyond that, explicit search structure, autonomy, and multi-agent orchestration add nothing statistically significant — and a minimal single-session agent ("Malena") matches or beats four open-source SOTA harnesses on MLE-bench and NatureBench.

## The problem
MLE harness design has been accumulating machinery — search trees, populations of programs, memory hierarchies, multi-agent orchestration — but leaderboard gains arrived alongside backbone capability gains, making it impossible to attribute progress to the harness. Existing comparisons run under different backbones, different hardware, and tiny seed counts. The question: once a frontier model has direct tool-use access to an execution environment, which harness components still earn their keep?

## How it works
Two experiments, both holding backbone, hardware (1×A100 80GB, 12 CPU, 144GB RAM), and 24h time budget fixed, on MLE-bench (a fixed30 set) and NatureBench. First, a ladder of ablations re-implemented in one OpenCode-based codebase: (1) **Chat vs Oneshot** — a single chat-API completion vs one coding-agent session, same 6h; (2) **search primitives** — Chain, Greedy, UCB1, Best-of-N tree search chained over Oneshot iterations at 24h; (3) **autonomy** — "Malena", a single session spanning the whole 24h with only submission/system/background-jobs tools and a minimal "keep going" prompt; (4) **multi-agent orchestration** — Delegation (subagents), Parallelism (3 independent Malena runs), Broadcast (peer messaging). Second, Malena run as-released against four open-source SOTA MLE harnesses — MLEvolve, AiScientist, Arbor, ScienceFlow — across four backbones (GLM 5.2, Kimi K3, DeepSeek V4 Flash, Gemma 4 31B), with self-select vs oracle selection distinguished and paired-by-task 95% bootstrap CIs throughout.

## Key results
- The coding-agent environment is the dominant intervention: Oneshot beats Chat dramatically for frontier backbones; the deep-DeepSeek-V4-vs-Preview gap suggests tool-use fluency matters more than raw model size.
- No search strategy gives a statistically significant advantage (paired-by-task 95% CIs); the largest gap, UCB1 over Best-of-N, is +2.71pp percentile with CI (−1.44, +6.60).
- Malena achieves the highest medal rate with a significant medal-rate advantage over all manual search methods (CI lower bounds 0.4–5.6pp) and the lowest validation–test selection gap (1.876pp vs 6.832pp for Best-of-N), attributed to reusing the same validation pipeline between attempts.
- Multi-agent interventions add nothing significant: base Malena ≥ +Delegation, +Parallelism, +Broadcast; parallelism raises the oracle ceiling but the selection gap eats it.
- Vs released harnesses: across 17 harness–backbone pairs, Malena matches or beats every harness at every frontier backbone. At GLM 5.2, Malena medals on 62.5% of competitions vs 47.1% for the best external harness. On NatureBench (Surpassed-SOTA rate), Malena ≈ AiScientist > MLEvolve; only the small Gemma 4 31B backbone favors a hand-crafted harness (MLEvolve ahead by mean, CIs overlapping) — weaker backbones still benefit from workflow priors.
- Trace analysis: Malena independently does adaptive search — builds one general pipeline (e.g., a two-stage embed-then-retrieve pipeline), then does hyperparameter search over code patches, reusing checkpoints and utility code; it proposes comparatively rare techniques (top-two technique rarity alongside MLEvolve) and shifts toward performance-oriented techniques (ensembling, independently-rediscovered pseudo-labeling) late in the run.
- Cost caveat: Malena resends its whole context each turn, so modeled cache-read cost is ~6.2× AiScientist's ($12.12 vs $1.95 at GLM 5.2), though total cost remains dominated by the hardware ($24–85 for 24h of A100).

## How it relates to adaptive decomposition
This is a **competing-but-reframing** paper, and the honest reaction is: it attacks a premise adaptive decomposition shares with the rest of the literature — that adding hand-crafted harness structure helps strong agents. Its negative result (hand-crafted search trees, populations, multi-agent scaffolding ≈ zero marginal value given a capable coding agent) says effort should move to the backbone and the runtime, not to elaborating scaffolding. Adaptive decomposition is *itself* a piece of hand-crafted scaffolding around search organization, so this paper is a direct skeptical counterweight: if UCB1-vs-Best-of-N search structure doesn't matter on MLE tasks, why would explicit component budgets / split-fuse operations matter? Two defenses. First, the paper's own small-model exception — hand-crafted priors still help weak backbones — suggests harness structure's value is a decreasing function of backbone capability, not zero everywhere; adaptive decomposition's bets (weaker/failing components need structural intervention) are exactly about the regimes where the agent alone plateaus. Second, the trace analysis shows the strong agent *does* decompose problems on its own (staged pipeline → patch-level search); adaptive decomposition aims to make that decomposition explicit and evolvable rather than emergent. Still: this paper raises the bar — any decomposition mechanism must now beat the "strong model with a shell" baseline at a matched budget, and it should not assume its gains will show up with today's frontier backbones.

## Limits and open questions
Relies heavily on MLE-bench, which the authors admit has task-preparation issues and is a plausible contamination target (mitigated by fixing broken tasks, contamination checks, and adding NatureBench). Statistical power is limited: several CIs are wide, and the authors say the "no-worse-than" claims are better supported than strong effect-size claims. Scope is single-worker interventions; sophisticated inter-agent coordination protocols are explicitly out of scope — so the multi-agent null result may be about their three simple interventions, not coordination in general. Possible asymmetry in tuning effort between Malena and the external harnesses (addressed via backbone-specific bug fixes in Appendix D.3, but worth skepticism). Open: does the selection-gap advantage (reusing one validation pipeline) generalize to domains where validation is noisier? And how far does the "machinery is redundant" claim extend beyond MLE tasks — e.g., to harness evolution itself, where the search space is harness code rather than ML pipelines?
