## What is actually new

VideoEvolve searches inside a **partially fixed structure**.

The main stage boundaries of the video-grounding harness stay stable, but code and instructions *inside* each stage can evolve. The search also keeps promising non-champion branches alive so a structural idea can receive another repair instead of being deleted after one near-miss.

This is a useful middle ground between:
- one monolithic editable harness;
- fully fixed hand-written modules;
- completely unconstrained architecture search.

## Mental model

The harness has stages such as:
- Observe;
- Propose;
- Cross-check;
- Arbitrate;
- Budget gate;
- Finalize.

Each stage has a contract. The optimizer can rewrite how a stage works but cannot casually destroy the interface between stages.

This reduces integration risk. It also makes failures easier to localize.

However, the best candidate is not always one edit away from the current champion. A branch may introduce a useful structure but need another round of repair before it wins. VideoEvolve therefore keeps selected non-champion branches.

## Key objects and state

- **Cloze-structured harness:** stable stage interfaces with editable bodies.
- **Code state:** executable implementation inside stages.
- **Text state:** stage instructions/prompts.
- **Champion:** current accepted best harness.
- **Retained branch:** promising non-champion.
- **Proposal slot:** one search opportunity.
- **Development batch**
- **Validation set**
- **Repair step**
- **Solver-call budget**

## Search loop

~~~mermaid
flowchart TD
    A["Champion + retained branches"] --> B["Choose parent branch"]
    B --> C["Proposer edits code/instructions inside one or more fixed stages"]
    C --> D["Run same development batch as reference"]
    D --> E{"Beats parent/champion?"}
    E -- "Clear win" --> F["Run video-disjoint validation"]
    E -- "Near miss with useful structure" --> G["Retain branch"]
    E -- "Bad" --> H["Reject"]
    G --> I["Repair branch in later proposal slot"]
    I --> D
    F --> J{"Validation win?"}
    J -- "Yes" --> K["Promote champion"]
    J -- "No" --> G
    K --> A
    H --> A
~~~

## Step-by-step implementation

1. Define stage interfaces first. Specify input state, output state, and allowed side effects.
2. Build a minimal seed implementation for each stage.
3. Freeze the underlying video model and tool APIs.
4. Run a development batch and save per-stage traces.
5. Let an external coding agent edit stage code or instructions.
6. Evaluate candidate and parent on the same batch.
7. Promote only a clear improvement to expensive validation.
8. Keep a small number of near-miss branches when they contain a distinct mechanism.
9. Allow later proposals to continue from those branches.
10. Use video-disjoint validation so the search cannot win by memorizing clips.
11. Enforce a fixed maximum number of solver calls/frames.
12. Freeze the final harness for five-benchmark evaluation.

## Experimental setup

The final harness is evaluated on five temporal-grounding benchmarks:

- Charades-STA
- ActivityNet
- QVHighlights
- ReXTime
- TimeLens-Bench

Metrics include **R@0.5** and **mean IoU**.

The search uses a fixed proposal budget, and the paper includes a direct branch-retention ablation with the same seed and development sampling schedule.

## Results that matter

VideoEvolve reports:

| Benchmark | R@0.5 | mIoU |
|---|---:|---:|
| Charades-STA | **70.05** | **61.35** |
| ActivityNet | **40.97** | **43.28** |
| QVHighlights | **71.68** | **66.27** |
| ReXTime | **59.17** | **53.93** |
| TimeLens-Bench | **53.53** | **50.73** |

The exact seed-to-evolved comparison improves mIoU on all five benchmarks while keeping the solver fixed.

## Branch-retention ablation

A matched Full versus No-Branch search tests whether non-champion continuation is useful.

No-Branch reaches roughly:
- Charades mIoU **58.82**
- QVHighlights mIoU **64.22**
- ReXTime mIoU **53.38**
- TimeLens mIoU **49.64**

The Full search improves the video-disjoint benchmarks and raises the TimeLens macro score by about **1.58 points**. It also uses fewer development-time solver calls in that comparison, so the benefit is not explained by more solver usage.

ActivityNet is a counterexample: one metric is slightly worse. Branch retention is not uniformly beneficial.

## Why fixed interfaces help

Stable interfaces provide:
- local edit scopes;
- compatibility guarantees;
- easier rollback;
- comparable traces across versions.

They also create a potential ceiling. If the best future harness requires a new stage or different dependency graph, fixed interfaces prevent that change.

This is exactly the tradeoff RHEvolution should study.

## Failure modes and limits

- Search cost is high.
- Stage boundaries are human-designed.
- Code edits help less consistently than instruction edits in some analyses.
- Retained branches can waste budget.
- Fixed interfaces can become the wrong abstraction.
- Video grounding is a specialized domain.

## Implementation checklist

For each stage keep:
- interface schema;
- source version;
- prompt/instruction version;
- stage-level trace;
- parent branch;
- candidate validation vector.

Retained branches need an explicit quota and reason for retention, otherwise the archive becomes unlimited.

## What RHEvolution should take from it

Use **stable interfaces as temporary measurement boundaries**, not permanent truth.

When RHEvolution splits an owner:
1. create explicit child interfaces;
2. freeze them for enough iterations to measure value;
3. keep the structural branch even if its first implementation is only a near-miss;
4. later allow another structural edit if evidence shows the interface itself is the bottleneck.

VideoEvolve is a good baseline between fixed modular search and fully adaptive graph search.
