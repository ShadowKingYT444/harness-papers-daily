## What is actually new

**PluginRSI changes the unit of evolution.** Meta-Harness-style search can rewrite a whole harness candidate. PluginRSI first turns the harness into named, executable plugins with stable interfaces. It can then change one plugin while the rest of the system stays fixed, keep several good versions of that plugin, and later rebuild the full harness from the growing library.

The important idea is not "use plugins." The important idea is **separate local mechanism discovery from global integration**. A local edit gets a cleaner credit signal because only one component changed. A later recomposition step handles the fact that individually good components can still interact badly.

## Mental model

Imagine a harness with four jobs: manage context, choose tools, enforce a review step, and remember useful facts. A whole-harness optimizer can change all four in one proposal. If the score improves, you do not know which change mattered. If the next proposal rewrites the file again, it can accidentally delete the useful change.

PluginRSI instead treats each job as a replaceable module. It tests variants of one module against the same local task batch. Good variants enter a persistent library rather than replacing the old version. The search therefore accumulates mechanisms. Periodically, a second search chooses which module versions should run together and how they should be connected.

This creates two different search problems:

1. **Mutation:** "Can I make this one mechanism better?"
2. **Recomposition:** "Which set of mechanisms works best as a complete harness?"

That split is the core novelty.

## Key objects and state

- **Seed workflow:** the original control graph.
- **Plugin:** a YAML-like specification plus executable implementation. The paper uses roles, tools, skills, and memory plugins.
- **Plugin library:** all accepted plugin variants, not only the latest version.
- **Mutation minibatch:** a small balanced set of successful and failed cases used to test one plugin variant.
- **Candidate harness:** one selected plugin set plus a workflow.
- **Lineage / evaluation history:** records of which variants and full harnesses were tried and how they scored.
- **Fixed solver:** the task model does not change during harness evolution.
- **Fixed proposer:** the model proposing mutations also stays fixed in the main experiments.

## Optimization loop

~~~mermaid
flowchart TD
    A["Current plugin library + workflow"] --> B["Choose one plugin to improve"]
    B --> C["Sample a balanced mini-batch of successes and failures"]
    C --> D["Generate several variants of only that plugin"]
    D --> E["Run each variant with every other plugin held fixed"]
    E --> F{"Better on the same mini-batch?"}
    F -- "No" --> B
    F -- "Yes" --> G["Add variant to shared library"]
    G --> H["Recompose: choose plugin versions + edit workflow"]
    H --> I["Run complete-harness validation"]
    I --> J{"Full system improves?"}
    J -- "No" --> B
    J -- "Yes" --> K["Promote candidate but keep older library entries"]
    K --> B
~~~

## Step-by-step implementation

1. Define a plugin interface. Each plugin needs a clear purpose, inputs, outputs, dependencies, and executable implementation.
2. Convert the starting harness into a workflow that calls these plugins. Do not let the optimizer change interfaces casually; stable interfaces make local evaluation possible.
3. Run the current harness and save task outcome, trajectory, token use, and plugin activations.
4. For a mutation round, choose one plugin. Build a small batch that includes both cases where the current harness succeeds and cases where it fails.
5. Give the proposer the target plugin, relevant traces, and feedback. Generate several variants while freezing the workflow and all other plugins.
6. Evaluate every variant on the **same** minibatch. This matched test matters because otherwise task sampling noise can look like an improvement.
7. If a variant improves the local objective, add it to the library. Do not delete its parent.
8. Periodically run recomposition. The composer selects plugin versions from the library and can revise the workflow that connects them.
9. Run the recomposed system on a broader validation set. A plugin that helped alone can conflict with another plugin.
10. Promote only the full harnesses that pass this global check. Keep the library so later search can reuse older mechanisms.
11. Freeze the final harness before held-out evaluation.

## Experimental setup

The paper tests software engineering, terminal work, and question answering. The important design choice is that optimization tasks and held-out tasks are separate.

- SWE-bench Verified is split into 400 optimization tasks and 100 held-out tasks.
- Terminal-Bench 2.1 uses a development subset and a held-out subset.
- The QA setting mixes several domains so the library must contain mechanisms that are useful for different task types.
- The solver model is fixed during each optimization run.
- The proposer model is also fixed. The measured change therefore comes from the harness search, not weight training.
- Meta-Harness is the main whole-harness search comparison.

## Results that matter

| Result | PluginRSI | Comparison | What it tells us |
|---|---:|---:|---|
| Terminal-Bench 2.1 held-out | **73.3%** | Meta-Harness **66.7%** | Component search can beat monolithic search. |
| QA overall accuracy | **0.675** | Meta-Harness **0.638** | The gain is not limited to coding. |
| SWE-bench Verified held-out, Kimi-K3 proposer | **69%** | No plugin mutation **57%** | Local plugin evolution contributes materially. |
| Same setting without recomposition | **59%** | Full **69%** | Good local parts still need global integration. |
| Library initialized with only 4 basic plugins | Still improves | Main library starts much larger | Search does not require a hand-built large library. |

The paper also reports SWE-bench held-out results around **65–69%** depending on proposer and roughly **6–10 percentage points** over Meta-Harness in the compared settings. A library evolved with one model also transfers useful behavior to other solver models.

## Ablations: what caused the gain

The two decisive ablations remove the two halves of the method.

**Remove plugin mutation:** the system can only recombine what it already has. Performance falls sharply. This says recomposition alone does not discover enough new mechanisms.

**Remove recomposition:** the system can create good local plugins but cannot reliably combine them. Performance also falls sharply. This is direct evidence that "optimize components independently and concatenate them" is not sufficient.

The reduced-library experiment is also important. It suggests the method can *grow* useful structure instead of only searching a large expert-written menu.

## Failure modes and limits

- Plugin boundaries are still human-defined. The optimizer cannot decide that one plugin contains two unrelated responsibilities and should split.
- A failure can cross several plugins. Local mutation gives weak credit when the cause is an interaction.
- Local minibatches can overfit. The global validation gate is essential.
- The library can grow large. A real implementation needs pruning, versioning, and compatibility checks.
- Transfer across solver models is encouraging, but it does not prove universal model-independent components.

## Implementation checklist

You need:

- a component registry with stable interfaces;
- a versioned implementation library;
- trajectory logging with plugin activation;
- matched local evaluation;
- a mutation proposer that is scoped to one component;
- a recomposition stage;
- a full-harness regression gate;
- held-out evaluation that the optimizer cannot inspect.

A minimal database row for a plugin version should contain: parent version, source hash, interface hash, task batch, local score, full-harness scores where used, token/runtime cost, and accepted/rejected status.

## What RHEvolution should take from it

This is one of the closest baselines to RHEvolution. Keep the **library + local mutation + global integration** structure.

The missing capability is adaptive decomposition. RHEvolution should let evidence change the component graph itself:

- **split** a component when its failure evidence contains several separable mechanisms;
- **fuse** components when they are too coupled to evaluate independently;
- **keep** multiple successful child variants instead of one linear successor;
- require a full-harness gate after structural edits.

The clean experiment is PluginRSI-style fixed boundaries versus RHEvolution learned split/fuse boundaries with the same solver, proposer, tasks, and rollout budget.
