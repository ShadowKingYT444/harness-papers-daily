## One line
Represents a harness as a set of atomized, independently-improvable plugins plus a coordination workflow, and runs recursive optimization at the plugin level so good mechanisms accumulate in a reusable library.

## The problem
Prior harness optimizers (DGM, Meta-Harness) search over complete harness programs, which couples multiple mechanisms together: a good rewrite can overwrite a locally-good mechanism, and improvements can't be isolated or reused across iterations. So the search keeps converging to similar designs instead of accumulating knowledge. PluginRSI's answer: make the plugin — not the whole harness — the unit of evolution.

## How it works
A plugin is a harness mechanism with a standardized interface: a YAML spec (input/output schemas, prompts, rubrics, config metadata) plus an executable Python implementation. A harness is H = H(W, P): a workflow W that coordinates execution, plus a selected plugin set P (the paper starts from a 75-plugin library implementing roles, tools, skills, memory). Each iteration has two stages:
1. **Plugin mutation**: N mutation candidates are explored *in parallel* on balanced minibatches of validation tasks (equal correct/incorrect examples per minibatch, varied feedback for diversity). For each, the proposer agent picks one plugin in the current harness, rewrites just that plugin while the workflow and all other plugins stay fixed, recompiles, and evaluates on its minibatch. Variants that improve the score are added to the shared plugin library.
2. **Harness recomposition**: the proposer selects a new plugin set from the updated library and revises the workflow W to coordinate them, then evaluates the recompiled candidate on the validation set. Adopt if better.
The library is the key: empirically beneficial plugins persist and get reused in later iterations and even new tasks (reusing an evolved library hits 69% held-out resolve vs 65% without). Policy model and proposer stay frozen throughout.

## Key results
- SWE-bench Verified held-out: 65.00% (GPT-5.6 Terra proposer) and 69.00% (Kimi-K3 proposer) — 6–10 pp over Meta-Harness, the best baseline; gains larger on held-out than held-in.
- Harnesses transfer across solver models without re-optimization (e.g., Kimi-optimized harness gets 64% on GPT-5.6 Terra and GLM-5.2).
- Terminal-Bench-2.1 held-out: 73.3% vs 66.7% for Meta-Harness; QA benchmarks overall accuracy 0.675 vs 0.638.
- Ablations: both stages contribute; it works even starting from only 4 basic plugins instead of the 75-plugin library. Reaching strong harnesses with fewer solver rollouts than Meta-Harness.

## How it relates to adaptive decomposition
This is the closest published cousin to adaptive decomposition: it genuinely breaks a harness into independently-mutable components, evolves them in parallel, and accumulates the winners. But the decomposition is **fixed and human-designed**, not discovered by the agent: plugins are pre-atomized with standardized interfaces from a hand-built 75-plugin library, and mutation picks from a fixed set of known slots (one plugin at a time). There is no mechanism for the agent to split a failing plugin into finer pieces, fuse two working plugins, or discover a new decomposition of the harness on the fly — the atomization is a design decision the authors made, not an evolvable parameter. Adaptive decomposition's core novelty — the agent *itself* deciding when and how to decompose — is absent.

## Limits and open questions
The paper doesn't say what happens when the true bottleneck cuts across plugin boundaries — a mechanism spanning two plugins would be hard to evolve piecemeal (this is exactly the coupling worry RLHarness raises about B/P/E). The initial 75-plugin library is hand-designed; the "strong even without the library" ablation is only from 4 basic plugins, so it's unclear how much of the success is the search vs. good human engineering of the starting set. All results are on tasks where harness mechanisms are naturally separable; I'd probe whether recombination actually discovers novel workflows or mostly just picks good plugins (the workflow revision step is thinly analyzed).
