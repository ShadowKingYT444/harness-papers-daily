## Main idea
PluginRSI does not rewrite the full harness every time. It splits the harness into reusable plugins. It improves one plugin at a time, saves useful versions, and then builds a new harness from the best plugins.

This is important because a full-harness rewrite can damage a part that already works.

## Key concepts
- **Harness:** The code and instructions around the model. It can include tools, memory, prompts, and control logic.
- **Plugin:** One harness function with a standard input and output interface.
- **Workflow:** The logic that decides when and how the plugins run.
- **Validation task:** A task used to check whether a change is actually better.

## Optimization loop
```mermaid
flowchart LR
    A[Current harness] --> B[Choose one plugin]
    B --> C[Create plugin variants]
    C --> D[Test variants]
    D --> E[Save better plugins]
    E --> F[Recompose harness]
    F --> G[Validate full harness]
    G --> A
```

## How it works in the paper
1. The paper used a workflow plus a plugin library. In the main setting, the library contained 75 plugins for roles, tools, skills, and memory. Each plugin had a structured interface and executable implementation.
2. For one mutation step, the proposer selected one plugin and generated several candidate versions while the workflow and all other plugins stayed fixed. This isolated the changed variable and made the evaluation signal easier to interpret.
3. The candidates were evaluated on small balanced minibatches that mixed successful and failed cases. The paper also varied the feedback used across candidates to reduce repeated, narrow edits.
4. A candidate that improved the evaluation score was added to the shared plugin library instead of replacing the old version. This let later search reuse several successful mechanisms from earlier rounds.
5. A second recomposition stage selected a new plugin set from the expanded library and could also revise the workflow that connected those plugins.
6. The recomposed full harness was then evaluated again because two plugins that were individually useful could still interact badly when combined.

The model that solves tasks stays fixed. The proposer also stays fixed. The improvement comes from the harness.

## Why it matters for RHEvolution
This paper gives strong evidence that **component-level evolution can work better than monolithic evolution**. It also gives RHEvolution a useful library idea: keep successful components so future search can reuse them.

The main difference is the decomposition. PluginRSI uses plugin boundaries that humans defined in advance. RHEvolution wants the agent to decide when a component is too large, split it, and later fuse components when that is useful.

## Exact reported results
- SWE-bench Verified held-out resolve: **65.0%** with the GPT-5.6 Terra proposer setting and **69.0%** with the Kimi-K3 proposer setting.
- The paper reports roughly **6 to 10 percentage points** over Meta-Harness, depending on the setting.
- Terminal-Bench 2.1 held-out: **73.3%** for PluginRSI versus **66.7%** for Meta-Harness.
- QA benchmark overall accuracy: **0.675** versus **0.638**.
- A Kimi-optimized harness reached about **64%** when transferred to GPT-5.6 Terra and GLM-5.2 without another harness-optimization run.
- Ablations showed that both plugin mutation and full-harness recomposition contributed.
- The method still worked when the initial plugin library was reduced from 75 plugins to **4 basic plugins**.
- The paper also reports fewer solver rollouts to reach strong harnesses than Meta-Harness.

## What the results mean
The central result is not only the final score. The shared library prevented useful local mechanisms from disappearing when another part of the harness changed. The transfer result also suggests that at least some discovered mechanisms were harness-level improvements rather than behavior tied to one solver model.

## Evidence and limits
- The paper reports stronger held-out results than Meta-Harness on SWE-bench Verified and Terminal-Bench 2.1.
- Reusing the evolved plugin library also helps on new optimization runs.
- The plugin boundaries are fixed. The system cannot decide that one plugin should become two smaller components.
- A failure that crosses several plugin boundaries can still be hard to assign to one component.
