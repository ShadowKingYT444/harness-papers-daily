## What is actually new

FloWright addresses **credit assignment inside workflows**.

Instead of optimizing a workflow from one final sparse reward, it records which role authored each important trace node. Failure evidence can then be mapped back to the role that produced the relevant part of the workflow, allowing several roles to co-evolve with more local learning signals.

The main novelty is an instrumented **authorship graph** for assigning learning credit in a multi-role workflow.

## Mental model

A workflow contains:
- planner;
- generator;
- critic;
- tool/execution role;
- downstream agent.

The final answer fails. A single 0 reward says nothing about who should change.

If the trace records that:
- the planner created step X;
- the generator filled node Y;
- the critic approved Y;
- execution later failed at Y;

the system can distribute blame more locally.

This is still not perfect causality: the generator may have failed because the planner gave it a bad subproblem. But it is much more informative than one global score.

## Key objects and state

- **Workflow graph**
- **Role:** one workflow-generating or execution responsibility.
- **Structured trace node**
- **Authorship link:** role → node.
- **Final outcome**
- **Role-level credit**
- **Role policy / prompt**
- **Experience pool**
- **Successful/failed workflow examples**
- **Co-evolution schedule**

## Credit loop

~~~mermaid
flowchart TD
    A["Several roles construct / execute workflow"] --> B["Record workflow graph + node authors"]
    B --> C["Run workflow to final outcome"]
    C --> D["Identify failed / useful trace nodes"]
    D --> E["Map nodes back to author roles"]
    E --> F["Compute role-specific credit/blame"]
    F --> G["Update multiple roles"]
    G --> H["Store successful experiences"]
    H --> A
~~~

## Step-by-step implementation

1. Give every workflow node a stable ID.
2. Record which role created or modified each node.
3. Execute the workflow and preserve node-level outputs.
4. When final evaluation arrives, identify the trace nodes most linked to the failure/success.
5. Map those nodes to authors.
6. Produce a per-role learning signal.
7. Update each role from evidence relevant to its authored nodes.
8. Allow several interacting roles to improve in the same training process.
9. Keep successful workflows in an experience pool.
10. Distill repeated successful patterns into future role context.
11. Re-run complete workflows after role updates because local role improvements can conflict.

## Why authorship is useful

Authorship is cheap. You do not need a second powerful judge to guess every failure owner if the runtime already records who created each node.

It creates an obvious default credit map.

But authorship is **not causal attribution**:
- upstream bad instructions can make a downstream node fail;
- a critic that fails to catch another role's error also shares responsibility;
- interface design can cause failure even when both roles behave as trained.

Use authorship as a starting prior, not final proof.

## Experimental evidence

The paper compares single-role optimization with co-evolving roles and reports better workflow-level performance from co-evolution.

It also studies experience-pool design:
- growing a pool from successful experiences gives about **+4.83 points** over a fixed pool in one reported analysis;
- distilling successful experience adds about **+1.44**;
- mixing success and failure into the same distillation gives a smaller gain, around **+0.53** in that comparison.

The exact values depend on task/workflow setting, but the pattern is clear: targeted role credit and curated successful experience help more than undifferentiated history.

## What makes this different from module search

A module can be a code area. A role is a **producer of trace structure**.

RHEvolution needs both:
- source ownership: which component implements behavior;
- execution authorship: which component produced this event.

When those disagree, that is useful evidence. For example, a generic context component may supply bad state to several role-specific actions.

## Failure modes and limits

- Reliable authorship requires instrumented workflows.
- Cascading failures violate simple one-owner blame.
- Co-evolving several roles can reintroduce interference.
- The workflow topology may still be human-defined.
- Credit from final score remains approximate when no step-level verifier exists.
- Experience pools can overfit recurrent task patterns.

## Implementation checklist

Trace schema needs:
- node ID;
- node type;
- author role/component ID;
- parent dependencies;
- source version;
- inputs/outputs;
- evaluator annotations.

Build ownership queries:
- failure frequency by author;
- cross-owner dependency failures;
- repeated cascades;
- nodes with high downstream impact.

## What RHEvolution should take from it

Use **authorship metadata in execution traces**.

A split is more justified when one source owner produces two separable families of trace nodes with different failure patterns.

A fuse is more justified when two owners form one repeated causal chain and independent edits fail.

FloWright's key lesson is that credit assignment gets easier when the harness emits ownership data during execution rather than asking an LLM to reconstruct ownership after the fact.
