## What is actually new

Adaptive-GEPA learns **both the specialists and the division of work between them**.

The system is not given task-family labels. Search can add a specialist, edit its code, edit its role description, change the router, or deactivate it. The router and specialist library therefore co-evolve from execution evidence.

This is one of the closest papers to adaptive decomposition. The main remaining restriction is that the learned structure is a flat set of top-level specialists, not a recursively changing harness graph.

## Mental model

A single program must answer four very different request families. One global prompt can compromise between them. A human could manually create four experts, but that assumes the right partition is known.

Adaptive-GEPA starts with a router and a small specialist set. Failures cause the reflection model to decide whether the problem is:
- wrong code inside a specialist;
- wrong role description;
- wrong routing;
- missing specialist;
- obsolete specialist.

That means search can change the **partition itself**, not only parameters inside a fixed partition.

## Key objects and state

- **Router:** maps a request to a specialist.
- **Specialist:** executable program for one learned region.
- **Role description:** plain-language scope used by routing/search.
- **Active specialist set:** up to a bounded number of slots.
- **Usage history:** which requests each specialist actually handled.
- **Action history:** recent add/edit/deactivate operations.
- **Search branch:** alternative evolving specialist libraries.
- **Request footprint:** set of validation requests handled by one specialist.
- **Merge matching:** aligns specialists from branches by footprint overlap.

## Optimization loop

~~~mermaid
flowchart TD
    A["Router + active specialist library"] --> B["Run mini-batch"]
    B --> C["Observe failures, scores, specialist usage"]
    C --> D["Reflection chooses ONE structural or local action"]
    D --> E{"Action"}
    E -->|Add| F["Create new specialist + role"]
    E -->|Edit code| G["Change one specialist program"]
    E -->|Edit role| H["Change specialist scope"]
    E -->|Edit router| I["Change assignment logic"]
    E -->|Deactivate| J["Remove specialist from active set"]
    F --> K["Small-batch screen"]
    G --> K
    H --> K
    I --> K
    J --> K
    K --> L["Validation"]
    L --> M["Keep strong branch candidates"]
    M --> N["Optional branch merge by request-footprint overlap"]
    N --> A
~~~

## Step-by-step implementation

1. Define a generic specialist program interface. Every specialist must accept the same request/context envelope and return the same result type.
2. Create a router plus one or a few initial specialists.
3. Run a mini-batch and log which specialist handled each request.
4. Give the reflection model failures, current role descriptions, usage counts, router behavior, and recent edit history.
5. Force the reflection step to choose one action class before generating code. This prevents one proposal from silently changing everything.
6. If adding a specialist, generate both its role description and implementation.
7. If editing a specialist, keep unrelated specialists fixed.
8. Screen the candidate on a small batch, then use a broader validation set.
9. Keep multiple search branches when they discover different partitions.
10. During branch merge, do not align "slot 1" with "slot 1." Compute overlap between the actual requests handled by specialists.
11. Match mutually overlapping specialists and inherit each matched role description + code together.
12. Revalidate the merged library.

## Experimental setup

The main mixture contains four request families:
- HotpotQA;
- AIME;
- PUPA;
- LiveBench instruction-following.

The search is not told these family labels. They are only available to researchers for analysis after the fact.

A Qwen3-8B setting compares:
- seed/single program;
- normal GEPA whole-program prompt evolution;
- GRPO;
- Adaptive-GEPA;
- an oracle-like per-family specialist reference.

## Results that matter

Reported family-mean performance is approximately:

| Method | Mean |
|---|---:|
| Seed | **52.6** |
| GRPO | **54.0** |
| GEPA single program | **62.5** |
| **Adaptive-GEPA** | **70.6** |
| Oracle per-family specialists | **73.0** |

The learned router's final partition matches the post-hoc four-family split on the reported **651 test requests**.

That is strong evidence that a useful task partition can emerge without giving the optimizer the labels.

## Branch merge detail

Specialist identity is not stable during search. One branch might use slot 2 for math while another uses slot 4.

The paper solves this by comparing **request footprints**:
- collect which validation requests each specialist handles;
- compute overlap, such as Jaccard similarity;
- use mutual best matches;
- inherit the role description and code as one unit.

This is a practical answer to "how do I identify the same component after the structure changes?"

## Failure modes and limits

- The main mixture contains known, separable families even though labels are hidden.
- One main seed is emphasized, so structural-search variance needs more study.
- Search has one global call budget rather than independent specialist budgets.
- A flat specialist library cannot recursively split a complex specialist internally.
- A perfect-looking router on this mixture may rely on obvious task cues.
- Branch merge uses behavioral overlap, which can fail when two specialists solve the same requests by very different mechanisms.

## Implementation checklist

Maintain per specialist:
- stable internal UUID, independent of slot;
- current role text;
- source version;
- request footprint;
- per-task successes/failures;
- activation count;
- parent/branch lineage.

Maintain per router:
- assignment logs;
- confusion cases;
- fallback behavior.

Never infer component identity from its list position.

## What RHEvolution should take from it

This is perhaps the closest **learned-partition** baseline.

RHEvolution extends it in three directions:
1. recursive split/fuse inside a component, not only add/remove top-level specialists;
2. source/execution ownership, not only task routing;
3. per-component optimization budgets.

Use request-footprint matching as one signal for component identity after graph edits. Then add execution coupling and source dependencies so identity is not based only on which tasks a node handles.
