## One line
Extends GEPA's reflective search to learn both how to divide requests and how to solve them: it jointly evolves a router and a library of specialist programs under one search budget, with specialists matched across branches by the requests they actually handle.

## The problem
A shared endpoint serves heterogeneous requests (factual retrieval, math, privacy-sensitive writing, constrained output) that need different tools, reasoning modes, and control flow. Optimizing one shared program leaves the division of work implicit in code search; optimizing per task family fixes the division beforehand and requires labels. The paper asks whether search can learn the division of work *and* the programs together, without being told the task partition.

## How it works
Each specialist pairs a short human-readable description of its responsibility with executable source code; a router assigns each request to a specialist. The search loop (Figure 2):
- **Actor LLM** routes requests and executes programs (tools: ColBERTv2 retrieval, fast vs deep thinking profiles); the **evaluator** scores with task metrics or a judge LLM.
- **Reflection LLM** (GPT-5.5) picks one action per iteration — add expert, edit program, edit role, edit router, deactivate — based on failures, roles, and recent changes; the chosen proposal is validated on a minibatch and must beat the parent before full validation and archive entry.
- **Branch merging:** to combine two libraries, specialists are matched by *request overlap* (the validation requests each actually handled), conflicts resolved by scores on shared requests, and each description is inherited together with its program — so specialist identity survives recombination even when slot numbers don't.
- No task labels are supplied to the router or reflection model; labels are used only for sampling and scoring.

## Key results
- On a fixed mixture of HotpotQA, AIME, PUPA, and LiveBench-IF with Qwen3-8B (seed 43, ~18k scored calls): family-mean test score rises 52.6 → 70.6, vs 62.5 for single-program GEPA (GEPA-FPA-ALL, same budget/tools/reflection) and 73.0 for the label-routed reference (four per-family GEPA runs). The learned router matched the post-hoc task partition on all 651/651 test requests.
- The gain is not one task: PUPA contributes 6.0 of the 8.1-point advantage, but reaveraging the other three tasks still favors Adaptive-GEPA (63.5 vs 60.7) without reselection.
- Search efficiency: at 5,018 scored calls Adaptive-GEPA's validation mean (67.5) already beats the best of single-program GEPA (65.6) and the 18k-call GRPO run (60.0). GRPO at 5× budget (90k) only reaches 56.3.
- With GPT-4.1 execution / GPT-5.5 reflection: 71.5 vs 69.8 for single-program GEPA, 74.9 for the label-routed reference.

## How it relates to adaptive decomposition
This is the closest thing to adaptive decomposition in today's literature, differing mainly in framing. Adaptive-GEPA *discovers the decomposition itself* (the router learns the division of work from data, no human-supplied task families), keeps per-specialist programs as independently evolvable units, and deactivates useless branches — the split/fuse instinct in embryo, though fusion here is branch-merging via request-overlap alignment rather than fusing working components. Two transferable ideas: (1) the request-overlap alignment rule is a concrete solution to the "component identity" problem — when components are re-derived each generation, match them by what they actually handled, not by slot or name; (2) inheriting description+program together (never splitting role from code) is a discipline an adaptive-decomposition search should copy when fusing. What it lacks relative to the user's mechanism: no per-component search budgets (one global 18k-call budget), no recursive splitting of failing specialists, and no reversion toward a monolith.

## Limits and open questions
Stated honestly in the paper: the main Qwen3-8B result is one seed (43) on four fixed task families, with no seed robustness or component-effect isolation (two seeds are reported only for an earlier version). Researchers saw periodic test results during development, so the test scores are not from a pristine held-out protocol. "Scored calls" ≠ total compute — a program can make several model calls per score — so the budget comparisons are nominal. No online task discovery: the mixture is fixed, so it doesn't show the router adapting to genuinely new request types arriving over time. The GPT-4.1 evidence is weakened by resumptions and a judge outage (Appendix L).
