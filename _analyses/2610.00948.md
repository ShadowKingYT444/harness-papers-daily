## What is actually new

GUI-HARVEST makes harness evolution **evidence-driven at the behavioral level**.

For GUI tasks, it:
1. repeats the same task from clean snapshots;
2. aligns actions with before/after screenshots;
3. identifies the decisive failure step;
4. groups recurring failures into open-vocabulary behavior modes;
5. requires a proposed patch to predict an observable behavior change *before* evaluation;
6. validates whether that predicted change actually occurred.

The key novelty is that the optimizer cannot simply tell a plausible story after seeing the score. It pre-registers what behavior its patch is supposed to change.

## Mental model

A GUI agent fails to edit a spreadsheet.

Possible causes:
- it clicked the wrong pixel once;
- it repeatedly misreads selected state;
- it never verifies that a dialog closed;
- its retry policy loops after focus loss.

One rollout is ambiguous. Repeating from a clean state shows which failures are persistent.

A screenshot-linked trace then lets the analyst point to the exact action where the task became unrecoverable. Similar findings across tasks become a behavior mode such as "acts before confirming focus."

The harness engineer then changes code for that mode and predicts a measurable effect: "after a focus-changing action, the next trace should contain a verification observation before typing."

## Key objects and state

- **Clean environment snapshot**
- **Repeated rollouts**
- **Action + before/after screenshot evidence**
- **Decisive failure step**
- **Verified finding**
- **Behavior mode:** learned recurring mechanism.
- **Source mapping:** code linked to the mode.
- **Pre-registered update plan**
- **Predicted behavioral effect**
- **Code tests / GUI tests / behavior tests**
- **Update ledger**
- **Rollback checkpoint**

## Optimization loop

~~~mermaid
flowchart TD
    A["Run same GUI task K times from clean snapshot"] --> B["Align actions with before/after screenshots"]
    B --> C["Evidence analyst finds decisive failure steps"]
    C --> D["Deterministic grounding check: cited evidence exists"]
    D --> E["Cluster verified findings into behavior modes"]
    E --> F["Select high-value behavior mode"]
    F --> G["Map mode to harness source"]
    G --> H["Engineer writes patch + predicted observable effect"]
    H --> I["Code tests + GUI replay"]
    I --> J{"Predicted behavior appears?"}
    J -- "No" --> K["Reject / rollback"]
    J -- "Yes" --> L["Run task + regression validation"]
    L --> M["Promote candidate + ledger entry"]
    M --> A
~~~

## Step-by-step implementation

1. Save a reproducible clean VM/snapshot per task.
2. Run each optimization task several times.
3. For every action, save the screen before, action payload, and screen after.
4. Ask an analyst to identify the earliest decisive mistake, not the last visible failure.
5. Verify automatically that every cited screenshot/action/step exists.
6. Aggregate findings across tasks.
7. Create behavior modes in open vocabulary; do not force a small fixed taxonomy.
8. Rank modes by recurrence and expected value.
9. Map the chosen mode to source locations in the harness.
10. Before editing, require the engineer to state the exact expected trace change.
11. Patch only the relevant runtime surface.
12. Run code/unit checks.
13. Replay GUI tasks and check whether the pre-registered behavior appeared.
14. Only then use end-task success for promotion.
15. Log the full change in an update ledger and keep rollback.

## Experimental setup

Main benchmark: **OSWorld-Verified**.

The paper freezes several different model backbones and evolves the harness around each. It also tests transfer to **Windows Agent Arena** with the evolved harness frozen.

This is strong experimental design for a harness paper because the solver weights stay fixed inside each comparison.

## Results that matter

Full OSWorld-Verified improvements include:

| Frozen backbone | Seed | GUI-HARVEST | Gain |
|---|---:|---:|---:|
| Qwen 8B-class | 29.49 | **36.83** | +7.34 |
| Qwen 32B-class | 38.61 | **50.94** | +12.33 |
| OpenCUA 32B | 30.71 | **34.24** | +3.53 |
| OpenCUA 72B | 37.65 | **42.33** | +4.68 |
| Gemini 3.1 Pro | 66.46 | **73.37** | +6.91 |
| GPT-5 | 55.20 | **62.42** | +7.22 |

Frozen transfer to Windows Agent Arena also improves:
- Qwen-32B: roughly **38.21 → 44.68**;
- GPT-5: roughly **50.88 → 64.75**.

A long-horizon Gemini setting reaches about **79.1** with a reported cost below a much weaker high-cost comparison.

## Ablations: what causes the gain

Removing **visual evidence** causes a large drop: text-only traces omit the state needed to diagnose GUI failure.

Removing the **cross-task behavior-mode clusterer** also hurts: single-task repairs overfit specific screens/actions instead of recurring mechanisms.

Repeated rollouts matter because GUI execution is stochastic. A one-off click error should not create a permanent harness rule.

These ablations make the paper especially relevant to credit assignment.

## Why pre-registration matters

Without a predicted effect, a patch can score higher by chance and the engineer can invent a post-hoc explanation.

Pre-registration makes the claim falsifiable:
"this patch should cause observation X before action Y."

If the task score improves but the predicted behavior never happens, the optimizer should not assign causal credit to the claimed mechanism.

## Failure modes and limits

- Repeated GUI rollouts are expensive.
- Visual analyst judgments can still be wrong.
- Behavior-mode clustering can merge unrelated causes.
- Source mapping remains within a fixed runtime surface; the method does not redesign the full component graph.
- VM state reproducibility is essential.
- The same visual evidence can support several plausible root causes.

## Implementation checklist

Every finding should contain:
- task/run ID;
- decisive step;
- before/after image IDs;
- action;
- failure statement;
- confidence.

Every patch should contain:
- target mode;
- source range;
- predicted trace change;
- code-test result;
- behavior-test result;
- task-score delta;
- regressions.

## What RHEvolution should take from it

GUI-HARVEST provides a strong **failure-space decomposition**: behavior modes are discovered from evidence rather than predefined.

RHEvolution can connect that to **harness-space decomposition**:
- map modes to current owners;
- split an owner when distinct modes repeatedly map to different source/trace regions;
- fuse owners when the same mode requires both;
- require pre-registered behavioral effects for structural changes.

This is one of the best templates for making RHEvolution's credit assignment empirically defensible.
