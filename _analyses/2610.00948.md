## One line
An automatic harness optimizer for GUI agents with frozen backbones: repeated task executions feed four optimizer roles (Evidence Analyst → Cross-task Clusterer → Harness Engineer → Validator) that turn observed failures into reusable, behavior-validated code edits; Qwen3-VL-32B-Instruct gains +10.16 pp on OSWorld-Verified Test (53.18%), and it beats a GUI-adapted Self-Evolving Harness under the same backbone and initial harness.

## The problem
GUI agents have an *executable* harness (how observations are assembled, actions executed, verification/recovery/termination controlled), and automatically optimizing it has three GUI-specific difficulties: (1) model intent must be reconciled with observed visual effects — a textual trace can claim success while a dialog stays open; (2) failures must be diagnosed under execution variability, where one bad run hides behind stochasticity; (3) task-specific findings must be lifted into reusable runtime changes, not one-off patches.

## How it works
GUI-HARVEST runs a budgeted self-improvement loop (at most B=10 rounds, P=5 promotion attempts per harness state) with four roles. The **Evidence Analyst** compares K=3 repeated runs of the same task from clean environment snapshots, aligning text/actions/before-after screenshots per step via the GAFT toolkit, and produces findings that identify the decisive failed step with links to step-level evidence (a deterministic verifier checks citation consistency before retaining findings). The **Cross-task Clusterer** groups verified findings into open-vocabulary "behavior modes" — recurring mechanisms with a membership test and behavioral target, discovered without a fixed taxonomy, supported by at least two tasks. The **Harness Engineer** translates selected modes into bounded code patches, recording an update plan *before* GUI evaluation that links target modes to the source surface, the proposed edit, predicted observable behavioral effects, and invariants that must hold. The **Validator** runs L0/L1 code checks, GUI evaluation, and behavioral checks (did the predicted behavioral effect actually occur?), promoting candidates that pass and rolling back on rejection; an update ledger records edits, predictions, scores, and decisions to guide subsequent proposals. Search uses a 15-step budget, validation sees only aggregate scores, and the final harness is frozen for sealed-test evaluation.

## Key results
On OSWorld-Verified across six frozen backbones, GUI-HARVEST improves Test and Full scores for all six under a unified protocol; Qwen3-VL-32B-Instruct gains +10.16 pp Test (53.18%) and +12.33 pp Full (50.94%). Gemini 3.1 Pro reaches 79.14% at 100 evaluation steps without per-task reruns. Evolved harnesses transfer to WindowsAgentArena at 50 steps without further optimization. With the same backbone and initial harness, GUI-HARVEST outperforms a GUI-adapted Self-Evolving Harness. Ablations: removing visual evidence is the biggest drop (to 44.54%), removing the Cross-task Clusterer costs ~7.5 pp, single-rollout diagnosis (K=1) costs 5.7–7.8 pp, and a hard-score-gate-only variant selects worse harnesses than the behavioral-check version. Code at github.com/GaryYang12345/GUI-HARVEST.

## How it relates to adaptive decomposition
This is harness evolution done with serious engineering discipline, and several of its primitives map onto adaptive decomposition's needs. The "behavior mode" abstraction — recurring mechanisms with membership tests, discovered across tasks rather than imposed by taxonomy — is a concrete answer to the granularity question: it is a discovered decomposition of failure space, one step short of a discovered decomposition of harness structure. The pre-registration discipline (engineer records predicted behavioral effects *before* evaluation, validator checks them) is the honest version of validation gating the user's own loop needs: acceptance without validation was the named failure mode of the Self-Evolving Harness work this paper outperforms. Most relevant: the update ledger and promotion/rollback rule is a working instance of a meta-controller's decision policy — accept, reject, retry differently. The contrast: the engineer edits are bounded patches to a fixed runtime surface, never a restructuring of the harness into new components; adaptive decomposition's split/fuse is the more radical version of what GUI-HARVEST does conservatively.

## Limits and open questions
All optimization evidence comes from OSWorld-Verified; the WindowsAgentArena transfer is a single checkpoint, not a repeated study. K=3 repeated rollouts per task is load-bearing (K=1 loses most of the gain), so the method is expensive where rollouts are — cost scaling to longer-horizon or API-billed tasks is unaddressed. The behavior modes are regenerated from the current harness's executions after each promotion, but modes supported by only two tasks could still encode benchmark-specific quirks; the "reusable" claim rests on one transfer target. The engineer operates within a fixed capability manifest and bounded patches — genuinely structural harness redesign is out of scope.
