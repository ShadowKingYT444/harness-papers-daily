## What is actually new

This paper shows that **model quality and harness quality cannot be ranked independently**.

The same model can move up or down the leaderboard when only the harness changes. A model's vendor harness is not always its best harness. The useful object is the **model-harness pair**.

The paper then studies matched trajectories to explain *why* the fit changes, especially how errors and recovery information are passed between harness and model.

## Mental model

Model A may be strong at self-recovery if it receives raw tool errors. Harness X sanitizes those errors into a short generic message. Model A loses useful information.

Model B may be less robust to malformed tool calls. Harness Y automatically repairs them before execution. Model B benefits more.

So "Harness Y is better" is not a universal statement. Its behavior can complement one model and interfere with another.

## Key objects and state

- **Configuration:** one model × one harness.
- **Matched task:** same task executed by several configurations.
- **Trajectory divergence point**
- **Initiator label:** model, harness message, or harness direct action.
- **Failure handoff:** information returned after an action fails.
- **Recovery action**
- **Ranking reversal:** relative model order changes across harnesses.
- **Standard trajectory format:** makes cross-harness analysis possible.

## Analysis loop

~~~mermaid
flowchart TD
    A["Same task set"] --> B["Run many model × harness configurations"]
    B --> C["Normalize trajectories"]
    C --> D["Match runs for the same task"]
    D --> E["Locate first important behavioral divergence"]
    E --> F["Inspect error handoff + recovery"]
    F --> G["Label initiator: model / harness message / harness action"]
    G --> H["Explain which harness behavior complements which model"]
~~~

## Experimental setup

The study evaluates **66 model-harness configurations**.

Harnesses include systems such as:
- OpenHands;
- DSH;
- PI;
- openJiuwen;
- Codex;
- Claude Code.

The dataset contains more than **6,000 scored runs** and a similarly large set of full conversations, with reward, cost, token, and time fields normalized for analysis.

The experiments focus mainly on coding/terminal-agent tasks.

## Results that matter

Large ranking reversals appear.

For example, one Opus-class model on a terminal-agent benchmark reports markedly different scores across harnesses, with some harnesses around the high-0.5/low-0.6 range and another near **0.69**.

The paper also finds:
- the vendor-provided harness is not always the best for its own model;
- error-recovery behavior is a major source of pair-specific differences;
- some useful actions originate directly from harness logic, while others come from a model after the harness exposes the right evidence.

The key result is not one leaderboard number. It is that the ranking itself changes when the harness changes.

## How trajectory attribution works

Matched trajectories let the analysis distinguish:

**Model-initiated recovery**
The harness reports enough information and the model fixes its own mistake.

**Harness-message-initiated recovery**
A harness-generated warning/instruction causes the model to recover.

**Harness-action recovery**
The scaffold repairs or performs an action directly.

These are different failure mechanisms. If the harness hides an error and the model never sees it, blaming the model is wrong.

## Why this matters for decomposition

A useful component boundary may depend on the solver model.

For a strong model:
- leave more reasoning/control inside the model;
- keep the harness lean.

For a weaker/less robust model:
- explicit parsing, retries, verification, or recovery components may be valuable.

Therefore a decomposition learned for one solver should not automatically be called universal.

## Failure modes and limits

- Most benchmarks are coding/terminal domains.
- Correlation in matched trajectories is not always causal proof.
- Model/harness versions change quickly.
- Some harnesses expose different tools, making "same model" comparisons partly interaction-space comparisons.
- The study analyzes fit; it does not propose a harness optimizer.

## Implementation checklist for RHEvolution

Every experiment must record:
- solver model/version;
- harness version;
- tool interface;
- error messages visible to model;
- which component initiates recovery.

When mapping trace failures to owners, distinguish:
- harness prevented evidence from reaching model;
- model saw evidence and failed;
- harness direct action was wrong.

## What RHEvolution should take from it

Do not optimize one decomposition and claim it is "the best harness."

Test at least:
- one weaker solver;
- one strong solver;
- ideally a cross-model transfer condition.

A useful RHEvolution result would show which components transfer and which are model-specific. Adaptive decomposition may itself need the solver identity as an input.
