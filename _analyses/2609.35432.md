## One line
Proposes "Physical Coding" — representing both world state and policy as executable code — and a versioned generate-evaluate-select loop through which a robot agent's harness, tools, data, and model co-evolve with independent evaluation gates and rollback.

## The problem
VLA (vision-language-action) and world-action models map observations straight to action chunks, so task requirements, progress, constraints, and recovery logic are implicitly buried in action sequences: a small viewpoint or layout change can collapse success, and nothing about a failure is inspectable or reusable. The authors' diagnosis is representational, not capacity-based: what's missing is an interface where task state, execution, and feedback exist as objects that can be checked, edited, versioned, and rolled back. Digital coding agents already work this way (explicit state, tool calls, verification, revision as code), so the paper ports that working pattern to the physical world — where actions are delayed, noisy, and irreversible — and builds a self-evolution program on top of it.

## How it works
The core abstraction is **Physical Coding**: two coupled executable artifacts. *Code as World* records objects, relations, observations, constraints, and progress predicates; *Code as Policy* organizes planning, tool calls, verification, recovery, and execution. Because both are code, a failure can be attributed to a missing state variable, a bad constraint, the wrong tool, an invalid workflow branch, or a weak verifier — and the implicated artifact can be edited and re-tested rather than the whole policy being retrained.

Self-evolution targets four coupled components — the **harness** (tools, workflows, verifiers, recovery), the **model**, **data & environments**, and **embodiment/compute** — with representation/interface evolution cutting across all four. Each round runs a 7-step loop: (1) Specify — freeze tasks, seeds, budgets, protocol; (2) Execute — run current and candidate bundles, recording typed traces; (3) Verify — an evaluator *independent of the proposing model* checks semantic predicates, safety, provenance; (4) Diagnose — localize the limiting factor via trace inspection and ablations; (5) Propose — a bounded edit to the implicated artifact; (6) Evaluate — static checks, regression tests, canary rollouts, held-out comparison against the frozen parent; (7) Select & commit — admit only if improvement, safety, provenance, and compatibility gates pass, otherwise roll back to the parent version. The unit of evolution is a versioned artifact bundle a_v = (W_v, P_v, H_v, D_v, M_v, E_v) covering world representation, policy, harness, data, memory, and evaluator. Crucially, the world representation itself is evolvable: the agent may eventually discover new object types, relations, affordances, progress predicates — and new control decompositions — when the existing representation can't explain a failure.

The authors instantiate this with **HexaAnything**, a physical coding agent whose harness maintains task state, coordinates execution, verifies intermediate outcomes, and adapts actions, calling tools ranging from perception/planning modules to VLA policies (which become just another tool, stripped of task decomposition and recovery duties).

## Key results
- **Harness effect, fixed action model** (RoboCasa365, XR-1 VLA as the action tool): HexaAnything driven by GPT-5.6-Sol raises success 34.3%→38.3% on Composite-Unseen, 54.8%→61.5% on Composite-Seen, 56.6%→61.1% overall. Case studies at 100 seeds: LoadKebabSandwich 17%→48%, PortionHotDogs 22%→37%, WaffleReheat 53%→70%. The same-model coding agent Codex reaches 59.5% overall — 1.6 points behind HexaAnything.
- **Model evolution**: HexaModel v0.1 (Qwen3.8-27B fine-tuned on 1.0K harness-returned agent traces + 9.3K VQA examples, 38.8% of 178.6M training tokens) beats its base on every split when placed back in the same harness — 61.7% overall, 0.6 points above GPT-5.6-Sol and ahead on every split. Evidence that verified traces internalize into the weights.
- **Tool evolution** (RoboDojo, fixed task + fixed evaluator, programming agent revises tools from failed traces): Fold cloth 0%→80%, Pour vase 40%→100%, Press by number 0%→100% over two revision rounds — non-monotonic (Pour vase dipped to 0% in round 1 before recovering), weights unchanged throughout.
- **PhyBench** (simulated physics lab: agent designs and runs experiments): all three frontier models keep mean relative error under 5% — e.g., Opus 5.5 gets spring constant to 1.3% and g to 1.0%.
- **Real dual-arm robot** (AgileX): 5 of 7 tabletop tasks succeed in all 3 trials, and 2.7–3.5x faster than published same-model references (tic-tac-toe in 5.0 min vs 13.6; block-in-bowl with 4.7x fewer tokens). Tools also evolve on the physical robot with rollback of two rejected versions.

## How it relates to adaptive decomposition
This is the strongest published statement of *recursive harness self-improvement as an explicit program*: the harness revises its own tools, workflows, verifiers, and representations through a gated generate-evaluate-select loop with rollback to the parent version — the closest analog to adaptive decomposition's "revert when local and global correctness disagree" instinct, and the "diagnose → localize the limiting factor" step is the direct counterpart of splitting failing components. Two gaps keep it from being the same mechanism: the decomposition is never *agent-discovered through recursive splitting* — the four evolution targets are a human-designed taxonomy, and edits are bounded revisions to implicated artifacts, not a harness that splits a failing component into finer subproblems with independent budgets or fuses working ones. And the paper is explicit that coordinated co-evolution of all four targets is future work; the experiments only demonstrate harness/tool evolution plus one data-to-model update. Still, its insistence on versioned parents, independent hold-out evaluators, and provenance as *attribution infrastructure* ("a better harness is not a better model") is a design lesson any adaptive-decomposition implementation should steal.

## Limits and open questions
The evidence is preliminary by the authors' own admission: the harness effect is measured with one action model (XR-1) on one benchmark, the margin over the same-model Codex baseline is only 1.6 points overall, tool-evolution rates rest on five seeds, and real-robot results are three trials per task with references from different hardware. Full four-target co-evolution — model architecture search, embodiment change, unrestricted self-rewriting — is explicitly not demonstrated. Open problems they name: preventing the model and verifier from co-adapting (the evaluator-gaming risk), learning physical causality from sparse trajectories, keeping lifelong memories private, and combining expert corrections with simulator and real-robot failures without overfitting to a self-generated evaluator. Section 8.2 also notes they designed longer-horizon decomposition tasks (agent must decompose into subgoals itself, objects hidden in drawers, 10K-step cap) but haven't evaluated anything on them yet.
