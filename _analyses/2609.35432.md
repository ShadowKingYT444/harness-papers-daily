## What is actually new

This paper proposes a broad framework for self-evolving coding agents in physical environments by representing both **world state and control policy as code**.

Its practical contribution is a versioned improvement cycle:
specify → execute → independently verify → diagnose → propose a bounded edit → regression/canary test → commit or rollback.

The strongest lesson is not a new search algorithm. It is an **artifact discipline** that makes self-modification inspectable.

## Mental model

Physical agents fail at many layers:
- wrong world representation;
- bad tool;
- bad recovery branch;
- weak verifier;
- model reasoning error.

If all state lives in hidden model context, the optimizer cannot cleanly target the cause. This framework externalizes important state and control into code.

A failure can therefore point to an explicit artifact. The system can edit that artifact, rerun a canary, and retain the previous bundle if the edit is harmful.

## Key objects and state

- **Code as World:** executable/stateful representation of objects, relations, constraints, progress.
- **Code as Policy:** planning, tool use, verification, recovery, and action logic.
- **Artifact bundle:** world state, policy, harness, data, memory, evaluator.
- **Independent evaluator:** separate check from the model proposing the edit.
- **Canary rollout:** small validation before wider acceptance.
- **Version / parent pointer:** every accepted bundle has provenance.
- **Rollback:** restore trusted parent.

## Improvement loop

~~~mermaid
flowchart TD
    A["Specify task, constraints, budget"] --> B["Execute current artifact bundle"]
    B --> C["Independent evaluator checks result"]
    C --> D["Diagnose limiting artifact"]
    D --> E["Propose bounded edit + expected effect"]
    E --> F["Static tests / regression tests"]
    F --> G["Canary rollout"]
    G --> H{"Evidence clears gate?"}
    H -- "No" --> I["Rollback to parent"]
    H -- "Yes" --> J["Commit versioned bundle"]
    J --> B
~~~

## Step-by-step implementation

1. Externalize important world state into files/data structures.
2. Externalize recurring control logic into code instead of relying on prompt memory.
3. Define an artifact manifest: source, data, tools, memory, evaluator, model checkpoint.
4. Run the current bundle and save the complete execution trace.
5. Use an evaluator separate from the editing model where possible.
6. Diagnose the earliest artifact whose behavior makes the failure likely.
7. Propose one bounded edit and state the expected observable effect before testing.
8. Run static and unit tests.
9. Run a small canary task set.
10. If the edit passes, create a new bundle version with a parent pointer.
11. If it fails, restore the parent without patching forward from a broken state.
12. Only later use successful verified traces for optional model training.

## What has actually been demonstrated

The paper spans simulated and physical tasks. Reported examples include:

- a RoboCasa setting where a harnessed system improves a composite/unseen score from about **34.3 to 38.3** relative to the referenced base;
- physical/tool evolution experiments where explicit tool changes improve task completion;
- a PhyBench-style validity study where strong frontier models produce nearly all valid artifacts in some conditions;
- real-robot tabletop experiments where the system completes **5 of 7** tested task types across repeated trials.

These results show that artifact-level control can matter. They do **not** constitute one clean end-to-end ablation of every proposed co-evolution target.

## Why the verification architecture matters

Self-modification creates a special danger: the system can alter the thing that judges it.

The paper's safer pattern is:
- keep important acceptance checks independent;
- require explicit evidence before commit;
- retain a known-good ancestor;
- test the changed bundle on small canaries before broad deployment.

For research, this also improves causal clarity. A versioned bounded edit is easier to study than an agent that silently changes prompts, tools, memory, and evaluator together.

## Failure modes and limits

- The paper is broad; some sections are framework proposals rather than fully isolated experiments.
- Real-robot trials are few.
- Independent evaluation is only useful if the evaluator actually measures the intended property.
- Artifact categories are still human-defined.
- Complex cross-artifact failures can resist single-target diagnosis.
- Optional later model training makes attribution harder if mixed with harness results.

## Implementation checklist

Version:
- code;
- tools;
- memory;
- task/evaluator definitions;
- environment config;
- model checkpoint ID.

For every candidate record:
- parent;
- diagnosis;
- target artifact;
- patch;
- predicted behavior;
- canary results;
- regression results;
- promotion decision.

Keep evaluation code in a trust boundary outside ordinary edit permissions.

## What RHEvolution should take from it

Use this paper as the **operational safety layer** around structural search.

Every RHEvolution split/fuse should be:
- versioned;
- tied to an explicit diagnosis;
- evaluated by an independent gate;
- reversible;
- tested first on canaries.

The paper does not solve adaptive decomposition. It gives the infrastructure that makes adaptive decomposition experimentally credible and recoverable.
