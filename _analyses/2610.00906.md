## What is actually new

ActiveSaddler optimizes **which training scenarios the harness optimizer sees next**.

It converts failed traces into learned failure-pattern "arms." A controller estimates which patterns still contain useful learning progress and decides whether to:
- revisit a known failure pattern;
- explore unseen scenarios to discover new weaknesses.

The critical result is that **granularity matters**. Coarse hand categories lose signal, but making every individual scenario its own arm fragments the evidence. Learned failure patterns sit between those extremes.

## Mental model

Suppose an optimizer has 1,000 tasks and 100 evaluation calls left.

Uniform sampling wastes calls on:
- already solved tasks;
- many near-duplicate failures;
- failure types that current edits cannot improve.

ActiveSaddler treats each recurring failure mechanism like an arm in a non-stationary bandit. Its value is not "current score." It is expected **future learning progress**.

As the harness fixes one weakness, the useful curriculum shifts to another.

## Key objects and state

- **Scenario pool**
- **Failed traces**
- **Failure-pattern arm:** learned recurring mechanism.
- **Dynamic arm set:** new arms appear as new failures are discovered.
- **Arm statistics:** recent attempts, improvements, unresolved rate.
- **Learning-progress estimate**
- **Draw action:** explore unseen scenarios.
- **Pull action:** sample from a known failure-pattern arm.
- **Underlying harness optimizer:** e.g. AutoSaddler or GEPA.

## Curriculum loop

~~~mermaid
flowchart TD
    A["Current harness"] --> B["Run selected scenarios"]
    B --> C["Extract failures from traces"]
    C --> D["Cluster / assign failures into pattern arms"]
    D --> E["Update arm learning-progress estimates"]
    E --> F{"Controller action"}
    F -->|Draw| G["Sample unseen scenarios"]
    F -->|Pull| H["Sample cases from high-value known arm"]
    G --> I["Underlying harness optimizer patches system"]
    H --> I
    I --> A
~~~

## Step-by-step implementation

1. Maintain a pool of not-yet-used training scenarios.
2. Run initial tasks and create failure descriptions from traces.
3. Group semantically/mechanistically similar failures into an arm.
4. Store representative cases and recent improvement for each arm.
5. Estimate how much additional learning signal an arm likely contains.
6. Decide between exploration (new scenario) and exploitation (known arm).
7. Feed the chosen scenarios into a normal harness optimizer.
8. After the harness changes, rerun selected cases and update arm statistics.
9. Create new arms when unseen failure mechanisms appear.
10. Merge or retire arms that become redundant/solved.
11. Keep a final held-out benchmark that never participates in curriculum choice.

## Experimental setup

The method is tested as a curriculum controller for harness optimization on:
- **GAIA2**
- **Terminal-Bench 2.0**

It is also paired with another optimizer (GEPA) to test whether the curriculum idea transfers beyond AutoSaddler.

## Results that matter

Compared with fixed-order AutoSaddler, ActiveSaddler reports roughly:
- **+4.4 percentage points** on GAIA2;
- **+7.5 points** on Terminal-Bench 2.0.

When applied to GEPA, the reported average moves about **54.2 → 57.2**, suggesting the curriculum mechanism is not tied to one harness optimizer.

## Granularity ablation

This is the most important result for RHEvolution.

Compared with learned failure-pattern arms:

| Arm representation | GAIA2 change | Terminal-Bench change |
|---|---:|---:|
| Coarse categories | **-3.0 pp** | **-10.8 pp** |
| Every scenario as own arm | **-3.6 pp** | **-6.7 pp** |

Too coarse:
- unrelated failures share one budget/statistic.

Too fine:
- evidence cannot accumulate across related cases.

The learned intermediate granularity performs best.

A fixed exploration schedule also falls by roughly **4.5 points** on GAIA and **8.3** on Terminal-Bench versus adaptive draw/pull control.

## Search behavior over time

The controller explores more early and revisits known patterns more later:
- draw/explore rate drops from about **44% in the first half** to **20% in the second**.

When it chooses to pull a known arm, those arms have a much higher unresolved-failure ratio than randomly explored cases, showing the scheduler is concentrating budget where weakness remains.

## Failure modes and limits

- Failure-pattern clustering is itself an LLM/representation decision.
- A wrong merge can hide distinct causes.
- A wrong split can fragment evidence.
- Non-stationary arm values require recent statistics; old scores become stale after harness changes.
- The system adapts training-data granularity, not harness-component granularity.
- Bandit gains depend on having enough scenarios to choose among.

## Implementation checklist

Per arm store:
- arm ID;
- representative failure explanation;
- member task IDs;
- current unresolved rate;
- recent candidate-parent gains;
- last sampled time;
- number of pulls;
- confidence.

Re-cluster periodically because fixes can change which failures are actually similar.

## What RHEvolution should take from it

This is direct empirical support for RHEvolution's **adaptive granularity hypothesis**.

Map the idea from failure arms to harness owners:
- too-coarse owner → mixed signals and weak credit;
- too-fine owner → too little evidence per component;
- adaptive split/fuse → maintain the granularity where evidence is coherent.

The split/fuse trigger can borrow ActiveSaddler statistics: learning progress, unresolved-rate heterogeneity, and evidence count per owner.
