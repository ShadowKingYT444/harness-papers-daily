## What is actually new

Mingbird is a hand-engineered case study showing that many apparent "small model limitations" are actually **harness failure forms**.

Instead of one large clever controller, it builds ten explicit mechanisms. Each mechanism targets one observed failure pattern such as context overflow, false completion, looping tool calls, or process faults.

Its research value is the mapping:
**concrete failure form → explicit mechanism → controlled measurement**.

That is what an automatic decomposition method should learn to reproduce.

## Mental model

A 2B model repeatedly fails a real task. It is easy to conclude "the model is too small."

But the trace may show:
- all context was consumed by tool schemas;
- the model declared completion before creating artifacts;
- it repeated the same command forever;
- the process died and state was lost.

Those are scaffold failures. A deterministic guard can fix them more cheaply than a larger model.

## Key mechanisms

The paper describes a set of local-first mechanisms. Important ones include:

- **M1 Flat prefill + net-zero budget:** load only the task-relevant tool surface so tool schemas do not consume the context.
- **M2 Chat/task layering:** casual chat does not enter the same tool-heavy loop as artifact-producing work.
- **M3 Finish gate + task/plan re-injection:** before accepting "done," re-read the original task and verify deliverables.
- **M4 Signature-level anti-loop:** detect repeated actions by normalized tool/argument signatures rather than only exact text.
- **Format rescue:** recover malformed tool-call/output formats.
- **Sandbox/edit safety:** constrain executable side effects.
- **Resilience/checkpoint layer:** survive encoding faults, empty turns, process kills.
- **Security boundaries:** separate unsafe actions from ordinary execution.

The exact numbered list is larger, but these illustrate the design pattern.

## Agent loop

~~~mermaid
flowchart TD
    A["User input"] --> B{"Chat or task?"}
    B -- "Chat" --> C["Lean conversational path"]
    B -- "Task" --> D["Route task and load bounded tool prefill"]
    D --> E["Model proposes action"]
    E --> F["Sandbox / edit / security guards"]
    F --> G["Execute tool"]
    G --> H["Normalize observation + resilience handling"]
    H --> I{"Repeated action signature?"}
    I -- "Yes" --> J["Escalating anti-loop intervention"]
    I -- "No" --> K{"Model claims completion?"}
    J --> E
    K -- "No" --> E
    K -- "Yes" --> L["Finish gate re-reads original task + plan"]
    L --> M{"Required artifacts / checks present?"}
    M -- "No" --> E
    M -- "Yes" --> N["Accept completion"]
~~~

## Why the finish gate matters

A model can confidently say "done" without creating the requested output.

The finish gate does not merely add "please double-check" to the system prompt. It intercepts the completion event, re-injects the task/plan, and can reject the finish claim.

That is an **executable control point**. It changes the action space, not only the model's advice.

## Experimental setup

The main LRAB comparison is deliberately controlled:
- **4 harnesses**
- **4 open models from about 2B to 35B**
- **18 real tasks**
- same machine/budgets/scoring
- **288 harness-model-task cells**

The paper also evaluates on a third-party τ²-style benchmark.

## Results that matter

Overall LRAB score:

| Harness | Score |
|---|---:|
| **Mingbird** | **0.886** |
| goose | 0.631 |
| opencode | 0.479 |
| agent-mini | 0.405 |

Mingbird by model size rises roughly:
**0.821, 0.876, 0.906, 0.941**.

On the third-party benchmark, Mingbird reports about **0.856** versus **0.791** and **0.737** comparison arms.

A frontier-model probe on the same 18 tasks spans roughly **0.478 to 0.997** across harnesses. That is strong evidence that harness choice can strand capability even for strong models.

## Ablation: be careful with the evidence

One leave-one-mechanism-out experiment at 2B reports:

| Disabled mechanism | Full baseline 0.821 → | Nominal delta |
|---|---:|---:|
| Finish gate | 0.723 | -0.098 |
| Verification feedback | 0.772 | -0.048 |
| Anti-loop | 0.805 | -0.015 |
| Flat prefill | 0.818 | -0.003 |

However, the authors explicitly warn that same-condition replications move the 18-task mean by up to **0.069**, and bootstrap intervals cross zero. Several mechanisms were also developed with the benchmark in the loop.

A cleaner matched follow-up repeats full executable guards versus text-only finish support three times. All three paired comparisons favor the executable guards, with total gains about **+0.096, +0.133, +0.056**.

So the qualitative mechanism story is useful, but do not treat every single ablation delta as a precise causal estimate.

## Failure modes and limits

- Self-built benchmark shares authors with the harness.
- Some mechanisms were developed against benchmark failures.
- Single-cell long-horizon variance is large.
- Hand-designed components do not prove automatic decomposition works.
- Deterministic guards can block legitimate unusual behavior.
- Small-model design choices may be unnecessary for frontier models.

## Implementation checklist

For every mechanism keep:
- failure form;
- observable trigger;
- intervention;
- invariant/test;
- tradeoff;
- activation log;
- ablation evidence.

This makes the scaffold auditable.

## What RHEvolution should take from it

Mingbird is a **target behavior** for automatic component discovery.

RHEvolution should be able to see:
- premature completion → create/strengthen completion owner;
- action repetition → create anti-loop owner;
- context overflow → isolate context owner;
- execution faults → separate resilience owner.

The paper also warns against overclaiming ablations. RHEvolution needs repeated matched evaluations before saying a discovered component caused a gain.
