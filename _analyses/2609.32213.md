## One line
A query-level router that jointly picks a (model, harness) pair by learning separate shared model and harness embeddings plus a CP-tensor-inspired three-way interaction term, so evidence from observed pairs transfers to unobserved model–harness combinations.

## The problem
In agentic deployments, performance depends on both the LLM and the harness (the scaffold managing tool use, observations, execution) — and the best model changes across harnesses, so model-only routing is suboptimal. But the candidate route space grows as |models| × |harnesses| while execution histories cover only a subset, creating a coverage bottleneck: treating each pair independently wastes evidence, and strong unobserved pairs can't be scored. The paper asks how to route queries over the joint model–harness space, capturing their compatibility and generalizing to combinations never executed.

## How it works
Define a route r = (m, h). The router learns a scorer S(q, r) and picks r̂(q) = argmax over a feasible pool R (which may include unobserved pairs). The key design is *factorized representations*: the query gets embedding q̃ = W_q x_q (x_q frozen, Qwen3-Embedding-8B in the paper); each model gets u_m = W_m[e_m; P_m z_m], each harness u_h = W_h[e_h; P_h z_h; T_h t_h], where e are learned identity embeddings, z are behavioral summaries (each component's observed success vector over training queries), and t_h is a frozen harness-description embedding. All live in ℝ^d and are shared across routes, so one outcome updates every route containing that model or harness.

The score is S(q, m, h) = S_M + S_H + S_MH. Component terms are bilinear in query and component: S_M = w_Mᵀ(u_m ⊙ q̃), S_H = w_Hᵀ(u_h ⊙ q̃). The interaction term, inspired by canonical polyadic (CP) tensor decomposition, is a three-way product S_MH = Σ_k w_k q̃_k u_m,k u_h,k — it captures how a harness's suitability shifts depending on the model *for this query*, which the additive terms cannot express. Everything is trained jointly with binary cross-entropy on the observed route outcomes Ω. For unseen pairs there are no pair-specific parameters: scoring uses only the shared factors, with a cold-start policy of zeroing identity/behavioral embeddings for never-observed components while keeping harness descriptions. Cost-aware selection is r̂_λ(q) = argmax_r ŷ(q,r) − λĉ(r), with ŷ = σ(S) and ĉ the mean observed route cost.

To reimplement the core: (1) collect (query, route, success/failure) outcomes for some model–harness pairs; (2) build per-component success-vector features plus identity embeddings and harness text descriptions; (3) train the factorized scorer S = w_Mᵀ(u_m ⊙ q̃) + w_Hᵀ(u_h ⊙ q̃) + Σ_k w_k q̃_k u_m,k u_h,k with BCE; (4) at inference score all feasible (m, h) pairs, including unobserved ones, and argmax. The CP interaction term is the piece that makes it "joint" rather than two independent routers.

## Key results
Benchmark: HM-ROUTER-BENCH, curated from 12 public agent benchmarks (TerminalBench 2.1, TauBench Airline, CORE-Bench, GAIA, SWE-bench Verified, etc.) — 293 routes, 73 models, 25 harnesses; five fixed 70/30 query splits; metric is oracle-normalized routing accuracy. HM-Router reaches 73.93% mean vs 66.65% for the strongest learned baseline (IRT), 66.61% (Avengers), 65.49% (EmbedLLM), 49.58% (Random) — a +7.3 pp gain over the best baseline. Cost tradeoff (six-benchmark HM-ROUTE-COST subset): leads at all seven dollar budgets, +8.5 pp over Avengers-Pro at $2/task. Unobserved combinations: progressively withholding train-best routes, allowing hidden pairs at inference beats observed-only routing by 1.6 pp at 25% removal, 15.8 pp at 90% removal, and 27.9 pp with one observed route left; at 90% it also beats the observed-pool oracle. Sample efficiency for a held-out route/model/harness: with just 1 training query, +5.0 pp over EmbedLLM; with 20, +6.9 pp. Held-out benchmarks (trained on other benchmarks): 49.4% vs 32.9% for IRT. Correctness forecasting: AUC 0.698 vs 0.643 EmbedLLM. Ablation: dropping the interaction term costs 5.4 pp (73.93 → 68.51); sign agreement on model-dependent harness preference changes 55.7% → 84.8%. Representations: 14/18 harnesses have nearest neighbor in the same design family (4.3 expected by chance). Interaction examples: OpenClaw(local)+Sonnet 4.6 performs 18.4 pp above additive expectation; +DeepSeek-V4 Flash 27.4 pp below — predicted deviations track observed ones (r = 0.98). Overhead: 25.4 ms query encoding + 0.2 ms scoring per query vs >100 s agent execution; training <4 s per benchmark. Code at https://github.com/hmarkc/HM-Router.

## How it relates to adaptive decomposition
Not at all, structurally: HM-Router selects among a fixed, human-curated pool of (model, harness) pairs per query — there is no decomposition of any problem or harness, no search over structures, no splitting, no parallel component improvement, no fusion, no revert. The 25 harnesses are fixed artifacts (Claude Code, SWE-agent, OpenClaw, etc.); the router only ever *chooses* them. The one conceptual echo is compositional: shared component factors let evidence about a model in one pairing inform predictions for that model in another — a form of component-level knowledge reuse across routes. But that is routing-time inference, not an agent discovering a decomposition or evolving structure. It is orthogonal to both self-evolution and adaptive decomposition. Relevance 1: about harness selection, not harness improvement.

## Limits and open questions
All 25 harnesses are fixed and hand-curated — the router cannot invent, modify, or decompose a harness, so it inherits the ceiling of the pool. The cold-start policy (zeroing embeddings for unseen components) is crude; behavioral summaries z require probe executions for any new component, and feasibility constraints (a harness needing interfaces a model lacks) are taken as given rather than learned. Evaluation is per-query routing accuracy/cost, not end-to-end task throughput, and the benchmarks are all existing public agent benchmarks — the "unseen benchmark" test still reuses the same harness set. Open: could a router like this *generate* new (model, harness) combos worth evaluating (active coverage of the |M|×|H| space), and could its learned compatibility embeddings guide which harness to evolve for which model — a bridge from routing to harness optimization?
