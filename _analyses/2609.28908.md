## Main idea
This paper evolves harnesses for hardware debugging and finds a major problem: different harnesses discover useful behaviors, but these gains do not reliably combine into one best harness. The archive can become stronger than any single final candidate.

## Key concepts
- **Subject model:** The fixed model that solves the debugging task.
- **Optimizer model:** A separate model that changes the harness.
- **Activation check:** A test that confirms a proposed harness rule actually ran.
- **Archive:** A store of candidate harnesses, traces, scores, and lineage.
- **Consolidation:** Combine useful discoveries from several candidates into one stronger harness.

## Optimization loop
```mermaid
flowchart LR
    A[Current harness] --> B[Branch candidate harnesses]
    B --> C[Activation check]
    C --> D[Run hardware tasks]
    D --> E[Classify failures and scores]
    E --> F[Promote or archive]
    F --> B
```

## How it works
1. An optimizer proposes new prompt or runtime changes.
2. Each candidate gets an isolated directory and full lineage record.
3. The system checks that the proposed change is active.
4. Candidates run on root-cause debugging tasks.
5. Promising candidates get more trials.
6. Good candidates can become the new incumbent, but other candidates remain in the archive.
7. The authors also try whole-harness edits and later combinations of earlier rules.

## Why it matters for RHEvolution
The most useful result is negative: **useful specialist behaviors did not reliably consolidate**. One harness solved one group of tasks, and another solved a different group.

This is direct motivation for RHEvolution. Instead of forcing all useful behavior into one monolithic harness, RHEvolution can keep separate components, assign credit to each one, and fuse them only after a global test shows that the combination works.

## Evidence and limits
- Evolved harnesses improved task coverage and completion on the reported hardware tasks.
- The archive union solved more tasks than any one promoted harness.
- The strongest repeated hardware study used only 12 proprietary tasks.
- Candidate changes often touched several controls at once, so exact causal attribution is difficult.
