## What is actually new

This hardware-verification study exposes a negative result that many harness-evolution papers hide: **the archive can contain more capability than the final promoted harness**.

Different evolved harnesses learn different useful behaviors. Trying to compress those gains into one successor often fails. The paper therefore gives direct evidence for a consolidation problem: discovery and integration are different optimization problems.

## Mental model

Imagine two harnesses:
- Harness A is good at diagnosing clock-domain bugs.
- Harness B is good at register-reset bugs.

The archive can solve both task groups if you are allowed to choose A or B. But a "merged" harness can become worse than both because their instructions, tools, or control rules interfere.

The paper's important contribution is not only higher hardware-debugging scores. It shows that **specialist gains can be real but non-additive**.

## Key objects and state

- **Subject model:** fixed model that performs hardware root-cause debugging.
- **Optimizer model:** separate model that edits the harness.
- **Candidate directory:** isolated filesystem state for one harness.
- **Manifest:** records configuration and lineage.
- **Activation check:** verifies that the proposed change actually executes.
- **Search evaluation:** cheaper, noisier measurements used during evolution.
- **Confirmation evaluation:** repeated trials used to verify promising candidates.
- **Archive:** all candidates, traces, scores, and parents.
- **Consolidation attempt:** tries to combine useful rules from multiple candidates.

## Search loop

~~~mermaid
flowchart TD
    A["Seed harness"] --> B["Optimizer proposes candidate"]
    B --> C["Create isolated candidate directory + manifest"]
    C --> D["Activation check"]
    D --> E{"Change actually active?"}
    E -- "No" --> F["Reject as non-intervention"]
    E -- "Yes" --> G["Run hardware debugging tasks"]
    G --> H["Record exact-match correctness + completion + failures"]
    H --> I["Promote promising candidates to repeated confirmation"]
    I --> J["Archive candidate and lineage"]
    J --> K{"Complementary archive branches?"}
    K -- "Yes" --> L["Try consolidation / combination"]
    L --> M["Replay full task set"]
    M --> A
    K -- "No" --> A
~~~

## Step-by-step implementation

1. Fix the subject model. Otherwise you cannot tell whether gains come from the harness.
2. Give each harness candidate its own directory and immutable manifest.
3. Record the exact parent, patch, prompts, runtime controls, and task results.
4. Before scoring, run an activation test. A syntactically valid change that never executes should not receive credit.
5. Use a cheaper search set to screen candidates.
6. Promote only promising candidates to repeated confirmation trials.
7. Score more than one property: exact root-cause correctness, completion, and repeated success.
8. Keep non-winning candidates in the archive if they solve unique tasks.
9. Compute archive-union coverage: "how many tasks can at least one archived harness solve?"
10. Compare that with the best single harness.
11. When the union is much larger, attempt consolidation.
12. Re-test the complete task set after consolidation. Do not infer that two useful patches will compose.

## Experimental setup

The main repeated hardware study uses **12 proprietary design-verification root-cause tasks**.

For the Kimi-K3 subject model, the seed harness reports:
- first-trial success: **2/12**;
- successful on at least 2 of 5 repeated trials: **5/12**;
- pass@5: **5/12**;
- correct attempts: **17/60**;
- completed attempts: **34/60**.

The study then compares several evolution styles, including evidence-grounded and batched/causal variants.

## Results that matter

| Harness | First trial | Success ≥2/5 | Pass@5 | Correct attempts | Completed attempts |
|---|---:|---:|---:|---:|---:|
| Seed | 2/12 | 5/12 | 5/12 | 17/60 | 34/60 |
| Evidence-grounded evolved | **6/12** | **6/12** | 9/12 | 20/60 | 58/60 |
| Batched-causal evolved | 5/12 | 5/12 | **10/12** | **21/60** | **60/60** |

The two evolved harnesses together solve **11 of 12** tasks, but neither individual harness reaches that coverage.

A DeepSeek search selected a candidate whose validation score rose from **0.375 to 0.725**, yet replay on the full 12-task suite did not preserve the apparent gain. A longer MiniMax search reached **72 generations** and improved one metric from roughly **1/12 to 5/12** before plateau.

These are useful negative results: validation gains and long search do not guarantee consolidated generalization.

## What the results mean

The archive contains **specialization**. That is different from a noisy search artifact because different candidates repeatedly solve different task subsets.

The hard part is consolidation. An optimizer that only asks "which whole harness is best?" can throw away useful minority mechanisms. An optimizer that merges every useful mechanism can create interference.

This is exactly the situation where a component graph is preferable to one monolithic file.

## Failure modes and limits

- The strongest repeated study has only 12 proprietary tasks.
- Candidate changes can touch several controls, so causal attribution is imperfect.
- Exact-match debugging metrics can miss partially useful reasoning.
- Search-set overfitting is visible in the DeepSeek example.
- Archive-union performance assumes a way to route to the right specialist; the paper does not automatically solve routing.
- Consolidation attempts are not a complete search over all possible combinations.

## Implementation checklist

Always report:
- seed score;
- best individual candidate;
- archive union;
- merged/consolidated candidate;
- repeated confirmation score.

Keep candidate-level solved-task bitsets. They make complementarity measurable.

Add an activation test to every mutation. Otherwise a "good" candidate can receive a lucky score even though the intended change never ran.

## What RHEvolution should take from it

This paper is a direct argument for **preserving specialists instead of forcing immediate global consolidation**.

For RHEvolution:
- when two lineages solve different failure groups, preserve them as separate components;
- fuse only after a global paired test;
- use archive complementarity as evidence for splitting a monolithic owner;
- let routing/ownership decide when each specialist is active;
- report archive-union performance separately from the final fused harness so the paper does not hide lost capability.

A major RHEvolution metric should be **consolidation efficiency**: how much of the union of discovered gains survives in one composable final system.
