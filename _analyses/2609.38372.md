## What is actually new

This paper removes much of the hand-designed outer optimizer: **the same frozen model solves tasks and edits the harness it is currently running inside**.

The harness starts small. After each mixed-domain task batch, the agent reads its own traces, scores, grader feedback, repository, and persistent evolution notes. It can create, delete, or rewrite files. The next generation runs under that new harness.

This is a strong baseline for "just give a frontier agent broad edit access and let it improve the repo."

## Mental model

Many harness-optimization papers add:
- a separate critic;
- a mutation taxonomy;
- a fixed module map;
- a specialized search algorithm.

This paper asks whether those structures are necessary. Maybe a strong agent already knows how to inspect failures, edit code, and verify changes.

The answer is partly yes: useful mechanisms emerge. But whole-repository freedom does not solve credit assignment, validation, or diversity. Some benchmark components still regress.

That makes it an important null baseline for RHEvolution.

## Key objects and state

- **Seed harness:** deliberately small repository.
- **Same model as solver and optimizer**
- **Evolution batch:** mixed tasks from several domains.
- **Task traces and grader feedback**
- **Evolution notes:** persistent summary of prior lessons.
- **Whole repository:** broad editable surface.
- **Replay anchors:** older successful tasks mixed into later continual evolution.
- **Generation:** one complete solve → inspect → edit cycle.

## Optimization loop

~~~mermaid
flowchart TD
    A["Current harness version"] --> B["Solve mixed-domain evolution batch"]
    B --> C["Store traces, scores, grader feedback"]
    C --> D["Same agent reads repo + evidence + evolution notes"]
    D --> E["Create/delete/rewrite harness files"]
    E --> F["Run local repository checks"]
    F --> G["Commit next harness generation"]
    G --> H["Update evolution notes"]
    H --> A
    I["Replay older successful tasks"] --> B
~~~

## Step-by-step implementation

1. Build a minimal but working harness repository.
2. Freeze model weights.
3. Select a mixed-domain evolution batch.
4. Run the harness and save full traces plus any available grader feedback.
5. Re-enter the *same* model in an optimizer role.
6. Give it the repository, recent evidence, and persistent evolution notes.
7. Allow broad file creation/deletion/editing.
8. Require it to run tests or smoke checks before finishing the generation.
9. Commit the resulting repository as the next harness.
10. Run the next task batch.
11. In continual settings, mix replay tasks from earlier domains so the harness does not forget them completely.
12. Evaluate held-out ID and OOD tasks only from frozen generations.

## Experimental results

The paper reports a main evolution chain with strong gains.

At one later generation:
- ID average reaches about **60.17**, around **+4.48** over the seed and **+2.99** over the reported Codex comparison.
- Terminal-Bench 2.1 rises roughly **66.67 → 83.91**.
- SWE-Bench Pro rises about **51 → 61**.

On OOD tasks:
- average reaches about **70.45**, around **+12.64** over the seed;
- the reported Codex comparison is about **70.57**, almost identical overall;
- BrowseComp Plus moves roughly **34 → 90**, compared with Codex around **93**.

If BrowseComp is removed, the OOD gain is much smaller, so the huge average improvement is not uniform across every benchmark.

## What the agent actually discovers

The evolved harness develops mechanisms such as:
- output truncation / compaction;
- time limits;
- review steps;
- execution-control improvements;
- task-specific handling.

The interesting part is that these are not supplied as a fixed mutation menu.

That supports the idea that frontier models can discover scaffold mechanisms on their own.

## Why unrestricted editing is still not enough

Broad edit freedom can collapse into a narrow set of familiar changes. The model may repeatedly improve prompts/context while ignoring structural alternatives.

Also, a whole-repo successor gives one scalar outcome for many simultaneous edits. If score falls, there is little clean evidence about which edit caused it.

The paper reports regressions on some benchmark components, demonstrating that "agent knows how to code" is not the same as "outer loop has solved safe harness optimization."

## Failure modes and limits

- Main evidence comes from one stochastic evolution chain per setting.
- Whole-harness changes mix causes.
- Broad permissions increase leakage/security risk.
- Evolution notes can bias later generations toward earlier ideas.
- Replay helps forgetting but does not guarantee preservation.
- Same-model optimization can reinforce the model's own blind spots.

## Implementation checklist

This is the minimal monolithic RSI baseline:
- one repository;
- fixed model;
- task batches;
- trace/grader logging;
- optimizer prompt;
- persistent notes;
- version control;
- replay;
- held-out evaluation.

Do not add decomposition machinery to this baseline. Its purpose is to answer: "How far does an unrestricted strong agent get by itself?"

## What RHEvolution should take from it

RHEvolution must beat this baseline **after charging for its extra machinery**.

The claim cannot be merely "our agent can improve a harness." This paper already shows that.

The stronger claim is:
- adaptive owners make edits more attributable;
- split/fuse prevents monolithic search from getting stuck;
- component histories preserve gains;
- OOD transfer improves under the same or lower search budget.

This monolithic same-model loop should be one of the core baselines in the final experiments.
