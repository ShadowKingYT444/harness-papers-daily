## What is actually new

Turbo Harness converts the **waste from a completed global harness search** into a task-specific editor.

A normal harness optimizer tries many candidates and then keeps only one final global harness. Turbo Harness mines the accepted/rejected archive into a playbook, trains an editor to propose one small instance-specific patch, and applies that patch before a new task runs.

The key idea is: **the search archive can teach adaptation policy, not just identify a winner.**

## Mental model

A global harness is a compromise. Some tasks need aggressive exploration; others need conservative editing. Some require a special tool pattern; others are harmed by it.

During normal optimization, the archive already contains evidence about which edits helped which cases. Throwing that history away loses information.

Turbo Harness distills that evidence into:
- a playbook of edit patterns;
- an RL-trained editor that maps a new task to one patch.

At inference time there is one adaptation call, not another expensive search loop.

## Key objects and state

- **Global harness**
- **Search exhaust/archive:** candidates, diffs, traces, results, reflections.
- **Playbook:** conditions + successful/failed edit strategies.
- **Editor model**
- **Task instance**
- **Patch proposal**
- **Patch validity check**
- **Fallback:** unchanged global harness.
- **RL training data:** relative rewards among proposed patches.

## Training and inference loop

~~~mermaid
flowchart TD
    A["Completed global harness search"] --> B["Collect candidate diffs + outcomes + traces"]
    B --> C["Distill playbook: when edits helped or failed"]
    C --> D["For training task, editor proposes several patches"]
    D --> E["Evaluate patches"]
    E --> F["Use relative rewards to train editor with RL"]
    F --> D
    C --> G["New unseen task"]
    F --> G
    G --> H["One editor call creates one patch"]
    H --> I{"Patch valid / safe?"}
    I -- "No" --> J["Fallback to global harness"]
    I -- "Yes" --> K["Run instance-specific patched harness once"]
~~~

## Step-by-step implementation

1. Run a normal harness optimizer first.
2. Keep **all** useful search artifacts, not only the winner.
3. For each edit, record task features, parent state, diff, result, regression, and cost.
4. Summarize recurring edit strategies and failure conditions into a playbook.
5. Create editor-training tasks from the archive or fresh environments.
6. Ask the editor for several patches per training task.
7. Evaluate them under the real task metric.
8. Train the editor from relative reward among patches.
9. At deployment, provide the new task, global harness, and playbook.
10. Generate one bounded patch.
11. Run static/compatibility checks.
12. If invalid, use the global harness unchanged.
13. If valid, execute the task once with the adapted harness.

## Experimental evidence

The paper compares:
- global Meta-Harness-style optimization;
- playbook without RL;
- RL editor without playbook;
- playbook + RL editor.

On a SWE-smith-MR ablation with a frozen Haiku-class actor:
- neither playbook-only nor RL-only clearly beats the global Meta-Harness reference;
- the **combined playbook + RL editor reaches about 64%** in the reported setting.

That interaction matters: historical knowledge gives the editor useful priors, while RL teaches when/how to apply them.

## Reliability result

The paper also reports "solved across all repeated runs" rather than only mean success.

In one set:
- Haiku condition rises from about **20 to 28 of 50** issues solved consistently;
- a Gemini condition rises from about **26 to 42**.

At the same time, the set of issues solved in only one run shrinks substantially for the stronger setting.

This suggests task-specific adaptation can improve repeatability, not only best-case success.

## Budget caveat

Turbo Harness uses one pre-execution patch. Some comparisons use test-time methods that first execute, inspect failure, then rerun.

Those are different budgets. A fair comparison must count:
- adaptation-model calls;
- solver calls;
- reruns;
- environment cost.

## Failure modes and limits

- The editor inherits biases from the original search archive.
- A new task outside playbook coverage can receive a bad patch.
- RL training needs additional environment rollouts.
- Strong global harnesses leave less adaptation headroom.
- One patch is still whole-harness/local-file adaptation, not a learned recursive component graph.
- Fallback prevents invalid code but not valid-looking harmful behavior.

## Implementation checklist

Your search archive should include:
- task features;
- candidate-parent diff;
- accepted/rejected reason;
- per-task delta;
- failure category;
- resource delta.

Playbook entries should be conditional:
"when X evidence appears, edit Y because Z" rather than generic advice.

Keep editor and solver evaluations separate.

## What RHEvolution should take from it

RHEvolution will generate an even richer search exhaust because each owner has its own edit history.

Distill **component-specific playbooks**:
- what edits work for this owner;
- what split conditions were productive;
- when a fuse repaired coupling;
- what regressions recur.

This can turn expensive offline RHEvolution search into fast future adaptation without rerunning the complete structural search.
