## What is actually new

Growing Harness starts from a scaffold with almost **no task-solving strategy** and lets persistent control structure emerge from failure evidence.

Instead of asking the model to rediscover the same workflow inside every task context, a stronger offline optimizer turns repeated control decisions into executable code. The deployed agent then spends its LLM calls on task-specific semantic work while cheap code handles recurring control.

This is unusually important for RHEvolution because the harness can **grow new helper functions**. The structure is not only choosing from a fixed plugin menu.

## Mental model

Suppose a browser agent repeatedly needs to:
- inspect the page before clicking;
- recover after a missing element;
- retry a search with a different query;
- verify that a form actually submitted.

A normal context-heavy agent reasons through these decisions every time. Growing Harness notices that these are recurring control patterns and writes them into code.

The learning loop is therefore closer to program synthesis from failure than prompt optimization. Failures are localized to functions that actually executed. A repair must fix several failures, survive a held-out success gate, and then becomes part of one shared program.

## Key objects and state

- **Strategy-free scaffold:** fixed model and tool interfaces with very little control policy.
- **Function-level execution DAG:** records which functions and calls executed and in what dependency order.
- **Failure window:** several recent failed tasks repaired together.
- **Trace-local edit scope:** functions active in the failed executions.
- **Optimizer:** a stronger offline model with code-edit access.
- **Success-first gate:** held-out successful tasks that protect prior capability.
- **Shared harness:** one persistent executable program that accumulates accepted repairs.
- **Rollback checkpoint:** last accepted version.

## Growth loop

~~~mermaid
flowchart TD
    A["Minimal shared harness"] --> B["Run stream of tasks"]
    B --> C["Collect failed traces + function execution DAGs"]
    C --> D["Group a bounded window of failures"]
    D --> E["Find functions active in those failures"]
    E --> F["Offline optimizer edits those functions or adds helpers"]
    F --> G["Replay failure window"]
    G --> H{"Repairs several failures?"}
    H -- "No" --> I["Reject candidate"]
    H -- "Yes" --> J["Run held-out success gate"]
    J --> K{"Prior capability preserved?"}
    K -- "No" --> L["Rollback"]
    K -- "Yes" --> M["Commit reusable code to shared harness"]
    M --> B
~~~

## Step-by-step implementation

1. Build the smallest usable agent loop: task input, model call, tool execution, observation return, termination.
2. Instrument every function call so one trajectory can be represented as an execution DAG.
3. Run a stream of tasks and keep failed executions in a bounded queue.
4. When enough failures accumulate, select a small window rather than optimizing one case at a time.
5. Use the execution DAGs to identify source functions that were actually involved.
6. Give the optimizer those functions, the traces, and the failure outcomes. Permit new helper functions when needed.
7. Ask for one coherent repair that explains how it should address *several* failures in the window.
8. Replay the failure window. Reject edits that only repair a single isolated case if the claimed mechanism is supposed to be general.
9. Run a held-out gate containing previously successful tasks.
10. If the candidate harms old capability, restore the last accepted checkpoint.
11. If it passes, commit the code into the shared harness and continue collecting tasks.
12. Periodically remove dead or duplicated code; otherwise persistent growth becomes program bloat.

## What moves from the model into code

The optimizer is encouraged to separate two classes of work:

**Good code targets**
- deterministic validation;
- retry policy;
- routing;
- state tracking;
- repetitive parsing;
- known recovery procedures;
- cheap consistency checks.

**Keep in the LLM**
- ambiguous semantic interpretation;
- novel reasoning;
- open-ended search decisions;
- language understanding that is hard to specify deterministically.

That boundary is why the method can reduce deployed LLM calls so much.

## Experimental setup

The paper tests two long-horizon web/search settings:
- **BrowseComp-Plus**
- **WebArena-Verified**

It uses deployment models from roughly **4B to 120B parameters**. The same learned harness idea is tested across those different model capacities.

The comparison of interest is not only task accuracy. The paper also measures the number of deployed LLM calls and inference cost, because the goal is to move recurring control out of the context.

## Results that matter

- Growing Harness has the highest mean success in **five of six benchmark-model settings** and is only **0.7 percentage points** behind the best mean in the sixth.
- Relative to a Tool-Calling agent, it reduces LLM calls by **76.0–91.8%**.
- It reduces deployed-agent inference cost by **74.4–98.6%**.
- On WebArena-Verified, success stays around **44.7–45.3%** across the tested model sizes.
- The Tool-Calling baseline falls to **6.7%** with the 4B model.

That last result is important. A stronger external controller can preserve much more capability when the deployed model becomes small.

## Ablations: what caused the gain

The paper reports that all three are useful:

- **trace-local edits:** reduce search over unrelated code;
- **joint repair:** prevents overfitting to one failure;
- **gate-based rollback:** stops new code from destroying earlier successes.

Together these form a clean pattern: localize → generalize across several failures → globally protect old behavior.

## Failure modes and limits

- The optimizer is stronger than the deployed model, so this is not fully self-contained RSI.
- Function-level locality is only a proxy for causality. An upstream function can cause a downstream failure without looking locally wrong.
- New helper functions can accumulate into tangled code.
- A small success gate can miss rare regressions.
- The system can grow structure, but it does not explicitly reason about split/fuse operations or component ownership.

## Implementation checklist

You need:
- a minimal seed harness;
- function-level trace instrumentation;
- source-location mapping;
- a bounded failure buffer;
- a code-edit optimizer;
- joint replay on several failures;
- a protected-success set;
- version control and rollback;
- cost accounting for model calls.

A useful invariant is: every persistent helper must have at least one recorded failure class it addresses and at least one regression test that protects it.

## What RHEvolution should take from it

This is strong evidence for **emergent executable structure**. RHEvolution should not assume the final decomposition must be present in the seed.

Use execution traces to decide when a repeated control decision deserves a new owner. The difference is that RHEvolution should make structural operations explicit:
- create/split an owner when one source region handles unrelated failure clusters;
- fuse owners when they cannot be validated independently;
- allocate separate search budgets after the split;
- track ownership through source ranges and execution traces.

Growing Harness gives the code-growth mechanism. RHEvolution should add the adaptive structural model and explicit credit assignment.
